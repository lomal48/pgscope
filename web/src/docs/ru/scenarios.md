# Типовые сценарии

Пошаговые рецепты для частых задач: подключить сервер, разобрать медленный запрос и прошедший инцидент, справиться с раздуванием, отставанием реплики, риском wraparound и нехваткой подключений, безопасно почистить индексы, настроить дежурные оповещения в закрытом контуре, подключить много баз в Docker и открыть доступ коллеге. Подробности о каждой странице интерфейса — в соответствующих разделах документации, ссылки даны по ходу.

## Подключить новый сервер за 10 минут {#new-server}

Понадобятся: работающий pgscope, учётная запись владельца и хост сбора, с которого доступны PostgreSQL и pgscope. Лучше всего запускать сбор на самом хосте базы: только тогда pgmetrics соберёт системные метрики и сможет читать журнал PostgreSQL. Если базы работают в Docker, используйте агент (см. [Подключить много баз в Docker](#docker-fleet)).

Первую учётную запись создают по ссылке «Регистрация» на странице входа. По умолчанию (`PGSCOPE_SIGNUP=first`) после неё регистрация закрывается: коллег добавляют приглашениями (см. [Дать доступ коллеге](#share-access)), а если нужны ещё владельцы со своими серверами и API-ключами, на время задайте `PGSCOPE_SIGNUP=open`.

1. **Роль мониторинга.** На ведущем сервере под суперпользователем:

```sql
CREATE ROLE pgmon LOGIN;
GRANT pg_monitor TO pgmon;
\password pgmon
```

Разрешите роли подключение с хоста сбора в `pg_hba.conf`. Подробнее о подготовке, в том числе о `pg_stat_statements` и `auto_explain`, — на странице [Подготовка PostgreSQL](postgres.md). `pg_stat_statements` требует перезапуска PostgreSQL; без него пустой будет только страница «Запросы» (и не будут срабатывать правила уровня «Запрос»), остальное заработает сразу.

2. **Утилиты и пароль.** Положите исполняемые файлы pgmetrics и pgdash CLI на хост сбора (в закрытом контуре — скопируйте файлами) и сохраните пароль роли:

```bash
echo 'DBHOST:5432:*:pgmon:ПАРОЛЬ' >> ~/.pgpass
chmod 600 ~/.pgpass
```

3. **Первая отправка.** Готовая команда с вашим ключом и адресом есть в «Профиль» → «Отправка отчётов»; в ней `db1 db2` — места для имён баз, их можно заменить флагом `--all-dbs`. Выполните команду вручную:

```bash
pgmetrics -w -f json -h DBHOST -U pgmon --all-dbs \
  | pgdash -a APIKEY --base-url=https://pgscope.example.com/api/v1 report prod-db-1
```

Имя сервера (`prod-db-1`) — латинские буквы, цифры и `_ . -`, до 64 символов; удобно брать имя хоста.

4. **Проверка.** Откройте «Серверы»: сервер появился, его «Обзор» и «Диагностика» уже заполнены. Графикам нужно хотя бы два отчёта. Если сервер не появился, см. [Отчёты не доходят](troubleshooting.md#no-data).

5. **Расписание.** Добавьте задачу cron раз в 5 минут. В cron короткий `PATH`, поэтому указывайте полные пути:

```text
*/5 * * * * /usr/local/bin/pgmetrics -w -f json -h DBHOST -U pgmon --all-dbs | /usr/local/bin/pgdash -a APIKEY --base-url=https://pgscope.example.com/api/v1 report prod-db-1
```

Не отправляйте отчёты одного сервера чаще `PGSCOPE_MIN_REPORT_INTERVAL` (по умолчанию 60 секунд): лишние получат ответ 429.

6. **Базовые оповещения.** «Оповещения» → «Правила» → «Новое правило». Хороший стартовый набор:

| Уровень | Метрика | Условие | Важность |
|---|---|---|---|
| Сервер | «Число бэкендов, ожидающих блокировки» | больше 10 | Предупреждение |
| Сервер | «Число бэкендов с транзакциями, открытыми дольше», «Возраст транзакции (минуты)» 30 | больше 0 | Предупреждение |
| Сервер | «Число неактивных слотов репликации» | больше 0 | Критично |
| Сервер | «Число файлов WAL, готовых к архивации» | больше 10 | Предупреждение |
| База данных | «Доля бэкендов от максимума подключений» | больше 80 % | Предупреждение |
| База данных | «Возраст XID в процентах от autovacuum_freeze_max_age» | больше 150 % | Предупреждение |
| Табличное пространство | «Свободное место на диске» | меньше 15 % | Критично |
| Запрос | «Среднее время выполнения запроса» | больше 10 секунд | Предупреждение |

«Свободное место на диске» работает, только если pgmetrics запускается на хосте базы под Linux и подключается локально. Затем добавьте канал на вкладке «Уведомления» (см. [Дежурные оповещения в закрытом контуре](#on-call)). Подробнее о правилах — на странице [Правила оповещений](alerts.md).

## Разобрать медленный запрос {#slow-query}

1. **Когда началось.** На «Обзор» выберите период графиков (1ч … 30д) и найдите момент, когда изменились транзакции, число бэкендов или попадания в кеш.
2. **Если проблема была в прошлом**, щёлкните по графику в этот момент или откройте окно «Перейти к моменту» кнопкой с временем отчёта в верхней панели: страницы «Запросы», «Бэкенды», «Блокировки» и «Диагностика» покажут состояние на тот момент, а кнопки «‹» и «›» (или клавиши `[` и `]`) переключают соседние отчёты. Доступны отчёты за `PGSCOPE_REPORT_RETENTION_DAYS` дней (по умолчанию 14), см. [Выбор прошлого отчёта](ui.md#report-picker).
3. **Какие запросы тяжелее всего.** На «Запросы» отсортируйте по «Общее время»: полоска показывает долю запроса в общем времени. Самые затратные — не обязательно самые медленные: частый быстрый запрос может занимать больше времени, чем редкий медленный.
4. **Страница запроса.** Откройте запрос кликом. В блоке «Советы» — автоматические подсказки: низкая доля попаданий в кеш, временные файлы, слишком много строк на вызов, большой разброс времени. На графиках сравните среднее время и число вызовов по интервалам: запрос стал медленнее или его стали чаще вызывать.
5. **План.** В разделе «Планы выполнения» — планы из `auto_explain` с предупреждениями под узлами (неверная оценка строк, Seq Scan с отбрасыванием строк, сортировка на диске). Если планов нет, см. [Нет планов выполнения](troubleshooting.md#no-plans).
6. **Окружение.** Проверьте «Блокировки» → «Цепочки блокировок» (запрос может ждать, а не работать) и «Бэкенды» с флажком «Только ожидающие». На «Система» видно, не упирается ли сервер в CPU или память (если pgmetrics запускается на хосте базы и подключается локально).
7. **Исправление и проверка.** Типичные решения — индекс, свежая статистика (`ANALYZE`), переписанный запрос, больший `work_mem` для конкретной сессии. Индекс на рабочей базе создавайте без блокировки записи:

```sql
CREATE INDEX CONCURRENTLY orders_customer_id_idx ON public.orders (customer_id);
```

После изменения следите за графиком среднего времени на странице запроса: он считается по интервалам между отчётами, поэтому эффект виден уже через один-два отчёта.

Подробнее о страницах — [Запросы](activity.md#queries), [Блокировки](activity.md#locks).

## Разобрать прошедший инцидент {#past-incident}

Ночью сработало оповещение или пользователи жаловались на ошибки, а сейчас всё в порядке. Посмотрите, каким был сервер в тот момент:

1. **Найдите момент.** На странице «Оповещения», вкладка «История», или в списке «Обнаруженные изменения» на странице «Оповещения об изменениях» нажмите «Открыть отчёт» у нужной записи — откроется «Обзор» на момент этого отчёта. Если записи нет, щёлкните мышью по графику на «Обзоре» в нужной точке или введите время в окне «Перейти к моменту» (кнопка с временем отчёта в верхней панели).
2. **Посмотрите состояние.** Пока выбран прошлый момент, «Запросы», «Бэкенды», «Блокировки», «Журнал», «Диагностика» и остальные страницы сервера показывают данные этого отчёта; переходы по меню и ссылкам момент сохраняют. На графиках отчёт отмечен пунктирной линией.
3. **Пройдите по соседним отчётам** кнопками «‹» и «›» или клавишами `[` и `]`; `Shift+[` и `Shift+]` сдвигают момент на час. Предупреждение «Отчёта на … нет» под панелью означает перерыв в отчётах больше 15 минут — часто это и есть сам инцидент.
4. **Сравните с репликой.** Выберите её в переключателе серверов в боковом меню — она откроется на тот же момент.
5. **Передайте коллеге** «Ссылку на этот отчёт» из окна «Перейти к моменту»: она откроет ту же страницу на тот же момент.
6. **Вернитесь к текущему состоянию** кнопкой «К последнему».

Полные отчёты хранятся `PGSCOPE_REPORT_RETENTION_DAYS` дней (по умолчанию 14), а графики и история событий — `PGSCOPE_METRICS_RETENTION_DAYS` дней (по умолчанию 90), см. [Сроки хранения](data.md#retention). Список сработавших оповещений и AI-чат всегда относятся к текущему состоянию. Подробнее — [Выбор прошлого отчёта](ui.md#report-picker).

## Найти и устранить раздувание {#bloat}

1. **Что раздуто.** «Диагностика» → «Проблемы»: «Раздутые таблицы» (раздувание больше 30 % при размере больше 10 МиБ), «Много мёртвых строк» (больше 10 000 и больше 20 % строк), «Раздутые индексы». Полный список — на «Таблицы» с сортировкой по столбцу «Раздувание». Раздувание — оценка pgmetrics; при `--omit=bloat` её нет, и в карточке стоит «не оценено».
2. **Справляется ли очистка.** На странице таблицы в блоке «Очистка и анализ» видно, когда последний раз работали `VACUUM` и autovacuum. На «Очистка (vacuum)» — «Таблицы с наибольшим числом мёртвых строк» и «Выполняется сейчас».
3. **Что мешает очистке.** Мёртвые строки не удаляются, пока их может видеть хоть одна транзакция:
   - долгие транзакции и сессии в простое в транзакции — «Бэкенды», в диагностике «Долгие транзакции» и «Бездействие в транзакции (idle in transaction)»;
   - слоты репликации со старым `xmin` — «Репликация» → «Слоты репликации», столбец `xmin`;
   - запросы на репликах при `hot_standby_feedback = on`.
4. **Устраните причину** и настройте autovacuum для проблемной таблицы:

```sql
ALTER TABLE public.orders SET (autovacuum_vacuum_scale_factor = 0.02, autovacuum_vacuum_cost_limit = 1000);
VACUUM (VERBOSE, ANALYZE) public.orders;
```

5. **Вернуть место на диске.** Обычный `VACUUM` освобождает место для повторного использования, но файл не уменьшает. `VACUUM FULL` переписывает таблицу и блокирует её целиком — только в окно обслуживания. Без долгой блокировки то же делает расширение `pg_repack`, если оно установлено. Раздутые индексы перестраивайте на «Управление индексами» → «Раздутые»: отметьте индексы и выполните сгенерированный `REINDEX INDEX CONCURRENTLY`.
6. **Оповещение на будущее**: уровень «Таблица», метрика «Раздувание таблицы в процентах от размера», больше 30 %, «Предупреждение». Условия разных правил не объединяются: отдельное правило «Размер таблицы (байты)» сработает само по себе и не ограничит первое. Чтобы не шуметь на мелких таблицах, используйте вместо процента метрику «Раздувание таблицы (байты)» с абсолютным порогом (например, больше 1 ГиБ) или ограничьте правило по имени таблицы и базе.

## Отставание реплики {#replication-lag}

1. **Оповещения.**
   - На ведущем сервере: уровень «Сервер», метрика «Отставание репликации по воспроизведению (replay) на ведущем (байты)», больше 1 ГиБ. Оповещение срабатывает отдельно для каждой реплики.
   - На самой реплике, если она тоже отправляет отчёты как отдельный сервер: «Отставание воспроизведения на реплике (байты)». Вариант «(время)» считается от времени последней воспроизведённой транзакции, поэтому на малоактивном ведущем растёт и без настоящего отставания.
2. **Диагностика** сообщает о «Реплики отстают» (больше 1 ГиБ или 60 секунд), «Реплика не успевает воспроизводить WAL» и «Воспроизведение WAL приостановлено». Если отставание в байтах неизвестно, «Реплики отстают» срабатывает только по времени, а в пункте стоит «отстаёт на —».
3. **Где задержка.** На «Репликация» ведущего сравните отставание по записи, сбросу и воспроизведению:
   - велико уже отставание по записи — WAL не доходит до реплики: сеть или отправка WAL;
   - запись в порядке, а сброс отстаёт — медленный диск реплики;
   - отстаёт только воспроизведение — реплика не успевает применять WAL: нагрузка на её диск и CPU, конфликты с запросами на реплике или пауза воспроизведения.

   У отправителей WAL без известных позиций (`pg_basebackup`, `pg_receivewal`, реплика, которая ещё запускается) отставание в байтах не считается: вместо него стоит «—», и оповещения по отставанию в байтах для них не срабатывают. Так же на реплике без работающего приёмника WAL нет значения «Отставание воспроизведения на реплике (байты)» и пункта «Реплика не успевает воспроизводить WAL».
4. **На реплике** проверьте паузу воспроизведения и состояние приёмника WAL. Снять паузу:

```sql
SELECT pg_wal_replay_resume();
```

5. **Весь парк сразу** — «Инспектор» → «Репликация»: число реплик, максимальное отставание и неактивные слоты по всем серверам. Если у сервера есть реплики, но ни одно отставание не известно, в столбце «Макс. отставание» стоит «—».
6. **Неактивные слоты.** Слот отключённой реплики удерживает WAL, и диск ведущего заполняется. Слот, у которого ещё нет `restart_lsn` (создан, но ни разу не использовался), WAL не удерживает, и диагностика показывает его как «имя (тип)» без объёма. Если реплика больше не нужна, удалите слот и ограничьте удержание WAL параметром `max_slot_wal_keep_size`:

```sql
SELECT pg_drop_replication_slot('old_standby_slot');
```

Подробнее — [Репликация](server.md#replication), [Инспектор](fleet.md#inspector).

## Не допустить переполнения счётчика транзакций {#wraparound}

Диагностика оценивает возраст XID каждой базы относительно предела в 2 147 483 647 транзакций: больше 75 % — «Угроза переполнения счётчика транзакций (wraparound)» (критично), больше 40 % — «Высокий возраст XID». Когда возраст превышает `autovacuum_freeze_max_age`, но ещё не достиг 40 % предела, появляется «Скоро запустится autovacuum против переполнения (wraparound)» — это нормальная работа, но за ней стоит следить.

1. **Оповещения.** Уровень «База данных», метрика «Возраст XID в процентах от autovacuum_freeze_max_age»: больше 150 % — «Предупреждение», больше 500 % — «Критично». При значении `autovacuum_freeze_max_age` по умолчанию (200 млн) это 300 млн и 1 млрд транзакций.
2. **Где старые XID.** «Очистка (vacuum)» → «Возраст XID по базам данных» и «Самые старые таблицы (возраст замороженного XID)»; в «Выполняется сейчас» видно, идёт ли уже очистка этих таблиц.
3. **Что мешает заморозке.** Долгие транзакции и простой в транзакции («Бэкенды»), слоты репликации со старым `xmin` или `catalog_xmin` («Репликация» → «Слоты репликации»), запросы на репликах с `hot_standby_feedback = on` и забытые подготовленные транзакции:

```sql
SELECT gid, prepared, owner, database FROM pg_prepared_xacts ORDER BY prepared;
```

4. **Заморозьте самые старые таблицы** в нужной базе:

```sql
VACUUM (FREEZE, VERBOSE) public.big_table;
```

5. **Настройте autovacuum**, чтобы ситуация не повторялась: `autovacuum_max_workers`, `autovacuum_vacuum_cost_limit`, `maintenance_work_mem`. Не отключайте autovacuum — «Диагностика» → «Проверка конфигурации» отметит это как критичную ошибку.

## Заканчиваются подключения {#connections}

Диагностика сообщает «Число подключений близко к max_connections», когда занято больше 80 % подключений (больше 95 % — критично).

1. **Оповещения.** Уровень «База данных», метрика «Доля бэкендов от максимума подключений», больше 80 % (если у базы задан собственный лимит подключений, процент считается от него). Для сервера целиком — «Общее число бэкендов» с порогом в штуках, например 80 % от `max_connections`.
2. **Кто занимает подключения.** На «Бэкенды» отфильтруйте по базе, пользователю, приложению и состоянию. Сессии в простое в транзакции подсвечены жёлтым, ожидающие блокировок — красным.
3. **Типичные причины:** пул соединений приложения слишком велик (размер пула × число экземпляров), утечки транзакций, очередь запросов за блокировкой (см. «Блокировки»).
4. **Срочные меры.** Завершить зависшие сессии:

```sql
SELECT pg_terminate_backend(pid)
FROM pg_stat_activity
WHERE state = 'idle in transaction'
  AND state_change < now() - interval '30 minutes';
```

5. **Долгосрочные меры:** `idle_in_transaction_session_timeout` и `idle_session_timeout` (PostgreSQL 14+), пулер соединений (PgBouncer в режиме транзакций) и его мониторинг в pgscope (см. [PgBouncer](integrations.md#pgbouncer)). Увеличение `max_connections` требует перезапуска и расходует память на каждое подключение.

## Безопасно почистить индексы {#index-cleanup}

1. **Кандидаты.** «Управление индексами» → «Неиспользуемые». В поле «Не сканировались» выберите период: «с момента сброса статистики» или «за последние 30 дней» / «за последние 90 дней». Число сканирований сравнивается с первым отчётом периода, поэтому нужна история такой длины (см. [Сроки хранения](data.md#retention)). Если истории меньше, сравнение идёт с самыми ранними сохранёнными временными рядами; их дата видна рядом с полем («по сравнению с отчётом от …»). Уникальные индексы в этот список не попадают. Индекс ограничения-исключения (`EXCLUDE`, по умолчанию с именем `*_excl`) не уникален и может оказаться в списке, но `DROP INDEX` для него завершится ошибкой: такой индекс удаляют только вместе с ограничением.
2. **Проверьте каждый кандидат:**
   - статистика использования своя у каждого сервера: если часть запросов идёт на реплики, проверьте тот же индекс на странице реплики в pgscope;
   - редкие задачи (ежемесячные отчёты, закрытие периода) берите период 90 дней;
   - столбец «Последнее использование» (PostgreSQL 16+) показывает время последнего сканирования.
3. **Сохраните определения** удаляемых индексов, чтобы при необходимости быстро их вернуть:

```sql
SELECT indexrelid::regclass AS index_name, pg_get_indexdef(indexrelid) AS definition
FROM pg_index
WHERE indexrelid = 'public.orders_created_at_idx'::regclass;
```

4. **Удаление.** Отметьте индексы флажками — ниже появится SQL с `DROP INDEX CONCURRENTLY`, сгруппированный по базам (со строкой `\c база` для psql). Выполняйте его в psql вне транзакции (`CONCURRENTLY` внутри транзакции не работает), по одному индексу, в спокойное время, и следите за временем запросов после удаления.
5. **Дубликаты.** На вкладке «Дубликаты» pgscope группирует индексы с одинаковым определением (признак `UNIQUE` при сравнении не учитывается). В каждой группе он оставляет индекс первичного ключа, если его нет — уникальный индекс, затем индекс ограничения, а остальные предлагает удалить. Уникальный индекс не предлагается, пока в группе есть неуникальный дубликат, а индексы первичного ключа и ограничений (`*_pkey`, `*_key`, `*_excl`) не предлагаются никогда. Тот же выбор показывает «Диагностика» в пункте «Дублирующиеся индексы» строками вида «t_id_idx повторяет t_pkey». pgmetrics не сообщает, какой индекс обеспечивает ограничение, поэтому pgscope узнаёт такие индексы только по именам, которые PostgreSQL даёт по умолчанию: у ограничения с другим именем проверьте индекс сами. Пару из уникального индекса и индекса ограничения `*_key` на тех же столбцах pgscope может не отметить вовсе — такие пары тоже проверяйте вручную.
6. **Раздутые индексы** — вкладка «Раздутые», SQL `REINDEX INDEX CONCURRENTLY`. На время перестройки нужно свободное место примерно размером с индекс.
7. **Откат** — `CREATE INDEX CONCURRENTLY` по сохранённому определению.

Подробнее — [Управление индексами](objects.md#index-management).

## Дежурные оповещения в закрытом контуре {#on-call}

Slack, PagerDuty, VictorOps и xMatters — облачные сервисы, и для них нужен доступ в интернет (адрес PagerDuty в pgscope зафиксирован: `https://events.pagerduty.com/v2/enqueue`). В закрытом контуре используйте email через внутренний SMTP-сервер или вебхук на внутренний адрес.

1. **SMTP.** Задайте `PGSCOPE_SMTP_ADDR` (например, `mail.example.local:25`) и `PGSCOPE_SMTP_FROM` с адресом, который примет почтовый сервер, и перезапустите pgscope (см. [Почта (SMTP)](config.md#smtp)). Письма pgscope содержат заголовки `Date` и `Message-ID`, которых требуют строгие почтовые серверы.
2. **Каналы.** На каждом сервере: «Оповещения» → «Уведомления» → «Канал» «Email» (несколько адресов через запятую; пробелы и пустые элементы списка игнорируются, а на повторяющийся адрес приходит одно письмо) или «Вебхук» с адресом внутреннего приёмника, затем «Добавить» и «Проверить». Формат вебхука — [Формат вебхука](notifications.md#webhook).
3. **Правила.** Начните со стартового набора из раздела [Подключить новый сервер за 10 минут](#new-server).
4. **Оповещения об изменениях** настраиваются отдельно, со своими каналами (см. [Оповещения об изменениях](change-alerts.md)).
5. **Как работает доставка** — учтите при выборе приёмника:
   - уведомление отправляется только при изменении набора сработавших оповещений: появилось новое или снято прежнее. Пока набор тот же, повторов нет, и изменение значения у уже сработавшего оповещения уведомления не вызывает. Добавление или удаление правила сразу перепроверяет последний отчёт и тоже может отправить уведомление;
   - когда всё нормализовалось, приходит уведомление о том, что все оповещения сняты;
   - если доставка не удалась, уведомление позже не повторяется. Письмо, которое SMTP-сервер не принял за 30 секунд, считается недоставленным. HTTP-каналы (вебхук, Slack, PagerDuty, VictorOps, xMatters) повторяют запрос до трёх раз с паузой 5 секунд, только если приёмник не ответил за 3 секунды; ответ с кодом не 2xx не повторяется. Ошибки пишутся в журнал pgscope строкой `notify …`.
6. **Контроль прихода отчётов.** pgscope проверяет правила только при получении отчёта, поэтому если сбор остановился, оповещений не будет. Проверяйте свежесть отчётов внешним заданием по базе для хранения. Роль только для чтения:

```sql
CREATE ROLE pgscope_check LOGIN PASSWORD 'secret';
GRANT SELECT ON servers TO pgscope_check;
```

Запрос серверов, от которых больше 15 минут нет отчётов:

```sql
SELECT name, last_report
FROM servers
WHERE last_report IS NULL OR last_report < now() - interval '15 minutes'
ORDER BY last_report NULLS FIRST;
```

Пример задания cron с отправкой письма через системный `mail`:

```bash
#!/bin/sh
# запускать раз в 10 минут; пароль роли — в ~/.pgpass
out=$(psql "postgres://pgscope_check@dbhost/pgscope" -XAt -c \
  "SELECT name FROM servers WHERE last_report < now() - interval '15 minutes'")
[ -n "$out" ] && printf 'Нет свежих отчётов:\n%s\n' "$out" | mail -s 'pgscope: устаревшие серверы' oncall@example.com
```

Время отчёта задаёт хост сбора, поэтому его часы должны быть синхронизированы. Отчёты PgBouncer время последнего отчёта сервера не обновляют.

7. **Контроль самого pgscope.** Если pgscope остановлен, он ничего не пришлёт. Проверяйте его доступность внешним мониторингом, например `curl -fsS -o /dev/null https://pgscope.example.com/`.

## Подключить много баз в Docker {#docker-fleet}

Для баз в контейнерах вместо cron на каждую базу используется pgscope-agent: один агент на Docker-хост или глобальный сервис в Swarm. Подробная инструкция — на странице [Docker и Docker Swarm](docker.md).

1. **Образы.** Соберите `pgscope-agent` на машине с доступом в интернет и перенесите в контур (`docker save` / `docker load` на каждом хосте и узле Swarm или внутренний registry).
2. **Секреты.** Подготовьте API-ключ из «Профиль» и пароль роли `pgscope_monitor`.
3. **Роль мониторинга.** На каждом Docker-хосте и узле Swarm с базами выполните `deploy/agent/bootstrap-monitor-role.sh --with-pg-stat-statements`.
4. **Метки.** Добавьте контейнерам баз метку `pgscope.enable=true`; в Swarm — в `labels:` сервиса, а не в `deploy.labels`. Имя сервера в pgscope строится автоматически или задаётся меткой `pgscope.name` (см. [Метки контейнеров](docker.md#labels)).
5. **Запуск.** На отдельных хостах — `deploy/agent/docker-compose.yml`; если на разных хостах есть проекты Compose с одинаковыми именами, задайте каждому хосту свой `PGSCOPE_AGENT_CLUSTER`. В Swarm — стек `deploy/agent/docker-stack.yml` с обязательным `PGSCOPE_AGENT_CLUSTER` и overlay-сетями баз, объявленными в стеке.
6. **Проверка.** На странице «Агенты» у каждой цели должен быть статус «Работает». Первые сборы распределены по интервалу (по умолчанию 5 минут), поэтому сначала цели будут в статусе «Ожидает первого сбора». Если статус другой, см. [Решение проблем](docker.md#troubleshooting).
7. **Объём хранения.** Десятки баз дают много временных рядов: оцените объём заранее (см. [Объём данных](data.md#sizing)).
8. **Правила оповещений** задаются для каждого сервера отдельно, шаблонов правил нет. Для большого числа серверов правила можно добавить скриптом через внутренний API (он может меняться между версиями, см. [Внутренний API интерфейса](api.md#internal-api)). Пример добавляет правило «Свободное место на диске меньше 15 %» всем серверам, чьё имя начинается с `prod-swarm.`; нужны curl, jq и cookie сеанса в файле `jar`, полученный, как показано в разделе [Пример](api.md#internal-example):

```bash
BASE=https://pgscope.example.com
for id in $(curl -sS -b jar "$BASE/api/servers" \
    | jq -r '.[] | select(.kind == "postgres" and (.name | startswith("prod-swarm."))) | .id'); do
  curl -sS -b jar -X POST "$BASE/api/servers/$id/alerts/rules" -H 'Content-Type: application/json' \
    -d '{"metric":"ts_disk_free_pct","op":"lt","threshold":15,"param":0,"severity":"crit","match":"all","match_text":"","db_name":""}'
  echo
done
```

Повторный запуск создаст правила-дубликаты: pgscope их не объединяет. Каждое добавленное правило сразу проверяется по последнему отчёту сервера, поэтому уведомления по уже настроенным каналам могут прийти сразу. Идентификаторы метрик и единицы порогов есть в каталоге, который возвращает `GET /api/servers/{id}/alerts`.

Учтите, что pgmetrics агента работает в контейнере агента и подключается к базе по IP контейнера. pgmetrics считает подключение локальным, только если адреса клиента и сервера совпадают (или подключение идёт через Unix-сокет), поэтому системные метрики и журнал PostgreSQL для таких баз, как правило, не собираются.

## Дать доступ коллеге {#share-access}

Доступ открывается к конкретному серверу, и сделать это может только его владелец.

1. Откройте сервер → «Команда и настройки» → карточка «Совместный доступ».
2. Введите адрес в поле «Пригласить по email» и нажмите «Пригласить».
   - Если у коллеги уже есть учётная запись в этом pgscope, доступ появляется сразу (при настроенном SMTP письмо получат и он, и вы).
   - Если нет, создаётся приглашение. Ссылка уходит на почту, если настроен SMTP, а её копия видна в списке рядом с адресом (кнопка копирования) — её можно передать самостоятельно. По ссылке коллега задаёт пароль и получает учётную запись участника команды. Ссылка строится из `PGSCOPE_BASE_URL`, поэтому он должен быть задан правильно.
   - Повторное приглашение того же адреса не создаёт второе: pgscope обновляет первое и отправляет ту же ссылку. Приглашение действует, пока по нему не создана учётная запись, поэтому ошибка при принятии (например, слишком короткий пароль) его не расходует.
   - Зарегистрироваться самостоятельно коллега обычно не может: при `PGSCOPE_SIGNUP=first` (по умолчанию) и `closed` новые учётные записи появляются только по приглашениям. Принять приглашение можно при любом режиме.
3. Что может участник: смотреть все данные сервера, пользоваться диагностикой и AI-чатом, менять правила оповещений, каналы уведомлений и настройки оповещений об изменениях. Чего не может: приглашать других, отзывать доступ, удалять сервер, иметь API-ключ и отправлять отчёты. Режима «только чтение» нет: участник может, например, добавить канал уведомлений на свой адрес.
4. Доступ открывается к одному серверу. Для нескольких серверов повторите приглашение на каждом; если у коллеги уже есть учётная запись, доступ к следующим серверам появится сразу.
5. **Отозвать доступ** — значок корзины рядом с участником («Отозвать доступ») или рядом с приглашением («Отменить приглашение»). Учётная запись участника при этом остаётся, но без открытых серверов он ничего не видит; удалить её может сам участник («Профиль» → «Удалить аккаунт») или администратор в базе для хранения.

Подробнее — на странице [Команда, профиль и аккаунт](teams.md#server-settings).
