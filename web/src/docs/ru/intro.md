# Что такое pgscope

pgscope — система мониторинга PostgreSQL, которую вы разворачиваете в своей инфраструктуре. Она принимает снимки состояния серверов PostgreSQL, PgBouncer и Pgpool-II, хранит их в собственной базе PostgreSQL, строит графики, находит проблемы, присылает оповещения и показывает всё это в веб-интерфейсе. На этой странице описано, как pgscope устроен, что он собирает, из каких частей состоит и как ориентироваться в документации.

## Для кого {#audience}

- **Администраторам баз данных (DBA)** — разбирать медленные запросы, блокировки, раздувание таблиц и индексов, отставание реплик, риск переполнения счётчика транзакций (wraparound) и ошибки конфигурации.
- **DevOps- и SRE-инженерам** — следить за парком серверов, получать оповещения на почту или во внутренние системы через вебхуки, видеть изменения схемы и параметров между отчётами.
- **Командам в закрытом контуре** — pgscope не требует облачных сервисов и не связывается с внешними адресами сам по себе (подробности в разделе [Только self-hosted](#self-hosted)).

## Как это устроено {#architecture}

pgscope работает по модели push: он не подключается к наблюдаемым базам. Данные ему присылают.

```text
PostgreSQL / PgBouncer / Pgpool-II
        │  запросы к статистическим представлениям (только чтение)
        ▼
pgmetrics ── снимок состояния сервера в формате JSON
        │
        ▼
pgdash CLI (cron, systemd-таймер) или pgscope-agent (Docker, Docker Swarm)
        │  HTTP POST /api/v1/report, /api/v1/reportpgbouncer, /api/v1/reportpgpool
        ▼
pgscope ── сохраняет отчёт и временные ряды в свою базу PostgreSQL
        ├──► веб-интерфейс: графики, таблицы, диагностика, Инспектор, AI-чат
        └──► правила оповещений и поиск изменений ──► email, вебхук и другие каналы
```

1. **pgmetrics** — открытая утилита: за один запуск она выполняет запросы к статистике PostgreSQL и выдаёт снимок состояния (отчёт) в JSON.
2. **pgdash CLI** — открытая утилита: отправляет этот JSON на сервер мониторинга. Обычно связку `pgmetrics | pgdash` запускают по расписанию на хосте с базой или рядом с ним.
3. **pgscope-agent** — агент pgscope для баз в контейнерах: сам находит контейнеры PostgreSQL и PgBouncer с меткой `pgscope.enable=true`, запускает pgmetrics и отправляет отчёты (см. [Docker и Docker Swarm](docker.md)).
4. **pgscope** принимает отчёт, проверяет API-ключ, сохраняет отчёт целиком в сжатом виде и извлекает из него временные ряды. Затем для отчётов PostgreSQL он проверяет правила оповещений и сравнивает отчёт с предыдущим, чтобы найти изменения.

Один отчёт — это снимок на момент сбора. Графики и тренды появляются, когда отчёты приходят регулярно.

## Что собирается и как часто {#data-collected}

Состав отчёта определяет pgmetrics. В него входят, в частности:

- сведения о сервере: версия, время запуска, режим восстановления (реплика), параметры конфигурации;
- бэкенды (сессии), блокировки и цепочки блокировок;
- репликация: реплики, отставание, слоты репликации;
- WAL, архивация, контрольные точки, фоновая запись;
- базы данных, табличные пространства, таблицы, индексы, последовательности, функции, расширения, роли, триггеры;
- статистика запросов из `pg_stat_statements` (если расширение установлено);
- процессы очистки (vacuum) в работе;
- системные метрики хоста (только Linux) и данные из журнала PostgreSQL (планы `auto_explain`, история autovacuum) — только если pgmetrics запущен на хосте базы данных: журнал он читает с локального диска, путь к нему можно указать флагами `--log-file` или `--log-dir` (для AWS RDS и Aurora журнал берётся из CloudWatch);
- метрики AWS CloudWatch и Azure Monitor — если pgmetrics запущен с соответствующими флагами;
- статистика PgBouncer и Pgpool-II — в отдельных отчётах.

Из каждого отчёта pgscope сохраняет:

| Что | Где используется | Срок хранения по умолчанию |
|---|---|---|
| Полный отчёт (JSON, сжатый gzip) | все страницы сервера, выбор прошлого отчёта, диагностика, AI-чат | 14 дней; последний отчёт каждого сервера хранится всегда |
| Временные ряды по серверу, базам, таблицам, индексам, запросам, функциям, табличным пространствам, репликам, слотам, PgBouncer и Pgpool | графики, рост размеров и числа строк в «Топ-k», неиспользуемые индексы за выбранный период в «Управление индексами» | 90 дней |
| История сработавших оповещений и обнаруженных изменений | вкладки истории на страницах оповещений | 90 дней |

Сроки настраиваются (см. [Настройка pgscope](config.md#retention-vars) и [Хранение данных](data.md#retention)).

Частоту задаёт тот, кто отправляет отчёты. Рекомендуемый интервал — 5 минут: так предлагает интерфейс, и таков интервал pgscope-agent по умолчанию (300 секунд). pgscope принимает отчёты одного сервера не чаще одного раза в 60 секунд (настраивается переменной `PGSCOPE_MIN_REPORT_INTERVAL`), более частые отклоняются с кодом 429.

## Совместимость с pgdash CLI {#pgdash-compatibility}

pgscope реализует тот же API приёма отчётов, что использует открытый pgdash CLI:

| Команда pgdash CLI | Адрес в pgscope | Что принимает |
|---|---|---|
| `report ИМЯ-СЕРВЕРА` | `POST /api/v1/report` | отчёт PostgreSQL |
| `report-pgbouncer ИМЯ-СЕРВЕРА ИМЯ-PGBOUNCER` | `POST /api/v1/reportpgbouncer` | отчёт PgBouncer, привязанный к серверу PostgreSQL |
| `report-pgpool ИМЯ-PGPOOL` | `POST /api/v1/reportpgpool` | отчёт Pgpool-II |

Чтобы направить существующие задания cron в pgscope, достаточно указать `--base-url=https://ВАШ-PGSCOPE/api/v1` и API-ключ из профиля pgscope. Проверки совпадают с проверками pgdash CLI: API-ключ — ровно 22 латинские буквы и цифры, имя сервера — от 1 до 64 символов из латинских букв, цифр и `_ . -`.

> [!WARNING]
> Всегда указывайте `--base-url`. Без него pgdash CLI отправляет отчёт на адрес по умолчанию — в облачный сервис pgDash, а не в ваш pgscope.

pgscope — самостоятельный продукт с тем же набором возможностей, что у pgDash, но это не pgDash и не связан с его облачным сервисом.

## Только self-hosted {#self-hosted}

- pgscope — один исполняемый файл со встроенным веб-интерфейсом. Все данные хранятся в базе PostgreSQL, которую вы ему указали.
- Нет телеметрии, проверки лицензий и обновлений, обращений «домой». Веб-интерфейс не загружает ресурсы из интернета: скрипты и стили встроены в исполняемый файл, шрифты используются системные.
- Кроме подключения к базе для хранения, pgscope устанавливает исходящие соединения только в двух случаях:
  - **уведомления**: SMTP-сервер из настроек, адреса вебхуков, а также внешние сервисы Slack, PagerDuty (`events.pagerduty.com`), VictorOps и xMatters, если вы создали такие каналы;
  - **AI-чат**: запросы к облачному API Anthropic, если задан `PGSCOPE_AI_KEY`.
- В закрытом контуре используйте email через внутренний SMTP-сервер и вебхуки на внутренние адреса, а AI-чат оставьте выключенным (по умолчанию он выключен). Подробнее: [Почта (SMTP)](config.md#smtp), [AI-чат](config.md#ai), [Формат вебхука](notifications.md#webhook).
- Образы Docker и бинарный файл собираются на машине с интернетом и переносятся в контур файлами (см. [Установка в закрытом контуре](install.md#air-gapped)).

## Компоненты {#components}

| Компонент | Что это | Где работает |
|---|---|---|
| Сервер pgscope | исполняемый файл `pgscope` (или образ `pgscope:latest`): API приёма отчётов, веб-интерфейс, оповещения, диагностика | любой Linux-хост или контейнер, порт 8080 по умолчанию |
| База для хранения | обычная база PostgreSQL; таблицы pgscope создаёт сам при запуске | отдельный сервер PostgreSQL или контейнер `postgres:17-alpine` из `deploy/docker-compose.yml` |
| pgmetrics | сборщик статистики | на хосте базы данных или рядом с ним; входит в образ агента |
| pgdash CLI | отправка отчётов в pgscope | там же, где pgmetrics |
| pgscope-agent | агент для баз в Docker и Docker Swarm (образ `pgscope-agent:latest` с pgmetrics внутри) | на каждом Docker-хосте или глобальным сервисом Swarm |
| Обратный прокси | nginx, Caddy и т. п. — HTTPS перед pgscope (сам pgscope TLS не поддерживает) | перед сервером pgscope |

## Возможности {#features}

- **Парк серверов**: список серверов с краткой сводкой и [Инспектор](fleet.md#inspector) — сводные таблицы по всем серверам, базам, репликации, возрасту транзакций, дискам и WAL.
- **Страницы сервера**: [обзор](monitoring.md#overview), [диагностика](monitoring.md#diagnostics) (проблемы и проверка конфигурации), [запросы](activity.md#queries) с планами `auto_explain`, [бэкенды](activity.md#backends), [блокировки](activity.md#locks), [базы данных](objects.md#databases), [таблицы](objects.md#tables), [индексы](objects.md#indexes) и [управление индексами](objects.md#index-management), [репликация](server.md#replication), [WAL](server.md#wal), [очистка](server.md#vacuum), [конфигурация](server.md#config), [система](server.md#system), [журнал](server.md#logs), [PgBouncer](integrations.md#pgbouncer) и [Pgpool](integrations.md#pgpool).
- **Просмотр прошлого**: любой сохранённый отчёт можно открыть вместо последнего, чтобы увидеть запросы, блокировки и бэкенды на момент инцидента.
- **Оповещения**: [правила](alerts.md) по метрикам сервера, баз, таблиц, табличных пространств и запросов с уровнями «Предупреждение» и «Критично»; [оповещения об изменениях](change-alerts.md) между соседними отчётами; [каналы уведомлений](notifications.md) — email, Slack, PagerDuty, VictorOps, xMatters, вебхук.
- **Команда**: доступ к серверу по email-приглашению (см. [Команда, профиль и аккаунт](teams.md)).
- **AI-чат** по последнему отчёту сервера (выключен по умолчанию, использует облачный API, см. [AI-чат](monitoring.md#ai-chat)).
- **Интерфейс на русском и английском**: язык выбирается в профиле, язык уведомлений — для каждого канала отдельно.

## Ограничения {#limitations}

- Детализация данных равна интервалу отправки отчётов (обычно 5 минут). Это не мониторинг в реальном времени: события между отчётами не видны.
- Правила оповещений проверяются только при поступлении нового отчёта. Если сбор остановился, оповещение об этом не придёт. Следите за индикатором свежести отчёта в интерфейсе: он становится жёлтым, если последнему отчёту больше 15 минут.
- pgscope не поддерживает TLS сам: HTTPS обеспечивает обратный прокси (см. [Reverse proxy и HTTPS](install.md#reverse-proxy)).
- Рассчитан на один экземпляр на одну базу хранения: ограничение частоты отчётов хранится в памяти процесса.
- Регистрация открыта для всех, кто может открыть веб-интерфейс. Каждый новый пользователь получает свой API-ключ и видит только свои серверы и серверы, к которым ему открыли доступ. Отключить регистрацию настройкой нельзя, поэтому ограничивайте доступ к pgscope на уровне сети.
- Нет входа через LDAP или SSO. Роли — только владелец сервера и участник команды.
- Каналы Slack, PagerDuty, VictorOps, xMatters и AI-чат требуют доступа в интернет.

## Глоссарий {#glossary}

| Термин | Что означает |
|---|---|
| Отчёт | JSON-снимок состояния сервера, собранный pgmetrics за один запуск и отправленный в pgscope |
| Сервер | объект в pgscope, которому принадлежат отчёты: экземпляр PostgreSQL или Pgpool-II. Создаётся автоматически при первом отчёте под новым именем; имя уникально в пределах аккаунта и типа (PostgreSQL или Pgpool) |
| Экземпляр PgBouncer | источник отчётов PgBouncer, привязанный к серверу PostgreSQL под своим именем |
| API-ключ | 22-символьный ключ из профиля, которым pgdash CLI и агент подписывают отчёты. Все серверы, отправленные с ключом, принадлежат его владельцу |
| Владелец | пользователь, чьим API-ключом отправляются отчёты сервера. Может открывать доступ другим и удалять сервер |
| Участник команды | пользователь, которому владелец открыл доступ к серверу. Может смотреть все данные сервера и менять правила оповещений и каналы, но не может удалить сервер или открыть доступ другим. Если учётная запись создана по приглашению, у неё нет API-ключа |
| Агент | pgscope-agent: процесс на Docker-хосте, который находит контейнеры с базами и отправляет их отчёты |
| Цель агента | контейнер PostgreSQL или PgBouncer, найденный агентом по метке |
| Правило оповещения | условие «метрика больше или меньше порога» с уровнем «Предупреждение» или «Критично» и фильтром объектов |
| Оповещение | сработавшее правило для конкретного объекта (базы, таблицы, запроса и т. д.) |
| Оповещение об изменении | различие между двумя соседними отчётами: новая таблица, изменённый параметр, перезапуск сервера и т. п. |
| Канал уведомлений | куда отправлять оповещения или изменения: email, Slack, PagerDuty, VictorOps, xMatters, вебхук. Для каждого канала задаётся язык |
| Диагностика | автоматические проверки последнего отчёта: проблемы сервера и проверка конфигурации |
| Инспектор | сводные таблицы по всем серверам аккаунта |
| База для хранения | база PostgreSQL, в которой pgscope хранит пользователей, отчёты, временные ряды и настройки (`PGSCOPE_DB`) |
| Базовый адрес | публичный адрес pgscope (`PGSCOPE_BASE_URL`), из которого строятся ссылки в оповещениях и приглашениях |
