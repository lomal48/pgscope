# Объекты баз данных

Эта страница описывает раздел «Объекты» сервера PostgreSQL: «Базы данных», «Таблицы», «Индексы», «Управление индексами», «Топ-k», «Табличные пространства», «Расширения и прочее» и «Роли». Здесь объяснено, откуда берутся показатели, как их читать, какие значения считать тревожными и как пользоваться SQL, который pgscope генерирует для обслуживания индексов и табличных пространств.

## Откуда берутся данные {#data-source}

Все страницы раздела строятся из отчёта pgmetrics: по умолчанию из последнего, а если в верхней панели сервера выбран прошлый отчёт — из него (см. [Интерфейс](ui.md)). Графики в блоках «Динамика» строятся из временных рядов, которые pgscope сохраняет при приёме каждого отчёта, и охватывают период, выбранный в верхней панели.

Что важно помнить при чтении цифр:

- В отчёт попадают только базы, которые pgmetrics обошёл при сборе: перечисленные в командной строке или все пользовательские базы при `--all-dbs` (см. [Отправка отчётов](collect.md)). Таблицы и индексы фильтруются флагами pgmetrics `-c`, `-C`, `-a`, `-A`, а `--omit=tables`, `--omit=indexes` и `--omit=indexdefs` отключают сбор таблиц, индексов или определений индексов (`--omit=tables` отключает и индексы, и отключённые триггеры).
- Счётчики PostgreSQL (сканирования, вставки, попадания в кеш, временные файлы, взаимоблокировки и т. п.) накопительные: в таблицах показано значение с момента последнего сброса статистики. Дату сброса для базы видно на её странице в поле «Сброс статистики». На графиках те же счётчики пересчитываются в скорость между соседними отчётами.
- Размеры собираются функциями PostgreSQL: таблица — `pg_table_size` (данные, TOAST и служебные слои без индексов), индекс — `pg_total_relation_size` индекса, база — `pg_database_size`, табличное пространство — `pg_tablespace_size`. Если pgmetrics не смог получить размер (тайм-аут блокировки или флаг `-S` / `--no-sizes`), значение отсутствует, а на графике будет разрыв, а не ноль.
- Раздувание (bloat) — оценка, которую pgmetrics вычисляет по статистике планировщика (формула из check_postgres), а не точное измерение. При `--omit=bloat` оценки нет, и в столбце «Раздувание» стоит «—».

Таблицы на страницах сортируются щелчком по заголовку столбца, поле «Фильтр…» ищет по тексту строки, щелчок по строке открывает страницу объекта.

## Базы данных {#databases}

Страница «Базы данных» — список всех баз из отчёта, по умолчанию отсортированный по размеру.

| Столбец | Что показывает |
|---|---|
| «База данных» | имя базы; щелчок открывает страницу базы |
| «Размер» | `pg_database_size` |
| «Бэкенды» | число текущих подключений к базе (`numbackends`) |
| «Доля фиксаций» | `xact_commit / (xact_commit + xact_rollback)` с момента сброса статистики |
| «Попадания в кеш» | доля чтений блоков из общего буферного кеша: `blks_hit / (blks_hit + blks_read)`; значение ниже 90 % подсвечивается |
| «Возраст XID / лимит заморозки» | `age(datfrozenxid)` в процентах от `autovacuum_freeze_max_age` |
| «Транзакции» | сумма фиксаций и откатов |
| «Временные файлы» | объём данных, записанных во временные файлы (`temp_bytes`) |
| «Взаимоблокировки» | число взаимоблокировок (`deadlocks`) |
| «Конфликты» | запросы, отменённые из-за конфликтов с восстановлением (имеет смысл на репликах) |

Как читать:

- **Попадания в кеш ниже 90 %** на нагруженной базе означают, что рабочий набор данных не помещается в `shared_buffers`. Проверьте `shared_buffers` (обычно около 25 % RAM) и тяжёлые запросы на странице «Запросы» ([Запросы, бэкенды и блокировки](activity.md#queries)).
- **Доля фиксаций ниже 90 %** — приложение часто откатывает транзакции: ищите ошибки в приложении и на странице «Журнал» ([Журнал](server.md#logs)).
- **Возраст XID больше 100 %** — для базы уже запланирован агрессивный autovacuum против переполнения счётчика транзакций. Подробнее — в разделе [Очистка (vacuum)](server.md#vacuum).
- **Растущие временные файлы** — сортировки и хеш-операции не помещаются в `work_mem`.

Карточки вверху страницы:

| Карточка | Что показывает |
|---|---|
| «Размер» | размер базы |
| «Бэкенды» | текущие подключения; подпись — «лимит N», если для базы задан `CONNECTION LIMIT`, иначе «без лимита подключений» |
| «Доля фиксаций» | как в списке баз |

| «Таблицы» | число таблиц базы в отчёте и число индексов |

Ниже — сводка накопительных счётчиков: «Строк выбрано», «Строк вставлено», «Строк обновлено», «Строк удалено», «Временные файлы» (число файлов и объём), «Взаимоблокировки», «Конфликты», «Время чтения блоков» и «Время записи блоков» (заполняются только при `track_io_timing = on`), «Сеансы» и «Сеансы: оборванные / прерванные» (PostgreSQL 14+), «Ошибки контрольных сумм» и «Сброс статистики».

Блок «Динамика» содержит графики: «Транзакции» (фиксации и откаты в секунду), «Строки» (выбрано, вставлено, обновлено, удалено в секунду), «Попадания в кеш» (доля за каждый интервал между отчётами), «Размер», «Бэкенды», «Временные файлы» (байт в секунду), «Возраст замороженного XID», «Взаимоблокировки и конфликты» (в минуту).

Ниже графиков:

- «Крупнейшие таблицы» — таблицы базы по размеру с числом строк и долей мёртвых строк;
- «Расширения» — установленные в базе расширения со схемой, версией и описанием; если доступна более новая версия, рядом с установленной стоит отметка «доступна X»;
- «Отключённые триггеры» — показывается, только если в базе есть отключённые триггеры.

> [!TIP]
> Если «Ошибки контрольных сумм» больше нуля, данные на диске повреждены. Это критичная проблема: проверьте хранилище и резервные копии. Счётчик заполняется, только если в кластере включены контрольные суммы данных (`data_checksums`).

## Таблицы {#tables}

Страница «Таблицы» — все таблицы из отчёта, включая секции секционированных таблиц (отмечены «секция»). Список фильтруется по базе выпадающим списком «Все базы» и полем поиска.

| Столбец | Что показывает |
|---|---|
| «Таблица» | `схема.имя` |
| «База данных» | база, в которой лежит таблица |
| «Размер» | `pg_table_size` |
| «Раздувание» | оценка лишнего места и её доля от размера; больше 30 % подсвечивается, «—» — оценки нет |
| «Живые строки» | `n_live_tup` |
| «Мёртвые строки» | `n_dead_tup`; подсвечивается, если мёртвых больше 20 % и больше 1000 |
| «Посл. сканирования» | число последовательных сканирований (`seq_scan`) |
| «Индексные сканирования» | число индексных сканирований (`idx_scan`) |
| «Попадания в кеш» | доля чтений блоков кучи из кеша |
| «Последняя очистка» | самая поздняя из ручной очистки и autovacuum, «никогда» — не было ни одной |
| «Последний анализ» | самый поздний из ручного ANALYZE и autoanalyze |

Как читать:

- Много мёртвых строк и давняя «Последняя очистка» — autovacuum не успевает. Смотрите [Очистка (vacuum)](server.md#vacuum) и настройки `autovacuum_vacuum_scale_factor` / `autovacuum_vacuum_cost_limit` для конкретной таблицы.
- Большая таблица, у которой последовательных сканирований больше, чем индексных, — вероятно, не хватает индекса. Найдите запросы к ней на странице «Запросы».
- Раздувание больше 30 % — кандидат на `VACUUM FULL` (блокирует таблицу) или `pg_repack`; в первую очередь стоит выяснить, почему autovacuum не справляется.

### Страница таблицы {#table-detail}

Карточки: «Размер» (с табличным пространством, если оно не по умолчанию), «Раздувание» (объём и доля от размера, «не оценено» без оценки), «Живые строки», «Мёртвые строки» (с долей от всех строк, подсвечивается выше 20 %), «Попадания в кеш», «HOT-обновления» (доля обновлений, выполненных без изменения индексов).

Блок «Очистка и анализ»:

- «Последняя ручная очистка», «Последний autovacuum», «Последний ручной анализ», «Последний autoanalyze»;
- «Очистки (вручную / авто)» и «Анализы (вручную / авто)» — счётчики запусков;
- «Изменено после анализа» (`n_mod_since_analyze`) и «Вставлено после очистки» (`n_ins_since_vacuum`, PostgreSQL 13+);
- «Возраст замороженного XID» таблицы (`age(relfrozenxid)`).

Блок «Активность»: последовательные и индексные сканирования с числом прочитанных и выбранных строк, «Последнее посл. / индексное сканирование» (PostgreSQL 16+), «Строк вставлено / обновлено / удалено», попадания и чтения блоков кучи, индексов и TOAST, число столбцов, «Тип» (таблица, секционированная таблица, материализованное представление, внешняя таблица; для нежурналируемых добавляется «нежурналируемая») и для секции — «Секция таблицы» с родителем и границами.

Графики «Динамика»: «Размер» (с раздуванием), «Строки» (живые и мёртвые), «Изменения строк» (вставки, обновления, удаления в секунду), «Сканирования» (последовательные и индексные в секунду), «Попадания в кеш» (куча), «Запуски очистки и анализа» (autovacuum и autoanalyze в час).

Ниже — «Индексы (N)» таблицы в том же формате, что и на странице «Индексы», а у секционированной таблицы — «Секции (N)» с границами, размером и числом строк каждой секции.

> [!TIP]
> Низкая доля HOT-обновлений у часто обновляемой таблицы означает, что каждое обновление меняет и индексы. Помогает уменьшение `fillfactor` таблицы и отказ от индексов на часто изменяемых столбцах.

### Страница индекса {#index-detail}

Вверху — определение индекса (`CREATE INDEX …`) и ссылка на таблицу. Карточки: «Размер», «Раздувание», «Сканирования» (с временем последнего на PostgreSQL 16+), «Прочитано кортежей», «Выбрано кортежей», «Попадания в кеш».

Блок «SQL для обслуживания» содержит готовые команды с правильно экранированными именами:

```sql
-- подключитесь к базе shop
REINDEX INDEX CONCURRENTLY "public"."orders_created_at_idx";
-- или, если индекс не нужен:
DROP INDEX CONCURRENTLY "public"."orders_created_at_idx";
```

Графики «Динамика»: «Сканирования» в секунду, «Размер» (с раздуванием), «Кортежи» (прочитано и выбрано в секунду), «Попадания в кеш».

Если выбранный в верхней панели отчёт не содержит индекс (например, он был создан позже), вместо карточек показывается «Отсутствует в выбранном отчёте», а графики остаются доступны.

## Управление индексами {#index-management}

Страница «Управление индексами» помогает найти индексы, которые стоит удалить или перестроить, и генерирует для них SQL. У неё три вкладки: «Неиспользуемые», «Раздутые» и «Дубликаты». Число на вкладке — количество найденных индексов.

На каждой вкладке отметьте нужные индексы флажками (флажок в заголовке отмечает все). Под таблицей появится SQL, сгруппированный по базам, с кнопкой копирования.

### Неиспользуемые индексы {#unused-indexes}

На вкладке «Неиспользуемые» показываются неуникальные индексы, которые не сканировались за выбранный период. Период задаётся списком «Не сканировались»:

| Вариант | Как определяется «не использовался» |
|---|---|
| «с момента сброса статистики» | `idx_scan = 0` в выбранном отчёте |
| «за последний день», «за последние 7 дней», «за последние 30 дней», «за последние 90 дней» | `idx_scan` в выбранном отчёте равен значению из первого сохранённого отчёта, полученного не раньше начала периода |

В отличие от проверки «Неиспользуемые индексы» на странице «Диагностика», которая берёт только индексы больше 1 МиБ, вкладка не отсекает индексы по размеру. Начало периода отсчитывается от текущего момента, а не от отчёта, выбранного в верхней панели.

В режиме «за последние N дней» рядом выводится «по сравнению с отчётом от …» — дата отчёта, с которым идёт сравнение. Проверяйте её: если история сервера короче выбранного периода, сравнение идёт с самым ранним сохранённым отчётом, и «90 дней» на деле может означать несколько дней. История ограничена сроком хранения временных рядов `PGSCOPE_METRICS_RETENTION_DAYS` (по умолчанию 90 дней, см. [Хранение данных](data.md#retention)).

Столбцы: «Индекс», «Таблица», «Размер», «Всего сканирований» (накопительный `idx_scan`) и «Последнее использование». Для выбранных индексов генерируется:

```sql
\c "shop"
DROP INDEX CONCURRENTLY "public"."orders_tmp_idx";
DROP INDEX CONCURRENTLY "public"."orders_status_idx";
```

> [!WARNING]
> Отсутствие сканирований не всегда означает, что индекс не нужен. Перед удалением учтите ограничения:
> - Статистика использования своя у каждого сервера. Индекс, который не используется на ведущем, может обслуживать запросы на репликах. Реплики видны в pgscope как отдельные серверы — проверьте индекс в их отчётах.
> - `pg_stat_reset()` и аварийный перезапуск PostgreSQL обнуляют счётчики. Режим «с момента сброса статистики» тогда покажет индексы, которые просто не успели поработать после сброса; проверьте «Сброс статистики» на странице базы. В режиме «за последние N дней» индекс, у которого счётчик после сброса стал меньше исходного, наоборот, в список не попадёт.
> - Индекс, которого не было в отчёте начала периода (создан позже), в режиме «за последние N дней» не показывается.
> - Из списка исключаются только индексы, в определении которых есть `UNIQUE` (в том числе первичные ключи). Индексы, обеспечивающие ограничения исключения (`EXCLUDE`), не исключаются, хотя удалить их PostgreSQL не даст. Если pgmetrics запущен с `--omit=indexdefs`, определений нет, и уникальные индексы тоже попадут в список.
> - Редкие, но важные запросы (ежемесячные отчёты, аварийные процедуры) могут не попасть в выбранный период.

### Раздутые индексы {#bloated-indexes}

Вкладка «Раздутые» показывает все индексы, для которых есть оценка раздувания, по убыванию лишнего объёма, со столбцом «Раздувание» (объём и доля). Если оценок нет (например, pgmetrics запущен с `--omit=bloat`), выводится «Нет оценок раздувания индексов». Для выбранных индексов генерируется `REINDEX INDEX CONCURRENTLY`:

```sql
\c "shop"
REINDEX INDEX CONCURRENTLY "public"."orders_created_at_idx";
```

Оценка приблизительная. Имеет смысл перестраивать индексы с заметной долей раздувания и ощутимым размером; диагностика pgscope, например, сообщает о раздутых индексах больше 10 МиБ с раздуванием больше 30 % (см. [Справочник проверок](checks.md)). `REINDEX CONCURRENTLY` не блокирует запись, но требует свободного места под новую копию индекса и выполняется дольше обычного `REINDEX`.

### Дубликаты {#duplicate-indexes}

Вкладка «Дубликаты» находит индексы одной базы с одинаковым определением: из текста `CREATE [UNIQUE] INDEX имя ON …` убираются имя индекса и слово `UNIQUE`, остальное (таблица, метод, столбцы, `INCLUDE`, условие `WHERE`) должно совпасть полностью. В каждой группе pgscope выбирает индекс, который нужно оставить: индекс первичного ключа (уникальный индекс с именем `*_pkey`), иначе другой уникальный индекс, иначе индекс ограничения исключения (неуникальный индекс с именем `*_excl`), иначе обычный индекс; из равных — первый в порядке отчёта. Остальные индексы группы выводятся в списке со столбцами «Дубликат индекса» (имя оставляемого индекса) и «Определение». В список не попадают:

- индексы, на которых держится ограничение: уникальные с именем `*_pkey` или `*_key` и неуникальные с именем `*_excl` — PostgreSQL не даст удалить их командой `DROP INDEX`;
- уникальные индексы, если в группе есть неуникальный: удаляется обычный индекс, а гарантия уникальности остаётся.

Для выбранных генерируется:

```sql
\c "shop"
DROP INDEX CONCURRENTLY "public"."orders_customer_id_idx1";  -- дубликат orders_customer_id_idx
```

> [!NOTE]
> pgmetrics не передаёт сведений об ограничениях, поэтому индексы ограничений pgscope узнаёт только по именам, которые PostgreSQL даёт по умолчанию: `таблица_pkey`, `таблица_столбцы_key`, `таблица_столбцы_excl`. Индекс ограничения с другим именем считается обычным — если PostgreSQL откажется его удалять, оставьте его. Самостоятельный уникальный индекс и индекс ограничения `UNIQUE` (`*_key`) на тех же столбцах равноправны: остаётся тот, что идёт в отчёте первым, и если это самостоятельный индекс, вкладка ничего не предлагает, хотя его можно удалить вручную. Индексы, совпадающие лишь частично (например, `(a)` и `(a, b)`), дубликатами не считаются. По тем же правилам работает проверка «Дублирующиеся индексы» на странице «Диагностика».

### Как выполнить сгенерированный SQL {#running-sql}

- SQL рассчитан на `psql`: строки `\c "база"` — метакоманды psql для переключения базы. В другом клиенте подключайтесь к каждой базе вручную и выполняйте только команды.
- `DROP INDEX CONCURRENTLY` и `REINDEX … CONCURRENTLY` нельзя выполнять внутри транзакции (`BEGIN … COMMIT`); выполняйте их по одной в режиме автофиксации. `DROP INDEX CONCURRENTLY` не применяется к индексам секционированных таблиц — для них используйте обычный `DROP INDEX` в окно обслуживания.
- Если `CONCURRENTLY`-команда прервалась, может остаться недействительный (`INVALID`) индекс — удалите его и повторите.
- Выполняйте удаление индексов сначала на тестовом окружении и сохраните определения (`pg_get_indexdef`), чтобы при необходимости быстро создать индекс заново.

## Топ-k {#topk}

Страница «Топ-k» строит рейтинги самых больших, нагруженных и быстрорастущих объектов. Выберите тип объектов, критерий и длину списка («Топ-10», «Топ-25», «Топ-50»).

| Тип | Критерии |
|---|---|
| «Таблицы» | «Размер», «Живые строки», «Мёртвые строки», «Раздувание», «Последовательные сканирования», «Записи (вст. + обн. + уд.)», «Рост размера», «Рост числа строк» |
| «Индексы» | «Размер», «Раздувание», «Сканирования», «Рост размера» |
| «Схемы» | «Размер таблиц», «Размер индексов», «Строки», «Число таблиц», «Число индексов» |

Схема в рейтинге — пара `база.схема`; её размер и число строк складываются из таблиц и индексов этой схемы в отчёте. Объекты с нулевым значением критерия в рейтинг не попадают. Счётчики «Последовательные сканирования», «Записи (вст. + обн. + уд.)» и «Сканирования» накопительные — они показывают нагрузку с момента сброса статистики, а не за последние дни. Щелчок по таблице или индексу открывает его страницу.

### Рост объектов {#growth}

Критерии «Рост размера» и «Рост числа строк» сравнивают текущий отчёт с первым сохранённым отчётом, полученным не раньше начала периода: «за 1 день», «за 7 дней» или «за 30 дней». Над списком выводится «По сравнению с отчётом от …». Уменьшение показывается со знаком «−» и жёлтой полосой.

Особенности:

- Если история сервера короче периода, сравнение идёт с самым ранним сохранённым отчётом — сверяйтесь с датой в подписи.
- Объекты, которых не было в отчёте начала периода (созданные позже), в рейтинг роста не попадают.
- Начало периода отсчитывается от текущего момента, а не от отчёта, выбранного в верхней панели.
- Если подходящей истории нет, выводится «Нет данных для рейтинга» с пояснением «Пока недостаточно истории за этот период.».

Рост размера — основной инструмент, когда нужно понять, куда уходит место на диске: сочетайте его с разделами [Табличные пространства](#tablespaces) и [WAL и контрольные точки](server.md#wal).

## Табличные пространства {#tablespaces}

Страница «Табличные пространства» показывает карточку на каждое табличное пространство:

- имя, владелец («владелец …») и расположение каталога; если подключение pgmetrics к PostgreSQL не локальное (см. [Система](server.md#system)), у `pg_default` и `pg_global` вместо пути стоит «(каталог данных)»;
- размер табличного пространства (`pg_tablespace_size`);
- «Диск» — занято и всего на файловой системе, где лежит пространство, и «Иноды» — доля занятых inode. Полоса жёлтая выше 80 % и красная выше 90 %. Эти данные pgmetrics собирает только на Linux и только при локальном подключении на хосте базы данных; иначе выводится «Использование диска собирается, когда pgmetrics запущен на хосте базы данных».

Щелчок по карточке выбирает табличное пространство. Ниже появляются:

- «Использование диска: …» — графики «Размер табличного пространства» и «Диск» (занято и всего);
- «Объекты в …» — таблицы и индексы из отчёта, лежащие в этом пространстве, с типом и размером.

Для объектов можно сгенерировать SQL: в строке «Сгенерировать SQL, чтобы» выберите «перенести в» и целевое пространство или «удалить», затем отметьте объекты флажками.

```sql
\c "shop"
ALTER TABLE "public"."events_2025" SET TABLESPACE "archive";
ALTER INDEX "public"."events_2025_pkey" SET TABLESPACE "archive";
```

При выборе «удалить» генерируются `DROP TABLE` и `DROP INDEX` без `CASCADE`.

> [!WARNING]
> `ALTER TABLE … SET TABLESPACE` и `ALTER INDEX … SET TABLESPACE` физически копируют объект и держат на нём блокировку `ACCESS EXCLUSIVE` всё время копирования: чтение и запись в таблицу будут ждать. Индексы таблицы при переносе таблицы остаются на месте — переносите их отдельно. Выполняйте перенос в окно обслуживания или используйте `pg_repack`. Команды «удалить» удаляют данные безвозвратно.

> [!NOTE]
> Таблицы и индексы, лежащие в табличном пространстве по умолчанию своей базы, отчёт не привязывает к конкретному пространству, и pgscope показывает их в `pg_default`. Если для базы задано другое пространство по умолчанию (`CREATE DATABASE … TABLESPACE`), её объекты всё равно окажутся в списке `pg_default`.

## Расширения и прочее {#extensions}

Страница «Расширения и прочее» состоит из четырёх вкладок.

| Вкладка | Что показывает |
|---|---|
| «Расширения» | расширения во всех базах: «База данных», «Схема», «Установлена», «Доступна», «Статус» — «доступно обновление» или «актуальна» — и «Описание». Расширения с доступным обновлением идут первыми |
| «Функции» | статистика пользовательских функций: «Вызовы», «Общее время», «Собственное время» (без вложенных вызовов), «Среднее». Требует `track_functions = pl` или `all`; без этого выводится подсказка |
| «Последовательности» | обращения к последовательностям: «Блоки: попадания» и «Блоки: чтения» |
| «Отключённые триггеры» | отключённые триггеры с таблицей и функцией |

Обновление расширения выполняется в каждой базе отдельно, например:

```sql
ALTER EXTENSION pg_stat_statements UPDATE;
```

Перед обновлением прочитайте примечания к версии расширения. «Доступна» — версия, которую предлагает установленный на сервере пакет расширения (`default_version`); после обновления пакета ОС она меняется, а установленная в базе — нет.

Отключённый триггер (`ALTER TABLE … DISABLE TRIGGER`) не срабатывает, поэтому, например, аудит или денормализация молча перестают работать. Если отключение было временным, включите триггер обратно:

```sql
ALTER TABLE "public"."orders" ENABLE TRIGGER "orders_audit";
```

Об установке и удалении расширений, смене их версий и об отключении триггеров могут сообщать [оповещения об изменениях](change-alerts.md).

## Роли {#roles}

Страница «Роли» — все роли кластера с атрибутами:

| Столбец | Что показывает |
|---|---|
| «Роль» | имя роли |
| «Может входить» | атрибут `LOGIN` |
| «Суперпользователь» | атрибут `SUPERUSER`, отмечен «суперпользователь» |
| «Создание БД» | `CREATEDB` |
| «Создание ролей» | `CREATEROLE` |
| «Репликация» | `REPLICATION` |
| «Обход RLS» | `BYPASSRLS` |
| «Лимит подкл.» | `CONNECTION LIMIT`, «∞» — без лимита |
| «Действует до» | срок действия пароля (`VALID UNTIL`), «бессрочно» — без срока |
| «Входит в роли» | роли, членом которых является роль |

На что смотреть: каждый лишний суперпользователь с правом входа — риск безопасности (диагностика сообщает о них проверкой «Дополнительные роли суперпользователя», см. [Справочник проверок](checks.md)); роли с `REPLICATION` и `BYPASSRLS` должны быть только у тех, кому они действительно нужны. Для мониторинга достаточно роли с членством в `pg_monitor`, суперпользователь не требуется (см. [Подготовка PostgreSQL](postgres.md)).

Чтобы узнавать о появлении новых ролей и изменении их атрибутов, включите [оповещения об изменениях](change-alerts.md).
