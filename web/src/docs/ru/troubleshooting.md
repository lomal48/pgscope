# Решение проблем и FAQ

Здесь собраны типичные проблемы, сгруппированные по симптомам: что проверить и как исправить. В конце — ответы на частые вопросы. Проблемы pgscope-agent разобраны отдельно, на странице [Docker и Docker Swarm](docker.md#troubleshooting).

## С чего начать {#first-steps}

**Журнал pgscope.** pgscope пишет журнал в стандартный поток ошибок (stderr):

```bash
journalctl -u pgscope -f                      # служба systemd
cd deploy && docker compose logs -f pgscope   # Docker Compose
```

При запуске в журнал выводится строка `pgscope listening on АДРЕС (public URL АДРЕС)` — по ней удобно проверить `PGSCOPE_LISTEN` и `PGSCOPE_BASE_URL`. Другие сообщения:

| Сообщение в журнале | Что значит |
|---|---|
| `schema setup: …`, после чего процесс завершается | нет связи с базой для хранения или нет права создавать таблицы (см. [pgscope не запускается](#startup)) |
| `store report …` | отчёт не сохранён, клиент получил 500 |
| `API key lookup: …` | база для хранения не ответила при проверке ключа, клиент получил 503 |
| `notify <тип> <адрес>: …` | уведомление не доставлено |
| `smtp: …` | SMTP-сервер недоступен, не ответил за 30 секунд или отклонил письмо |
| `team emails are not sent: SMTP is not configured (PGSCOPE_SMTP_ADDR); pass invitation links on yourself` | SMTP не настроен, поэтому письма о доступе к серверу и приглашения не отправляются; пишется один раз за время работы процесса |
| `team email "…" to … not sent: …` | письмо о доступе к серверу или приглашение не доставлено |
| `webhook: …` | адрес вебхука или сервиса уведомлений недоступен |
| `ai chat: …`, `ai request: …` | ошибка AI-чата |
| `retention: …` | ошибка очистки старых данных |

**Сторона отправки.** Посмотрите вывод pgdash CLI в cron (письма cron или перенаправление вывода в файл). Чтобы увидеть точный код ответа и текст ошибки, отправьте отчёт вручную через curl (см. [Пример: отправка отчёта через curl](api.md#curl-example)).

## Отчёты не доходят, сервер не появляется {#no-data}

Проверьте по порядку:

1. **pgmetrics работает.** Выполните команду сбора отдельно и убедитесь, что вывод — JSON:

```bash
pgmetrics -w -f json -h DBHOST -U pgmon --all-dbs > /tmp/report.json; echo "exit $?"; head -c 200 /tmp/report.json
```

Без `-f json` pgmetrics выводит текстовый отчёт, и такой отчёт принят не будет (при отправке через curl pgscope ответит 400). Флаг `-w` нужен, чтобы pgmetrics не ждал ввода пароля в cron.

2. **Адрес.** У pgdash CLI должен быть `--base-url` с суффиксом `/api/v1`, например `--base-url=https://pgscope.example.com/api/v1`. Без суффикса запрос уходит на неверный путь и получает 404 (см. [404](#http-404)). Без `--base-url` pgdash CLI отправляет отчёт в облачный pgDash, а в закрытом контуре просто получает сетевую ошибку.
3. **Доступность.** С хоста сбора: `curl -sS -o /dev/null -w '%{http_code}\n' https://pgscope.example.com/` должен вернуть 200. Если сертификат выпущен внутренним центром сертификации, хост сбора должен ему доверять.
4. **Ключ.** Ключ взят со страницы «Профиль» этого же pgscope и не перегенерирован после этого. У участников команды ключа нет.
5. **Чей сервер.** Сервер появляется у владельца ключа. Если вы вошли под другой учётной записью, вы его не увидите, пока владелец не откроет доступ.
6. **Код ответа** — см. [Ошибки HTTP при отправке](#http-errors).

Если сервер есть в списке, но его страницы показывают «Отчёт ещё не получен», то чаще всего под этим именем приходили только отчёты PgBouncer. Как правило, это опечатка в имени сервера в команде `report-pgbouncer`: такой отчёт создаёт отдельный пустой сервер. Исправьте имя и удалите лишний сервер (см. [Удаление данных](data.md#deleting)). Другая возможная причина — база для хранения восстановлена из копии без данных таблицы `reports` (см. [Резервное копирование](data.md#backup)); тогда страницы заполнятся со следующим отчётом.

## Ошибки HTTP при отправке {#http-errors}

Полная таблица ответов — в разделе [Ответы](api.md#ingest-responses) и в разделе [Ответы сервера](collect.md#responses).

### 400 {#http-400}

| Сообщение | Что сделать |
|---|---|
| «Некорректное тело запроса» | тело не JSON, оборвано или до поля `data` в нём больше 64 КиБ. Проверьте, что pgmetrics завершился успешно и вывел JSON целиком. Слишком большой отчёт получает не 400, а 413 (см. [413](#http-413)) |
| «Не удалось распаковать тело запроса (gzip)» | клиент указал `Content-Encoding: gzip`, но тело не сжато. Уберите заголовок или сжимайте тело |
| «Некорректное имя сервера» | в имени сервера, PgBouncer или Pgpool допустимы только `A–Z a–z 0–9 _ . -`, от 1 до 64 символов. Пробелы, кириллица и `:` не допускаются |
| «Данные не являются JSON-отчётом pgmetrics» | в `data` не отчёт pgmetrics: запуск без `-f json`, другая утилита или отчёт без времени сбора |
| «В отчёте нет данных PgBouncer» | `report-pgbouncer` отправил отчёт, снятый не со служебной базы `pgbouncer`. Подключайте pgmetrics к порту PgBouncer и базе `pgbouncer` |
| «В отчёте нет данных Pgpool» | для `report-pgpool` pgmetrics нужно запускать с флагом `--pgpool` |

### 401 и 403 {#http-401-403}

- **401 «Некорректный API-ключ»** — ключ не из 22 латинских букв или цифр. Обычно это обрезанный при копировании ключ, лишний пробел или кавычка.
- **403 «Неизвестный API-ключ»** — ключа нет в этом pgscope: его перегенерировали («Сгенерировать заново»), аккаунт удалён или ключ взят из другой установки. Скопируйте актуальный ключ со страницы «Профиль» и обновите все cron-задачи и секреты агентов.

### 404 {#http-404}

Ответ 404 с текстом `404 page not found` (не JSON) означает, что запрос пришёл на неверный путь и попал в обработчик файлов веб-интерфейса. Обычно в `--base-url` нет суффикса `/api/v1` или в нём опечатка. Правильные пути: `/api/v1/report`, `/api/v1/reportpgbouncer`, `/api/v1/reportpgpool` (см. [API приёма отчётов](api.md#ingest)). 404 с другим текстом (например, HTML-страница) отдаёт reverse proxy: проверьте, что он передаёт пути `/api/` в pgscope без изменений.

### 409 {#http-409}

«Предыдущий отчёт этого сервера ещё сохраняется»: новый отчёт того же источника пришёл, пока сохранялся предыдущий. Так бывает при очень больших отчётах, медленной базе для хранения или когда два сборщика отправляют отчёты под одним именем. Повторять не нужно: следующий отчёт придёт в свой срок. Если ошибка постоянная, проверьте, нет ли дублирующих cron-задач или агентов, и нагрузку на базу для хранения.

### 413 {#http-413}

Ответ 413 приходит в двух случаях:

- **413 «Отчёт больше N МиБ — это предел PGSCOPE_MAX_REPORT_MB на сервере pgscope»** (JSON) — отчёт больше предела pgscope в переданном виде или после распаковки gzip (по умолчанию 256 МиБ). Сократите отчёт флагами pgmetrics (`--omit=bloat`, `-S`, фильтры схем и таблиц) или поднимите `PGSCOPE_MAX_REPORT_MB`, учитывая память хоста pgscope (см. [Ограничения частоты и размера](collect.md#limits)).
- **413 без JSON** (например, HTML-страница) — ответ reverse proxy: тело отчёта больше его лимита. У nginx по умолчанию лимит 1 МиБ. Увеличьте его для `/api/v1/` не ниже `PGSCOPE_MAX_REPORT_MB`:

```nginx
location /api/v1/ {
    client_max_body_size 256m;
    proxy_pass http://127.0.0.1:8080;
}
```

Пример полной конфигурации — в разделе [Reverse proxy и HTTPS](install.md#reverse-proxy).

### 429 {#http-429}

«Отчёты отправляются слишком часто»: с момента сохранения предыдущего отчёта того же источника прошло меньше `PGSCOPE_MIN_REPORT_INTERVAL` секунд (по умолчанию 60). Частые причины:

- cron запускается каждую минуту. Интервал отсчитывается от момента, когда предыдущий отчёт был сохранён, а сбор и сохранение занимают несколько секунд, поэтому следующий запуск приходит раньше лимита. Отправляйте раз в 5 минут;
- один сервер отправляют два сборщика: две cron-задачи, cron и агент или два агента с одинаковыми именами серверов. Каждому серверу нужно своё имя;
- интервал агента (`PGSCOPE_AGENT_INTERVAL`) меньше `PGSCOPE_MIN_REPORT_INTERVAL`.

Отклонённый отчёт не сохраняется. После перезапуска pgscope счётчик сбрасывается.

### 500 и 503 {#http-5xx}

- **500 «Не удалось сохранить отчёт»** — ошибка записи в базу для хранения. Причина — в журнале pgscope в строке `store report …`: закончилось место на диске, нет прав, база перегружена.
- **503 «Хранилище временно недоступно»** — база для хранения не ответила при проверке ключа. Проверьте, работает ли она и доступна ли с хоста pgscope.

pgdash CLI повторяет запрос при ответах 5xx и сетевых ошибках (число повторов задаёт `--retries`), агент повторяет отправку один раз через 5 секунд.

### 502 и 504 {#http-502-504}

Эти ответы формирует reverse proxy, а не pgscope:

- **502** — pgscope не запущен или слушает другой адрес и порт, чем указано в `proxy_pass`. Проверьте `PGSCOPE_LISTEN` и строку `pgscope listening on …` в журнале.
- **504** — pgscope не ответил за время ожидания прокси. Сохранение большого отчёта и ответ AI-чата могут занимать больше минуты; увеличьте `proxy_read_timeout` (например, до `300s`).

У самого pgscope тоже есть пределы: заголовки запроса должны прийти за 10 секунд, весь запрос с телом — за 10 минут, ответ готовится не дольше 35 минут, а простаивающее соединение закрывается через 2 минуты. Эти значения не настраиваются.

## Сервер помечен как устаревший {#stale-server}

Если последнему отчёту больше 15 минут, значение «Отчёт» в карточке на странице «Серверы» и точка с временем отчёта в верхней панели сервера становятся жёлтыми. Сам pgscope об этом не оповещает (см. [Дежурные оповещения в закрытом контуре](scenarios.md#on-call)).

Что проверить:

- работает ли cron-задача или агент: письма cron, журнал агента, страница «Агенты»;
- не отвечает ли pgscope ошибкой (см. [Ошибки HTTP при отправке](#http-errors)). Ошибки 403 и 429 в cron легко пропустить;
- не стал ли сбор слишком долгим: pgmetrics на больших базах может работать дольше интервала. Сократите сбор флагами (`--omit=bloat`, `-S`) или увеличьте интервал;
- синхронизированы ли часы. Время отчёта задаёт хост сбора, а «возраст» отчёта браузер считает по своим часам. Если часы хоста сбора отстают, отчёт кажется устаревшим;
- отчёты PgBouncer время последнего отчёта сервера не обновляют: сервер, для которого приходят только отчёты PgBouncer, всегда выглядит устаревшим.

## Пустая страница «Запросы» {#empty-queries}

Страница показывает «Нет статистики запросов», а диагностика — проблему «Нет статистики запросов». Причины:

- `pg_stat_statements` нет в `shared_preload_libraries`. После добавления нужен перезапуск PostgreSQL, перечитывания конфигурации недостаточно;
- не выполнен `CREATE EXTENSION pg_stat_statements` в базах, которые собирает pgmetrics;
- pgmetrics запущен с `--omit=statements`.

Если запросы на странице есть, но вместо текста у части из них `<insufficient privilege>`, у роли мониторинга нет `pg_monitor` (или `pg_read_all_stats`): без этого права PostgreSQL скрывает тексты запросов других пользователей.

Проверка под ролью мониторинга:

```sql
SELECT count(*) FROM pg_stat_statements;
SELECT query FROM pg_stat_statements LIMIT 1;
```

По умолчанию pgmetrics собирает 100 самых затратных по общему времени запросов; больше даёт флаг `--statements-limit=N`. Подробнее — на странице [Подготовка PostgreSQL](postgres.md).

## Нет планов выполнения {#no-plans}

На странице запроса в разделе «Планы выполнения» показано «Планы выполнения не собраны». Планы берутся из журнала PostgreSQL, куда их пишет `auto_explain`, поэтому нужно всё сразу:

- `auto_explain` загружен (`shared_preload_libraries` или `session_preload_libraries`);
- `auto_explain.log_format = json` — другие форматы не разбираются деревом;
- запрос выполнялся дольше `auto_explain.log_min_duration`;
- pgmetrics читает журнал: подключается к базе локально на её хосте и запущен от имени пользователя ОС с правом чтения файлов журнала (подробнее — в [следующем разделе](#no-logs)); для RDS и Aurora журнал читается через API AWS при `--aws-rds-dbid`;
- план попал в журнал за последние `--log-span` минут (по умолчанию 5). Делайте `--log-span` равным интервалу сбора.

Планы показываются для выбранного отчёта и сопоставляются с запросом по его идентификатору или по тексту без литералов. Если план есть в журнале, но не отображается, откройте отчёт, снятый сразу после выполнения запроса: кнопкой «›» или окном «Перейти к моменту» в верхней панели (см. [Выбор прошлого отчёта](ui.md#report-picker)).

## Нет журнала, системных метрик и истории autovacuum {#no-logs}

Страница «Журнал» показывает «Нет записей журнала», пусты «Система», заполнение дисков у табличных пространств и «История autovacuum (из журнала)». Всё это pgmetrics собирает только при локальном подключении: на хосте базы через Unix-сокет, по одинаковому адресу клиента и сервера или по loopback-адресам `127.0.0.0/8`. Локальный сбор видно по пометке «(локально)» в строке «Собрано» карточки «Кластер» на странице «Обзор». Кроме того:

- системные метрики и заполнение дисков pgmetrics собирает только под Linux;
- файлы журнала должны быть доступны для чтения пользователю ОС, от имени которого запущен pgmetrics. Если pgmetrics не находит журнал сам, укажите `--log-file` или `--log-dir`; при удалённом подключении эти флаги не помогают. Для RDS и Aurora журнал читается через API AWS при `--aws-rds-dbid`;
- журнал в формате `csvlog` на PostgreSQL 13+, а pgmetrics — официальный выпуск (в строке «Собрано» нет `+pgscope`): такие файлы он молча пропускает. Поставьте [pgmetrics из сборки pgscope](collect.md#pgmetrics-build) или переключите журнал на `stderr`;
- записи в журнале есть, но в отчёт не попадают или их время сдвинуто на смещение часового пояса: pgmetrics — официальный выпуск, а `log_timezone` не совпадает с часовым поясом его хоста. Поставьте [pgmetrics из сборки pgscope](collect.md#pgmetrics-build), который читает время в поясе из `log_timezone`, или задайте `log_timezone` равным поясу хоста pgmetrics либо `'UTC'`, см. [Журнал PostgreSQL](postgres.md#logs).

Для истории autovacuum нужен ещё `log_autovacuum_min_duration` (например, `1000`). Взаимоблокировки PostgreSQL по умолчанию пишет в журнал сам (ошибка `deadlock detected`), а `log_lock_waits = on` добавляет в журнал долгие ожидания блокировок.

Агент для Docker запускает pgmetrics в своём контейнере и подключается к базе по IP контейнера. Такое подключение не локальное, поэтому для баз в контейнерах эти данные, как правило, не собираются.

## Пустые графики и разрывы {#empty-charts}

- **«В этом диапазоне пока недостаточно данных».** Большинство графиков показывает скорость или долю за интервал между соседними отчётами, поэтому в выбранном периоде нужно хотя бы два отчёта. Сразу после подключения сервера подождите второй отчёт или выберите период длиннее.
- **Разрывы.** Отчёт не пришёл; счётчики сбросились (перезапуск PostgreSQL, `pg_stat_reset()`) — такой интервал пропускается, а не рисуется отрицательным; pgmetrics не смог прочитать размер из-за блокировки (`--lock-timeout`) — точка пропускается, а не рисуется нулём; pgmetrics не получил позицию WAL (LSN), например у `pg_basebackup` или реплики без приёмника WAL, — точка отставания реплики, удержания WAL слотом или генерации WAL пропускается.
- **График показывает прошлое время.** В верхней панели выбран прошлый момент (вдоль верхнего края панели видна цветная полоса): графики строятся вокруг выбранного отчёта, он отмечен пунктирной линией. Нажмите «К последнему».
- **Нет свежих точек, хотя отчёты приходят.** Часы хоста сбора спешат: время отчёта задаёт хост сбора, а графики строятся до текущего времени браузера. Синхронизируйте часы (NTP).
- **Нет старых данных.** Временные ряды старше `PGSCOPE_METRICS_RETENTION_DAYS` дней удаляются, если это значение не `0` (см. [Сроки хранения](data.md#retention)).
- **Пусты графики нагрузки и памяти.** pgmetrics подключается к базе не локально или работает не под Linux (см. [Нет журнала, системных метрик и истории autovacuum](#no-logs)).

## Оповещения не приходят {#alerts-not-delivered}

1. **Сработало ли оповещение.** Откройте «Оповещения» → «Сработавшие». Правила проверяются при получении каждого отчёта и сразу после добавления или удаления правила. Нет отчётов — нет и проверки.
2. **Изменился ли набор.** Уведомление отправляется только при изменении набора сработавших оповещений: появилось новое оповещение или снято прежнее. Пока набор тот же, повторов нет; изменение значения у сработавшего оповещения уведомления не вызывает. Когда набор менялся, видно на вкладке «История».
3. **Есть ли канал в нужном месте.** Каналы обычных оповещений добавляются на вкладке «Уведомления» страницы «Оповещения», каналы оповещений об изменениях — на странице «Оповещения об изменениях». Это разные списки.
4. **Работает ли канал.** Нажмите «Проверить» рядом с каналом. Ошибка покажется в интерфейсе, например «Не удалось отправить уведомление: SMTP не настроен (задайте PGSCOPE_SMTP_ADDR)» или «Не удалось отправить уведомление: … вернул код HTTP 404».
5. **Ошибки настоящих уведомлений** видны только в журнале pgscope (строки `notify …`, `smtp: …`, `webhook: …`). Позже такое уведомление не повторяется.
6. **Вебхук и другие HTTP-каналы** (Slack, PagerDuty, VictorOps, xMatters) должны ответить кодом 2xx за 3 секунды. Если ответа нет, pgscope повторяет запрос до трёх раз с паузой 5 секунд; ответ с другим кодом не повторяется (см. [Формат вебхука](notifications.md#webhook)).
7. **Нужен ли интернет.** Slack, PagerDuty, VictorOps и xMatters — облачные сервисы. Адрес PagerDuty зафиксирован (`https://events.pagerduty.com/v2/enqueue`). В закрытом контуре используйте email или вебхук на внутренний адрес. Если исходящий доступ идёт через HTTP-прокси, задайте pgscope переменные `HTTPS_PROXY` и `NO_PROXY`: запросы уведомлений их учитывают.
8. **Тип отчёта.** Правила проверяются только для отчётов PostgreSQL. Для PgBouncer и Pgpool оповещений нет.
9. **Оповещения об изменениях.** На странице «Оповещения об изменениях» в карточке «Отслеживаемые изменения» должны быть отмечены нужные виды изменений и нажата кнопка «Сохранить». Каждый отчёт сравнивается с предыдущим отчётом сервера, поэтому после подключения первое сравнение возможно только со второго отчёта. Уведомление уходит, только если изменения найдены.

## Письма не отправляются {#email}

- Если `PGSCOPE_SMTP_ADDR` не задан, при выборе канала «Email» показывается предупреждение «SMTP не настроен на этом сервере pgscope (PGSCOPE_SMTP_ADDR), поэтому письма не будут доставлены.».
- Проверьте канал кнопкой «Проверить». Ответ «Не удалось отправить уведомление: SMTP-сервер не принял письмо» значит, что SMTP-сервер недоступен, не ответил за 30 секунд или отклонил письмо; подробная причина — в журнале pgscope в строке `smtp: …`.
- Ответ «Не удалось отправить уведомление: Не указан ни один адрес получателя» значит, что в адресах канала нет ни одного адреса, например там только запятые. Удалите канал и добавьте его заново с адресами. Пробелы, пустые элементы списка и повторы адресов pgscope отбрасывает сам.

Частые причины:

| Причина | Что сделать |
|---|---|
| порт 465 (TLS с первого байта) | не поддерживается: используйте 587 со STARTTLS или 25 |
| задан `PGSCOPE_SMTP_USER`, а сервер не поддерживает STARTTLS | pgscope не передаёт пароль по незашифрованному соединению (кроме сервера на `localhost`). Включите STARTTLS или используйте релей без аутентификации, разрешённый по IP |
| задан `PGSCOPE_SMTP_USER`, а сервер не предлагает AUTH, в том числе старый сервер, который отвечает только на HELO (в журнале `smtp: server doesn't support AUTH`) | если сервер принимает письма без аутентификации, уберите `PGSCOPE_SMTP_USER`; иначе включите на нём AUTH |
| сертификат SMTP-сервера выпущен внутренним центром сертификации | добавьте корневой сертификат в системное хранилище хоста pgscope или укажите его в `SSL_CERT_FILE` |
| отправитель `pgscope@localhost` (значение по умолчанию) отклоняется | задайте `PGSCOPE_SMTP_FROM` с настоящим адресом вашего домена |
| неверный `хост:порт` | порт обязателен, например `mail.example.local:25` |

Письма с приглашениями отправляются в фоне, и интерфейс не сообщает об ошибке отправки: отказ SMTP-сервера виден только в журнале (строки `team email "…" to … not sent: …` и `smtp: …`). Если SMTP не настроен, под формой приглашения показывается «SMTP не настроен: скопируйте ссылку-приглашение из списка и отправьте её самостоятельно.», а в журнал один раз пишется `team emails are not sent: SMTP is not configured …`. В обоих случаях ссылку-приглашение можно скопировать на странице «Команда и настройки». Подробнее — [Почта (SMTP)](config.md#smtp).

## Проблемы с приглашениями {#invites}

- **«Приглашение не найдено или уже использовано».** Приглашение уже принято, отменено владельцем, сервер удалён или ссылка скопирована не полностью. Попросите владельца пригласить снова.
- **Ссылка ведёт на `localhost` или на неверный адрес.** Ссылки строятся из `PGSCOPE_BASE_URL`. Задайте правильный адрес и перезапустите pgscope; ссылка в списке на странице «Команда и настройки» обновится, а в уже отправленных письмах останется старый адрес — замените его вручную, токен действует.
- **При принятии — «Учётная запись с этим адресом электронной почты уже существует. Войдите в неё и попросите владельца сервера открыть доступ этой учётной записи.»** (HTTP 409). У коллеги уже есть учётная запись с этим email (например, он зарегистрировался сам). Приглашение при этом не расходуется. Коллега входит в свою учётную запись, а владелец приглашает тот же адрес ещё раз: для существующей учётной записи доступ открывается сразу, а ненужное приглашение удаляется.
- **«Пароль должен содержать от 8 символов и не более 72 байт (символ кириллицы занимает 2 байта)».** Приглашение остаётся действительным: задайте другой пароль. Пароль только из кириллицы может быть не длиннее 36 букв.
- **Два приглашения одному адресу.** Их не бывает: повторное приглашение обновляет прежнее и отправляет ту же ссылку.
- **Письмо не пришло.** См. [Письма не отправляются](#email); ссылку можно передать вручную.

## Не удаётся войти {#login}

- **«Неверный адрес электронной почты или пароль».** Сброса пароля по email нет; администратор может задать временный пароль в базе для хранения (см. [Сброс забытого пароля](security.md#password-reset)).
- **«Регистрация новых аккаунтов отключена. Попросите администратора пригласить вас.»** Регистрацию закрывает настройка `PGSCOPE_SIGNUP`: по умолчанию (`first`) зарегистрироваться можно, только пока в базе нет ни одной учётной записи, а при `closed` — никогда. Ссылки «Регистрация» на странице входа в этом случае нет. Новых пользователей добавляют приглашениями (см. [Дать доступ коллеге](scenarios.md#share-access)); если нужна самостоятельная регистрация, задайте `PGSCOPE_SIGNUP=open` и перезапустите pgscope.
- **Вход проходит, но сразу снова показывается страница входа.** Браузер не сохранил cookie. Обычно cookie выдан с флагом `Secure` (`PGSCOPE_BASE_URL` начинается с `https://` или прокси передаёт `X-Forwarded-Proto: https`), а pgscope открыт по `http://`. Открывайте его по HTTPS-адресу (см. [Reverse proxy и HTTPS](install.md#reverse-proxy)). Также проверьте, не блокирует ли браузер cookie для этого сайта.
- **Пришлось войти заново.** Сеанс действует 30 дней с момента входа и не продлевается. После смены адреса pgscope нужно войти заново. После смены пароля завершаются все остальные сеансы учётной записи: в других браузерах и на других устройствах нужно войти с новым паролем.
- **Скрипт получает 415.** Для запросов к API интерфейса с любым методом, кроме GET, нужен заголовок `Content-Type: application/json`, в том числе для `/api/login`, `/api/logout`, `/api/signup` и `/api/invite/…` (см. [Внутренний API интерфейса](api.md#internal-api)).

## Ошибки AI-чата {#ai-chat}

| Сообщение | Причина и решение |
|---|---|
| «AI-чат не настроен. Задайте PGSCOPE_AI_KEY (API-ключ Anthropic) и перезапустите pgscope.» | ключ не задан. В закрытом контуре это нормальное состояние: чат отправляет данные в облако Anthropic |
| «AI-провайдер вернул HTTP 401» (или 403) | неверный или отозванный ключ |
| «AI-провайдер вернул HTTP 404» | обычно неизвестная модель: проверьте `PGSCOPE_AI_MODEL`, а если задан `PGSCOPE_AI_BASE_URL`, то и этот адрес |
| «AI-провайдер вернул HTTP 429» (или 5xx) | превышены лимиты или сбой на стороне провайдера; повторите позже |
| «Не удалось связаться с AI-провайдером» | нет сетевого доступа к API Anthropic или к адресу из `PGSCOPE_AI_BASE_URL` |
| «AI-модель отказалась отвечать на этот вопрос» | переформулируйте вопрос |
| «Отчётов пока нет» | у сервера ещё нет отчётов |
| «Некорректный запрос» в длинном диалоге | в диалоге не больше 50 сообщений, а тело запроса — не больше 1 МиБ. Начните «Новый диалог» |
| 504 от reverse proxy | ответ готовится дольше таймаута прокси: увеличьте `proxy_read_timeout` |

Если ответ заканчивается пометкой «(ответ обрезан)», он упёрся в предел длины (16 000 токенов): задайте вопрос уже. Подробнее — [AI-чат](config.md#ai).

## Docker-агент {#docker-agent}

Статусы целей, сети, ошибки аутентификации и проблемы с сетями Docker разобраны на странице [Docker и Docker Swarm](docker.md#troubleshooting). Коротко:

- агента нет на странице «Агенты» — смотрите его журнал (`docker compose logs agent` или `docker service logs pgscope-agent_agent`). Строка `ERROR: pgscope rejected the API key (HTTP 403 …)` означает неверный ключ в секрете;
- `pgscope answered HTTP 429` — интервал агента меньше `PGSCOPE_MIN_REPORT_INTERVAL` или тот же сервер отправляет кто-то ещё;
- агент сразу завершается с `configuration: …` — не задан `PGSCOPE_URL`, нет секретов или неверный формат ключа;
- на узле Swarm агент требует `PGSCOPE_AGENT_CLUSTER`.

## pgscope не запускается {#startup}

- **`schema setup: …`** — pgscope не смог подключиться к базе для хранения или создать таблицы. Проверьте `PGSCOPE_DB` (хост, порт, имя базы, роль, пароль, `pg_hba.conf`). Если причина — `permission denied for schema public`, роли не хватает права создавать таблицы: в PostgreSQL 15 и новее схема `public` по умолчанию это запрещает всем, кроме владельца базы. Сделайте роль pgscope владельцем базы:

```sql
ALTER DATABASE pgscope OWNER TO pgscope;
```

- **`listen tcp …: bind: address already in use`** — порт занят: освободите его или измените `PGSCOPE_LISTEN`.
- **`PGSCOPE_SIGNUP=…: use first, open or closed`** — недопустимое значение `PGSCOPE_SIGNUP`.
- **`PGSCOPE_METRICS_RETENTION_DAYS=-1: set a number of days to keep the data, or 0 to keep it forever`** (или то же для `PGSCOPE_REPORT_RETENTION_DAYS`) — срок хранения отрицательный. Задайте число дней или `0`, чтобы хранить данные бессрочно.
- **`PGSCOPE_MAX_REPORT_MB must be at least 1`** — предел размера отчёта меньше 1 МиБ.
- **Docker Compose:** pgscope ждёт, пока база в сервисе `db` пройдёт проверку готовности. Если `.env` не содержит `PGSCOPE_DB_PASSWORD`, Compose не запустится и сообщит об этом.

## Частые вопросы {#faq}

**Нужен ли pgscope доступ в интернет?** Для работы — нет. Сбор и приём отчётов, хранение, интерфейс, диагностика и уведомления по email и вебхукам работают в закрытом контуре. Интернет нужен только AI-чату и каналам Slack, PagerDuty, VictorOps и xMatters (см. [Данные за пределами периметра](security.md#egress)), а также для сборки образов, которую выполняют на отдельной машине.

**Подключается ли pgscope к базам сам?** Нет. Отчёты присылают pgdash CLI и pgscope-agent, pgscope только принимает их. Ему нужен лишь входящий HTTP(S) от сборщиков.

**Можно ли запретить регистрацию?** Да, переменной `PGSCOPE_SIGNUP`. По умолчанию (`first`) зарегистрироваться можно, только пока в базе нет ни одной учётной записи: первый пользователь становится владельцем, остальных добавляют приглашениями. `closed` закрывает регистрацию полностью, `open` открывает её всем, кто может открыть интерфейс. Принять приглашение можно при любом значении. Если в установке уже есть учётные записи и вы полагались на открытую регистрацию, после обновления задайте `PGSCOPE_SIGNUP=open` (см. [Открытая регистрация](security.md#signup)).

**Как сбросить забытый пароль?** Через базу для хранения (см. [Сброс забытого пароля](security.md#password-reset)).

**Почему у участника команды нет API-ключа?** Отчёты отправляются от имени владельца сервера. Участник смотрит серверы, открытые ему, и сам серверов не создаёт.

**Почему уведомление пришло один раз, хотя проблема не ушла?** Уведомления отправляются только при изменении набора сработавших оповещений (см. [Оповещения не приходят](#alerts-not-delivered)).

**Есть ли оповещения для PgBouncer и Pgpool?** Нет, правила проверяются только для отчётов PostgreSQL.

**Где хранится переписка AI-чата?** Только во вкладке браузера, до её закрытия. В базе для хранения переписка не сохраняется.

**Почему не открывается старый отчёт?** Полные отчёты хранятся `PGSCOPE_REPORT_RETENTION_DAYS` дней (по умолчанию 14). Любой отчёт за этот срок можно открыть кнопками «‹» и «›», окном «Перейти к моменту» или щелчком по графику; для более раннего момента показывается «Нет отчёта на этот момент» (см. [Выбор прошлого отчёта](ui.md#report-picker) и [Что от чего зависит](data.md#dependencies)).

**Как переименовать сервер?** Имя — это идентификатор сервера. Отчёты под новым именем создадут новый сервер, а старый останется со своей историей и последним отчётом, пока его не удалят. Перенести историю на новое имя в интерфейсе нельзя.

**Можно ли запустить несколько экземпляров pgscope с одной базой?** pgscope на это не рассчитан, и такая схема не проверялась: ограничение частоты отчётов и защита от одновременного сохранения работают в памяти процесса, а очистку старых данных выполнял бы каждый экземпляр. Используйте один экземпляр.

**Как часто отправлять отчёты?** Обычно раз в 5 минут (у агента это значение по умолчанию). Чаще, чем раз в `PGSCOPE_MIN_REPORT_INTERVAL`, нельзя, а более частые отчёты быстрее заполняют базу для хранения (см. [Объём данных](data.md#sizing)).

**Сколько хранится история?** По умолчанию 90 дней временных рядов и 14 дней полных отчётов (см. [Сроки хранения](data.md#retention)). Значение `0` в `PGSCOPE_METRICS_RETENTION_DAYS` или `PGSCOPE_REPORT_RETENTION_DAYS` отключает очистку: данные хранятся бессрочно.
