# Безопасность

На этой странице описано, как pgscope защищает данные и доступ к ним: модель угроз, учётные записи и пароли, сеансы и cookie, открытая регистрация, API-ключи, защита приёма отчётов, роль мониторинга, агент и Docker-сокет, хранение секретов и данные, которые могут покинуть периметр. В конце — список рекомендаций для промышленной установки.

## Модель угроз {#threat-model}

**Что нужно защищать.**

- **Данные мониторинга.** Отчёты pgmetrics содержат тексты запросов из `pg_stat_statements` и `pg_stat_activity` (с литералами, а значит, возможно, с персональными или коммерческими данными), имена баз, схем, таблиц и ролей, параметры конфигурации, имена хостов, адреса клиентов и строки журнала PostgreSQL, если pgmetrics читает журнал.
- **Учётные записи pgscope и их сеансы.**
- **API-ключи.** С ключом можно записывать отчёты от имени аккаунта.
- **Секреты интеграций**: пароль SMTP, ключ AI, адреса вебхуков Slack, ключи PagerDuty и другие адреса каналов уведомлений.

**Точки входа.**

| Точка входа | Кто обращается | Чем защищена |
|---|---|---|
| Веб-интерфейс и его API (`/api/…`) | браузеры пользователей | сеанс в cookie |
| API приёма отчётов (`/api/v1/…`) | pgdash CLI, pgscope-agent | API-ключ в теле запроса |
| Исходящие соединения | pgscope → SMTP, вебхуки, сервисы уведомлений, API AI | адреса задают пользователи (каналы) и администратор (переменные окружения) |
| База для хранения | pgscope, администратор | роли и `pg_hba.conf` PostgreSQL |

pgscope сам не подключается к наблюдаемым базам: отчёты присылают сборщики. Взлом pgscope не даёт прямого доступа к базам, но раскрывает всё, что есть в отчётах.

**Чего в pgscope нет** (учитывайте это при оценке рисков):

- встроенного TLS: HTTPS обеспечивает reverse proxy (см. [Reverse proxy и HTTPS](install.md#reverse-proxy));
- единого входа (SSO, LDAP) и двухфакторной аутентификации;
- ограничения числа попыток входа;
- настройки, запрещающей регистрацию;
- роли администратора: каждая учётная запись видит только свои серверы и те, к которым ей открыли доступ, а действия уровня всего экземпляра выполняются в базе для хранения;
- журнала аудита действий пользователей;
- сброса пароля по email.

## Учётные записи и пароли {#accounts}

- Пароли хешируются алгоритмом bcrypt со стоимостью по умолчанию библиотеки `golang.org/x/crypto/bcrypt` (10). Пароль в открытом виде не хранится.
- Длина пароля — от 8 до 72 байт (72 байта — ограничение bcrypt). Для латиницы это столько же символов; символ кириллицы занимает 2 байта.
- Email приводится к нижнему регистру. Подтверждение email не требуется, а формат проверяется минимально: есть `@`, не длиннее 254 символов, без пробелов.
- При неудачном входе ответ одинаков для неизвестного email и неверного пароля: «Неверный адрес электронной почты или пароль». Но регистрация сообщает «Учётная запись с таким адресом электронной почты уже существует», поэтому через неё можно узнать, зарегистрирован ли адрес. Кроме того, на вход с неизвестным адресом pgscope отвечает заметно быстрее: пароль с хешем в этом случае не сравнивается.
- Ограничения попыток входа нет. Настройте его на reverse proxy, например `limit_req` в nginx для `/api/login`.
- Учётные записи бывают двух видов: владелец (регистрируется сам и получает API-ключ) и участник команды (создаётся по приглашению, API-ключа нет). Подробнее — на странице [Команда, профиль и аккаунт](teams.md).

### Сброс забытого пароля {#password-reset}

Самостоятельного сброса пароля нет. Администратор базы для хранения может задать пользователю временный пароль. Для этого нужно расширение pgcrypto; в PostgreSQL 13 и новее его может установить владелец базы.

```sql
CREATE EXTENSION IF NOT EXISTS pgcrypto;
UPDATE users SET pwhash = crypt('Temporary-Passw0rd', gen_salt('bf', 10))
WHERE email = 'user@example.com';
```

Временный пароль может остаться в истории psql и в журнале базы для хранения, поэтому пользователь должен сразу сменить его в «Профиль» → «Смена пароля».

## Сеансы и cookie {#sessions}

- После входа создаётся сеанс со случайным токеном из 52 символов, полученным от криптографического генератора. Токен хранится в таблице `sessions` в открытом виде.
- Сеанс действует 30 дней с момента входа. При работе срок не продлевается.
- «Выйти» удаляет сеанс на сервере.
- Смена пароля и перегенерация API-ключа другие сеансы **не** завершают. Завершить все сеансы пользователя можно только в базе для хранения:

```sql
DELETE FROM sessions WHERE user_id = (SELECT id FROM users WHERE email = 'user@example.com');
```

Атрибуты cookie:

| Атрибут | Значение |
|---|---|
| Имя | `pgscope_session` |
| `Path` | `/` |
| `Expires` | через 30 дней после входа |
| `HttpOnly` | всегда: скрипты страницы не могут прочитать токен |
| `SameSite` | `Lax` |
| `Secure` | если прокси передал заголовок `X-Forwarded-Proto: https` или если `PGSCOPE_BASE_URL` начинается с `https://` |

За прокси с HTTPS задайте `PGSCOPE_BASE_URL` с `https://` или передавайте `X-Forwarded-Proto`, иначе cookie будет без флага `Secure`. Если же флаг стоит, а pgscope открыт по `http://`, браузер не сохранит cookie, и войти не получится. Все варианты разобраны в разделе [Reverse proxy и HTTPS](install.md#reverse-proxy).

**Защита от CSRF.** Запросы к той части API интерфейса, которая требует входа, с любым методом HTTP, кроме GET, должны иметь заголовок `Content-Type: application/json`, иначе pgscope отвечает 415. Такой запрос нельзя отправить с чужого сайта обычной HTML-формой, а для `fetch` браузер требует разрешения CORS, которого pgscope не даёт. Дополнительную защиту даёт `SameSite=Lax`: в POST-запросах с чужих сайтов браузер cookie не передаёт. Методы, доступные без входа (`/api/signup`, `/api/login`, `/api/logout`, `/api/invite/…`), заголовок `Content-Type` не проверяют.

## Открытая регистрация {#signup}

Регистрация (`POST /api/signup`) доступна без входа и без ограничений, и отключить её настройкой нельзя. Любой, кто может открыть веб-интерфейс, может создать учётную запись и получить API-ключ.

Что может такой пользователь:

- видеть только свои серверы: чужие данные ему недоступны;
- отправлять отчёты и тем самым занимать место в базе для хранения;
- добавлять к своим серверам каналы уведомлений. Тогда pgscope будет отправлять POST-запросы на указанные им адреса, в том числе на адреса внутренней сети, доступные с хоста pgscope. Кнопка «Проверить» отправляет запрос сразу и показывает код ответа HTTP или ошибку соединения, поэтому ею можно проверять доступность внутренних адресов;
- отправлять через ваш SMTP-сервер письма на любые адреса: уведомления и приглашения (текст писем формирует pgscope).

Что сделать:

1. Откройте веб-интерфейс только из сетей, где работают пользователи pgscope: межсетевой экран, VPN, правила reverse proxy.
2. Когда учётные записи владельцев созданы, закройте регистрацию на reverse proxy. Приглашения в команду продолжат работать: они используют другой адрес (`/api/invite/…`).

```nginx
# внутри блока server { … } рядом с location /
location = /api/signup {
    return 403;
}
```

Форма «Регистрация» останется на месте, но её отправка закончится ошибкой «Ошибка HTTP 403».

3. Ограничьте исходящие соединения хоста pgscope: разрешите только SMTP-сервер и адреса, на которые действительно нужны вебхуки.

## API-ключи {#api-keys}

- Ключ создаётся при регистрации владельца. Он состоит из 22 символов; pgscope генерирует их из заглавных латинских букв и цифр от 2 до 7 (около 110 бит случайности). Принимается любой ключ формата `[A-Za-z0-9]{22}` — так же его проверяет pgdash CLI.
- У аккаунта один ключ. У участников команды ключа нет.
- **Что даёт ключ.** Только запись: отправку отчётов PostgreSQL, PgBouncer и Pgpool и сигналов агентов от имени аккаунта. Сервер с новым именем создаётся автоматически при первом отчёте. Читать данные по ключу нельзя.
- **Чем опасна утечка.** Можно засорить аккаунт серверами и данными или подменить отчёты существующего сервера, например скрыть проблему и тем самым снять оповещения.
- Ключ хранится в базе для хранения в открытом виде (`users.apikey`).
- **Перегенерация**: «Профиль» → «API-ключ» → «Сгенерировать заново». Старый ключ перестаёт работать сразу (ответ 403), поэтому заранее подготовьте обновление cron-задач и секретов агентов (см. [Профиль](teams.md#profile)).
- В командах вида `pgdash -a КЛЮЧ` ключ виден в списке процессов и в crontab хоста сбора. Ограничьте доступ к этим хостам. Агент получает ключ из Docker-секрета и в командную строку его не передаёт.

## Защита приёма отчётов {#ingest-protection}

| Мера | Как работает |
|---|---|
| Размер тела | отчёт — не больше 256 МиБ в сети и не больше 2 ГиБ после распаковки gzip; сигнал агента — не больше 4 МиБ; запросы веб-интерфейса — не больше 1 МиБ |
| Проверка формата | ключ — ровно 22 латинские буквы или цифры; имена сервера, PgBouncer и Pgpool — символы `A–Z a–z 0–9 _ . -`, от 1 до 64; поле `data` должно быть отчётом pgmetrics с заполненным временем сбора, а для PgBouncer и Pgpool — ещё и с их разделом |
| Частота | отчёт одного источника (сервер или его PgBouncer) принимается не чаще раза в `PGSCOPE_MIN_REPORT_INTERVAL` секунд (по умолчанию 60), иначе ответ 429 |
| Параллельность | пока сохраняется предыдущий отчёт того же источника, новый получает 409 |
| Ошибки | подробности ошибок базы пишутся в журнал pgscope, клиент получает только общий текст |

Ограничения, о которых стоит знать:

- Учёт частоты ведётся в памяти процесса: он сбрасывается при перезапуске и не учитывает неуспешные запросы. Общего ограничения числа запросов нет.
- Тело запроса читается и разбирается **до** проверки API-ключа. Лимиты рассчитаны на крупные отчёты, поэтому даже клиент без ключа может заставить pgscope разбирать до 2 ГиБ данных и занять много памяти.

Поэтому откройте `/api/v1/` на reverse proxy только для сетей, где работают сборщики, и ограничьте размер тела тем, что нужно вашим отчётам (средний размер отчёта показывает запрос из раздела [Как проверить фактический объём](data.md#size-check)):

```nginx
location /api/v1/ {
    allow 10.20.0.0/16;          # сети хостов сбора и Docker-хостов с агентами
    deny  all;
    client_max_body_size 64m;
    proxy_pass http://127.0.0.1:8080;
}
```

Коды ответов API приёма описаны на странице [API](api.md).

## Роль мониторинга {#monitoring-role}

- Сборщикам нужна роль с `pg_monitor`, суперпользователь не нужен. Как её создать — на странице [Подготовка PostgreSQL](postgres.md).
- `pg_monitor` открывает полные тексты запросов других пользователей в `pg_stat_statements` и `pg_stat_activity`. В них бывают литералы с данными, и всё это попадает в pgscope и видно каждому, у кого есть доступ к серверу, включая участников команды. Длину сохраняемого текста ограничивает флаг pgmetrics `--sql-length` (по умолчанию 500 символов).
- Журнал PostgreSQL pgmetrics читает только при локальном подключении на хосте базы (например, через Unix-сокет) и от имени пользователя ОС с правом чтения файлов журнала. Строки журнала тоже попадают в отчёт.
- Пароль роли храните в `~/.pgpass` с правами `0600`, а не в командной строке.
- Для баз в Docker скрипт `deploy/agent/bootstrap-monitor-role.sh` создаёт роль `pgscope_monitor`, передавая SQL через stdin и отключая на время своей сессии журналирование команд и учёт служебных команд в `pg_stat_statements`, чтобы пароль не попал ни в список процессов, ни в журнал, ни в отчёты. Подробнее — на странице [Docker и Docker Swarm](docker.md).

## Агент и Docker-сокет {#docker-agent}

- Доступ к `/var/run/docker.sock` равнозначен правам root на хосте. Агент работает в контейнере от root, потому что обращается к сокету; его образ собран на базе Alpine Linux, и кроме базовой системы в нём только агент, pgmetrics и корневые сертификаты (`ca-certificates`). Монтирование сокета с `:ro` доступ к API не ограничивает.
- Доступ можно сузить через docker-socket-proxy. Реальное ограничение даёт только запрет POST-запросов (`POST=0`); тогда автоподключение к сетям невозможно, и сети баз нужно перечислить в compose-файле агента (`PGSCOPE_AGENT_AUTOCONNECT=false`).
- Агент предъявляет пароль роли мониторинга каждому контейнеру с меткой `pgscope.enable=true`. Кто может запускать контейнеры с метками на этом хосте, тот может получить пароль. Поэтому у роли не должно быть прав сверх `pg_monitor`.
- Режим `sslmode=prefer` (по умолчанию) шифрует соединение, если сервер поддерживает TLS, но сертификат не проверяет. Для проверки задайте `PGSCOPE_AGENT_SSLMODE` или метку `pgscope.sslmode`.

Подробности и пример конфигурации с socket proxy — на странице [Docker и Docker Swarm](docker.md).

## Секреты {#secrets}

| Секрет | Где хранится | Рекомендация |
|---|---|---|
| Пароль базы для хранения | в `PGSCOPE_DB` или в `PGPASSWORD` (так сделано в `deploy/docker-compose.yml`) | файл окружения с правами `0600` (`EnvironmentFile` в systemd, `deploy/.env`) |
| `PGSCOPE_SMTP_PASS`, `PGSCOPE_AI_KEY` | переменные окружения процесса | так же; переменные окружения видны root и через `docker inspect` |
| Хеши паролей, API-ключи, токены сеансов и приглашений | таблицы `users`, `sessions`, `invites` в открытом виде (кроме хешей) | ограничьте доступ к базе для хранения и к её резервным копиям, шифруйте копии |
| Адреса каналов уведомлений (URL вебхуков Slack, ключи PagerDuty, URL VictorOps и xMatters) | таблица `notifiers` | они видны в интерфейсе всем, у кого есть доступ к серверу, и попадают в журнал pgscope при ошибке доставки |
| Ключ API и пароль роли у агента | Docker-секреты в `/run/secrets/` | переменные `PGSCOPE_*` агент не передаёт pgmetrics, а пароль роли передаёт только в его окружении (`PGPASSWORD`) |

**TLS.** Сам pgscope принимает только HTTP. Публикуйте его через reverse proxy с HTTPS, а сам сервис держите на локальном интерфейсе: `PGSCOPE_LISTEN=127.0.0.1:8080` или `PGSCOPE_PORT=127.0.0.1:8080` в Docker Compose. Исходящие TLS-соединения (STARTTLS к SMTP, вебхуки, API AI) проверяют сертификат по системному хранилищу. Если сертификат выпущен внутренним центром сертификации, добавьте его в системное хранилище или укажите PEM-файл в `SSL_CERT_FILE` (стандартное поведение Go в Linux). Подключение к базе для хранения шифруется параметром `sslmode` в `PGSCOPE_DB`.

## Данные за пределами периметра {#egress}

pgscope рассчитан на работу в закрытом контуре: веб-интерфейс не загружает внешних ресурсов (шрифтов, CDN), а ссылки на сайты pgmetrics и pgdash CLI на странице «Профиль» — обычные гиперссылки. Наружу данные уходят только через функции из таблицы, и каждую из них включаете вы сами.

| Функция | Куда уходят данные | Что передаётся | Альтернатива в закрытом контуре |
|---|---|---|---|
| AI-чат | API Anthropic (облако) или адрес из `PGSCOPE_AI_BASE_URL` | вся переписка текущего диалога (вопросы и прежние ответы) и сводка последнего отчёта: имя сервера, версия, нестандартные параметры, базы, роли, расширения, 40 крупнейших таблиц и индексов, 25 самых затратных запросов с текстами, до 60 активных сессий с текстами запросов и адресами клиентов, блокировки, репликация, системные метрики, результаты диагностики | оставьте `PGSCOPE_AI_KEY` пустым (см. [AI-чат](config.md#ai)) |
| Канал Slack | URL Incoming Webhook (обычно `hooks.slack.com`) | тема и текст уведомления: тексты правил, имена объектов, значения | email через внутренний SMTP или вебхук на внутренний адрес |
| Канал PagerDuty | всегда `https://events.pagerduty.com/v2/enqueue`, адрес изменить нельзя | тема, имя сервера, все данные уведомления, включая тексты запросов | то же |
| Каналы VictorOps и xMatters | URL из настроек канала (облачные сервисы) | VictorOps — тема, текст и имя сервера; xMatters — тема, текст, важность, имя сервера и все данные уведомления, включая тексты запросов | то же |
| Канал email | ваш SMTP-сервер | тема и текст уведомления | внутренний SMTP-сервер (см. [Почта (SMTP)](config.md#smtp)) |
| Канал «Вебхук» | любой URL из настроек канала | JSON с оповещениями или изменениями (см. [Формат вебхука](notifications.md#webhook)) | внутренний приёмник |

Внимание и на стороне сборщиков:

- pgdash CLI без `--base-url` отправляет отчёт в облачный pgDash. Всегда указывайте адрес своего pgscope; в закрытом контуре такой запрос просто не пройдёт.
- pgmetrics с `--aws-rds-dbid` обращается к API AWS CloudWatch, а с `--az-resource` — к Azure Monitor. Эти обращения идут с хоста сбора, а не с pgscope.

## Рекомендации {#checklist}

1. pgscope слушает только локальный интерфейс (`PGSCOPE_LISTEN=127.0.0.1:8080` или `PGSCOPE_PORT=127.0.0.1:8080`), а пользователи и сборщики обращаются к нему через reverse proxy с HTTPS.
2. `PGSCOPE_BASE_URL` начинается с `https://`, cookie сеанса получает флаг `Secure`.
3. Веб-интерфейс доступен только из нужных сетей; после создания учётных записей регистрация закрыта на прокси (`location = /api/signup`).
4. `/api/v1/` доступен только из сетей сборщиков, `client_max_body_size` соответствует размеру ваших отчётов.
5. Число попыток входа (`/api/login`) ограничено на прокси.
6. У роли мониторинга только `pg_monitor`; её пароль хранится в `~/.pgpass` с правами `0600` или в Docker-секрете.
7. Пароли и ключи pgscope хранятся в файлах окружения с правами `0600`, а не в unit-файле или compose-файле под системой контроля версий.
8. База для хранения доступна только pgscope и администраторам, резервные копии шифруются.
9. Хосту pgscope разрешены только нужные исходящие соединения: SMTP и внутренние приёмники вебхуков. Если данные не должны покидать периметр, `PGSCOPE_AI_KEY` пуст, а каналы Slack, PagerDuty, VictorOps и xMatters не используются.
10. Владельцы регулярно проверяют список «Совместный доступ» и неиспользованные приглашения и отзывают доступ у тех, кому он больше не нужен. Журнала аудита нет, поэтому такие проверки — единственный способ контроля.
11. Агент работает через docker-socket-proxy с `POST=0`, если автоподключение к сетям не требуется.
12. При подозрении на утечку API-ключа он сразу перегенерируется, а при подозрении на кражу сеанса сеансы пользователя удаляются в базе для хранения (см. [Сеансы и cookie](#sessions)).
