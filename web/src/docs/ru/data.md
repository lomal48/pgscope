# Хранение данных

На этой странице описано, что pgscope хранит и где: таблицы базы для хранения, сроки хранения и фоновая очистка, оценка и проверка объёма, резервное копирование и восстановление, удаление данных и перенос pgscope на другой хост.

## Где хранятся данные {#overview}

Все данные pgscope хранит в одной базе PostgreSQL — той, что указана в `PGSCOPE_DB` (по умолчанию `postgres://localhost/pgscope`). Сам процесс pgscope файлов не пишет: веб-интерфейс встроен в исполняемый файл, журнал выводится в стандартный поток ошибок (stderr). Поэтому для резервного копирования и переноса нужны только база для хранения и ваши настройки запуска (переменные окружения, unit-файл systemd или `.env` для Docker Compose).

Таблицы создаются при каждом запуске командами `CREATE TABLE IF NOT EXISTS`, новые столбцы добавляются через `ALTER TABLE … ADD COLUMN IF NOT EXISTS`. Отдельного шага миграции нет, но роли из `PGSCOPE_DB` нужно право создавать таблицы в базе.

Несколько вещей хранятся не в базе:

- Время последнего принятого отчёта каждого источника, по которому работает ограничение `PGSCOPE_MIN_REPORT_INTERVAL`, хранится в памяти процесса и сбрасывается при перезапуске.
- Переписка AI-чата хранится в браузере (`sessionStorage`) до закрытия вкладки. С каждым вопросом браузер отправляет её pgscope целиком, но pgscope её не сохраняет.
- Тема оформления, язык интерфейса и выбранный период графиков запоминаются в браузере (`localStorage`). Язык вошедшего пользователя дополнительно сохраняется в его профиле (столбец `users.lang`).

### Таблицы базы для хранения {#tables}

| Таблица | Что хранит |
|---|---|
| `users` | учётные записи: email, хеш пароля (bcrypt), API-ключ (у участников команды пусто), выбранный язык, часовой пояс интерфейса (`NULL` — пояс браузера) |
| `sessions` | сеансы входа: токен, пользователь, срок действия |
| `servers` | серверы: владелец, тип (`postgres` или `pgpool`), имя, время последнего отчёта, краткая сводка для списка серверов и Инспектора |
| `shares` | кому открыт доступ к серверу |
| `invites` | неиспользованные приглашения, не больше одного на адрес и сервер |
| `reports` | полные отчёты pgmetrics в том виде, в каком они пришли, сжатые gzip. Поле `source` пустое у отчётов самого сервера и содержит имя PgBouncer у отчётов пулера |
| `metrics` | временные ряды: по одной строке на каждый объект каждого отчёта, значения в `jsonb` |
| `alert_rules` | правила оповещений |
| `change_rules` | настройки оповещений об изменениях |
| `notifiers` | каналы уведомлений: тип, адрес, язык |
| `alert_state` | текущий набор сработавших оповещений каждого сервера |
| `events` | история: изменения набора сработавших оповещений и обнаруженные изменения |
| `agents` | Docker-агенты: сведения об агенте и его целях из последнего сигнала |

Основной объём занимают `metrics` и `reports`. По ключу объекта в `metrics.obj` видно, к чему относится строка:

| Ключ `obj` | Объект |
|---|---|
| пустая строка | сервер целиком (у Pgpool — сам Pgpool) |
| `db:<база>` | база данных |
| `tbl:<база>.<схема>.<таблица>`, `idx:<база>.<схема>.<индекс>` | таблица, индекс |
| `q:<база>:<queryid>` | запрос из `pg_stat_statements`; строки одного запроса под разными пользователями суммируются. Строки из уже удалённых баз приходят без имени базы и попадают в общий ключ `q::<queryid>` |
| `fn:<база>.<схема>.<функция>` | пользовательская функция |
| `ts:<имя>` | табличное пространство |
| `repl:<реплика>`, `slot:<слот>` | реплика (в отчёте ведущего сервера), слот репликации |
| `pgb:<имя>`, `pgb:<имя>:db:…`, `pgb:<имя>:pool:…` | PgBouncer, его базы и пулы |
| `be:<номер узла>` | бэкенд Pgpool |

### Что от чего зависит {#dependencies}

| Возможность | Источник | Срок хранения |
|---|---|---|
| Графики на страницах сервера, критерии «Рост размера» и «Рост числа строк» в «Топ-k», период на вкладке «Неиспользуемые» в «Управление индексами» | `metrics` | `PGSCOPE_METRICS_RETENTION_DAYS` |
| Вкладка «История» в «Оповещения» и список «Обнаруженные изменения» | `events` | `PGSCOPE_METRICS_RETENTION_DAYS`; интерфейс показывает последние 200 событий |
| Выбор прошлого отчёта в верхней панели: запросы, бэкенды, блокировки, планы, журнал и диагностика на тот момент | `reports` | `PGSCOPE_REPORT_RETENTION_DAYS` |
| Текущие данные страниц, диагностика, AI-чат, сравнение с предыдущим отчётом для оповещений об изменениях | последние записи `reports` | последний отчёт каждого источника хранится всегда |
| Список серверов и Инспектор | `servers` | пока существует сервер |

> [!NOTE]
> Список отчётов в верхней панели сервера показывает не больше 2000 последних отчётов за 30 дней. При отправке раз в 5 минут это примерно 7 дней. Более старые отчёты хранятся до конца срока, но выбрать их в интерфейсе нельзя.

## Сроки хранения {#retention}

| Переменная | По умолчанию | Что ограничивает |
|---|---|---|
| `PGSCOPE_METRICS_RETENTION_DAYS` | `90` | временные ряды (`metrics`) и историю событий (`events`), дней |
| `PGSCOPE_REPORT_RETENTION_DAYS` | `14` | полные отчёты (`reports`), дней |

Как работает очистка:

- Фоновая очистка выполняется сразу при запуске pgscope и затем повторяется через час после окончания предыдущего прохода.
- Удаляются строки `metrics` и `events` старше `PGSCOPE_METRICS_RETENTION_DAYS` дней и отчёты старше `PGSCOPE_REPORT_RETENTION_DAYS` дней. Возраст считается по времени отчёта, то есть по времени сбора на хосте, где работал pgmetrics.
- **Последний отчёт каждого источника не удаляется никогда**, даже если он старше срока. Источник — это сам сервер и каждый его PgBouncer. Поэтому сервер, сбор с которого остановился, продолжает показывать последнее состояние.
- Тем же проходом удаляются истёкшие сеансы входа — при любых сроках, в том числе при `0`.
- Ошибки очистки пишутся в журнал pgscope с префиксом `retention:`.
- Переменные читаются при запуске: после изменения перезапустите pgscope.

Автоматически не удаляются: сами серверы (даже если отчёты давно не приходят), записи об агентах, неиспользованные приглашения (срока действия у них нет) и текущее состояние оповещений. Как удалить их вручную, описано в разделе [Удаление данных](#deleting).

> [!NOTE]
> `0` означает «хранить всегда»: при `PGSCOPE_METRICS_RETENTION_DAYS=0` не удаляются временные ряды и история, при `PGSCOPE_REPORT_RETENTION_DAYS=0` — полные отчёты. База для хранения тогда растёт без ограничения, см. [Объём данных](#sizing). Отрицательное значение останавливает pgscope при запуске с сообщением `PGSCOPE_METRICS_RETENTION_DAYS=-1: set a number of days to keep the data, or 0 to keep it forever` (так же для `PGSCOPE_REPORT_RETENTION_DAYS`). Нечисловое значение (например, `30d`) игнорируется, и действует значение по умолчанию.

Как выбрать сроки:

- `PGSCOPE_METRICS_RETENTION_DAYS` не должен быть меньше самого длинного периода, которым вы пользуетесь: для периода графиков «30д» нужно не меньше 30 дней, для варианта «за последние 90 дней» в «Управление индексами» — не меньше 90.
- `PGSCOPE_REPORT_RETENTION_DAYS` определяет, сколько дней можно вернуться к полному отчёту (с учётом ограничения списка отчётов, описанного выше). Отчёты сжаты, но на серверах с тысячами таблиц каждый из них занимает заметное место.

После уменьшения срока ближайший проход удалит много строк. Освободившееся место PostgreSQL использует повторно, но файлы таблиц сами не уменьшатся, см. [Освобождение места на диске](#reclaim-space).

## Объём данных {#sizing}

### Из чего складывается объём {#size-drivers}

- **`metrics`**: строк в сутки = число объектов в отчёте × число отчётов в сутки. Объекты отчёта PostgreSQL — это сам сервер и каждая база, таблица, индекс, запрос из `pg_stat_statements` (pgmetrics по умолчанию берёт 100 строк; строки одного запроса под разными пользователями дают один объект), пользовательская функция (если включён `track_functions`), табличное пространство, реплика и слот репликации. В отчёте PgBouncer объекты — сам пулер, его базы и пулы, в отчёте Pgpool — сам Pgpool и его бэкенды.
- **`reports`**: средний размер сжатого отчёта × число отчётов в сутки × `PGSCOPE_REPORT_RETENTION_DAYS`, плюс последний отчёт каждого источника.
- **`events`** обычно невелика: строка добавляется только при изменении набора сработавших оповещений или при обнаруженном изменении.

Пример. Сервер с 2 000 таблиц, 3 000 индексов и 100 запросами даёт около 5 100 объектов. При отчёте раз в 5 минут (288 отчётов в сутки) это около 1,47 млн строк `metrics` в сутки и около 132 млн строк за 90 дней. Если строка вместе с индексами занимает 400 байт (это допущение для примера, своё значение получите вторым запросом ниже), таблица `metrics` займёт около 49 ГиБ.

### Как проверить фактический объём {#size-check}

Запросы выполняются в базе для хранения pgscope, например `psql "postgres://pgscope@dbhost/pgscope"`.

Размер таблиц pgscope:

```sql
SELECT c.relname AS table_name,
       pg_size_pretty(pg_total_relation_size(c.oid)) AS total_size,
       c.reltuples::bigint AS approx_rows
FROM pg_class c
WHERE c.relkind = 'r'
  AND pg_table_is_visible(c.oid)
  AND c.relname IN ('metrics', 'reports', 'events', 'servers', 'users', 'sessions', 'shares',
                    'invites', 'alert_rules', 'change_rules', 'notifiers', 'alert_state', 'agents')
ORDER BY pg_total_relation_size(c.oid) DESC;
```

Сколько байт приходится на одну строку `metrics` с учётом индексов (оценка по статистике планировщика; пока таблица ни разу не анализировалась, результат пустой):

```sql
SELECT pg_size_pretty(pg_total_relation_size(c.oid)) AS total_size,
       c.reltuples::bigint AS approx_rows,
       round(pg_total_relation_size(c.oid) / nullif(greatest(c.reltuples, 0), 0)) AS bytes_per_row
FROM pg_class c
WHERE c.oid = 'metrics'::regclass;
```

Число объектов в последнем отчёте и строк за последние сутки по серверам:

```sql
SELECT s.name,
       (SELECT count(*) FROM metrics m
         WHERE m.server_id = s.id AND m.at = s.last_report) AS objects_per_report,
       (SELECT count(*) FROM metrics m
         WHERE m.server_id = s.id AND m.at > now() - interval '1 day') AS rows_last_day
FROM servers s
ORDER BY rows_last_day DESC;
```

Полные отчёты по серверам и источникам (пустой `source` — отчёты самого сервера, иначе имя PgBouncer):

```sql
SELECT s.name, r.source, count(*) AS reports,
       pg_size_pretty(sum(octet_length(r.data))) AS total_compressed,
       pg_size_pretty(avg(octet_length(r.data))::bigint) AS avg_report
FROM reports r
JOIN servers s ON s.id = r.server_id
GROUP BY s.name, r.source
ORDER BY sum(octet_length(r.data)) DESC;
```

Чтобы оценить объём на будущее, умножьте `rows_last_day` на срок хранения временных рядов и на `bytes_per_row`, а `avg_report` — на число отчётов за срок хранения отчётов.

### Как уменьшить объём {#size-reduce}

- **Реже отправлять отчёты.** Увеличьте интервал cron или `PGSCOPE_AGENT_INTERVAL` у агента. Вдвое больший интервал вдвое уменьшает и `metrics`, и `reports`.
- **Собирать меньше объектов.** У pgmetrics есть флаги `-c`/`-C` (включить или исключить схемы) и `-a`/`-A` (таблицы) по регулярному выражению, `--omit=…` (например, `--omit=indexes`), `--statements-limit=N`. Подробнее — на странице [Отправка отчётов](collect.md). Учтите: чего нет в отчёте, того не будет ни на графиках, ни в диагностике, ни в правилах оповещений.
- **Сократить сроки хранения** (см. [Сроки хранения](#retention)).
- **Удалить ненужные серверы** (см. [Удаление данных](#deleting)).

## Резервное копирование {#backup}

Копировать нужно базу для хранения и настройки запуска. Исполняемый файл и образы можно собрать заново из исходников.

`pg_dump` делает согласованный снимок, останавливать pgscope не нужно.

Обычная установка:

```bash
pg_dump -Fc -d "postgres://pgscope@dbhost/pgscope" -f pgscope-$(date +%F).dump
```

Docker Compose из `deploy/docker-compose.yml` (база работает в сервисе `db`):

```bash
cd deploy
docker compose exec -T db pg_dump -U pgscope -Fc pgscope > pgscope-$(date +%F).dump
```

Если историю можно потерять, а важны только учётные записи, серверы, правила, каналы и доступы, исключите данные крупных таблиц:

```bash
pg_dump -Fc -d "postgres://pgscope@dbhost/pgscope" \
  --exclude-table-data=metrics --exclude-table-data=reports --exclude-table-data=events \
  -f pgscope-config-$(date +%F).dump
```

После восстановления такой копии графики и история будут пустыми, а страницы серверов будут показывать «Отчёт ещё не получен», пока не придёт следующий отчёт.

Для больших баз подходят и обычные средства физического резервного копирования PostgreSQL (`pg_basebackup`, архивация WAL): pgscope хранит всё в одной базе и других требований к копированию не предъявляет.

> [!WARNING]
> В копии базы для хранения есть хеши паролей, API-ключи, токены сеансов и приглашений, а также адреса каналов уведомлений (URL вебхуков Slack, ключи PagerDuty). Храните копии так же бережно, как саму базу: ограничьте доступ к ним и шифруйте их.

## Восстановление {#restore}

1. Остановите pgscope. Иначе при запуске он создаст пустые таблицы, и восстановление на них споткнётся.
2. Создайте пустую базу, владельцем которой будет роль pgscope.
3. Восстановите копию.
4. Запустите pgscope.

Обычная установка (команды `createdb` и `pg_restore` выполняются под суперпользователем и под ролью pgscope соответственно):

```bash
sudo systemctl stop pgscope
createdb -U postgres -O pgscope pgscope
pg_restore --no-owner -d "postgres://pgscope@dbhost/pgscope" pgscope-2026-10-26.dump
sudo systemctl start pgscope
```

Docker Compose (команда `dropdb` удаляет текущую базу со всеми данными):

```bash
cd deploy
docker compose stop pgscope
docker compose exec -T db dropdb -U pgscope pgscope
docker compose exec -T db createdb -U pgscope pgscope
docker compose exec -T db pg_restore -U pgscope --no-owner -d pgscope < pgscope-2026-10-26.dump
docker compose start pgscope
```

Что учесть после восстановления:

- Учётные записи, API-ключи и сеансы восстанавливаются вместе с базой. Сборщики продолжают работать без изменений, а пользователи остаются в системе, если их сеанс не истёк.
- Состояние оповещений восстанавливается на момент копии. Первый новый отчёт сравнивается с ним, поэтому могут прийти уведомления о сработавших или снятых оповещениях.
- Отчёты, которые сборщики не смогли отправить, пока pgscope был остановлен, позже не досылаются: на графиках останется разрыв.

## Удаление данных {#deleting}

### Сервер {#delete-server}

Владелец сервера удаляет его на странице «Команда и настройки»: в карточке «Удаление данных сервера» введите имя сервера и нажмите «Удалить сервер». Удаляются отчёты, временные ряды, правила оповещений, настройки оповещений об изменениях, каналы уведомлений, состояние и история оповещений, доступы и приглашения. Участники команды удалить сервер не могут. Подробнее — в разделе [Страница «Команда и настройки»](teams.md#server-settings).

> [!WARNING]
> Сначала остановите сбор: уберите cron-задачу или снимите метку `pgscope.enable` с контейнера (метки меняются только при пересоздании контейнера). Иначе следующий отчёт под тем же именем создаст сервер заново — пустым, без правил и каналов уведомлений.

Если владелец недоступен, администратор может удалить сервер в базе для хранения. Все связанные данные удалятся каскадно. Здесь `42` — id сервера, его видно в адресе страницы `#/s/42`:

```sql
DELETE FROM servers WHERE id = 42;
```

### Отдельный PgBouncer {#delete-pgbouncer}

В интерфейсе удалить отдельный PgBouncer нельзя. Последний отчёт каждого источника хранится всегда, поэтому выведенный из работы пулер остаётся в меню сервера, пока его данные не удалены вручную. Удалите их в базе для хранения (здесь `42` — id сервера, `pgb-1` — имя PgBouncer):

```sql
BEGIN;
DELETE FROM reports WHERE server_id = 42 AND source = 'pgb-1';
DELETE FROM metrics WHERE server_id = 42 AND (obj = 'pgb:pgb-1' OR starts_with(obj, 'pgb:pgb-1:'));
COMMIT;
```

### Аккаунт {#delete-account}

В «Профиль» → «Опасная зона» → «Удалить аккаунт». У владельца вместе с аккаунтом удаляются все его серверы со всеми данными и его агенты. У участника команды удаляется только учётная запись, серверы владельцев не затрагиваются. Подробнее — в разделе [Профиль](teams.md#profile).

### Агенты и приглашения {#delete-other}

- Запись об агенте, который не выходит на связь дольше 3 минут, удаляется кнопкой «Удалить» на странице «Агенты» (см. [Страница «Агенты»](docker.md#agents-page)). Работающий агент появится снова со следующим сигналом.
- Неиспользованное приглашение отменяет владелец сервера значком корзины («Отменить приглашение») рядом с приглашением в карточке «Совместный доступ» на странице «Команда и настройки». Само оно не истекает.

### Освобождение места на диске {#reclaim-space}

После удаления большого объёма (уменьшение срока хранения, удаление сервера) autovacuum помечает место как свободное, и PostgreSQL заполняет его новыми строками. Файлы таблиц при этом не уменьшаются. Чтобы вернуть место операционной системе:

- `VACUUM FULL metrics;` переписывает таблицу целиком. Всё это время таблица заблокирована, приём отчётов ждёт, а сборщики могут получать ошибки по таймауту. Нужно свободное место на диске примерно размером с новую копию таблицы.
- Расширение `pg_repack`, если оно установлено в базе для хранения, делает то же почти без долгой блокировки.

## Перенос на другой хост {#migration}

Всё состояние pgscope лежит в базе для хранения, поэтому перенос сводится к переносу базы и настроек запуска.

Если база остаётся на месте, достаточно запустить pgscope на новом хосте с теми же переменными окружения и переключить на него адрес (DNS или reverse proxy).

Если переносится и база:

1. Перенесите исполняемый файл или образы. В закрытом контуре образы переносятся файлами: `docker save` на старом хосте и `docker load` на новом.
2. Подготовьте на новом хосте ту же конфигурацию: unit-файл systemd или каталог `deploy` с файлом `.env`.
3. Остановите pgscope на старом хосте. С этого момента отчёты не принимаются.
4. Снимите копию базы и восстановите её на новом хосте (см. [Резервное копирование](#backup) и [Восстановление](#restore)).
5. Запустите pgscope на новом хосте, проверьте вход и приход отчётов.
6. Если изменился адрес, переключите сборщики (см. ниже).

Пример для Docker Compose:

```bash
# старый хост
cd deploy
docker compose stop pgscope
docker compose exec -T db pg_dump -U pgscope -Fc pgscope > pgscope.dump

# новый хост: тот же каталог deploy с файлом .env и копией pgscope.dump
cd deploy
docker compose up -d --wait db
docker compose exec -T db pg_restore -U pgscope --no-owner -d pgscope < pgscope.dump
docker compose up -d
```

Если у pgscope меняется адрес:

- Задайте новый `PGSCOPE_BASE_URL`: из него строятся ссылки в уведомлениях и приглашениях.
- Обновите `--base-url` во всех cron-задачах и `PGSCOPE_URL` у агентов. API-ключи остаются прежними.
- Cookie сеанса привязан к имени хоста, поэтому пользователям нужно войти заново.
- В уже отправленных письмах-приглашениях остался старый адрес. Токены приглашений действуют и на новом хосте: замените адрес в ссылке или скопируйте ссылку заново на странице «Команда и настройки».

Отчёты, отправленные во время простоя, теряются, и на графиках остаётся разрыв. Держите окно переноса коротким.
