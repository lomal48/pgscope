# Настройка pgscope

Справочник всех настроек сервера pgscope: подключение к базе для хранения, адреса, регистрация, ограничение частоты и размера отчётов, сроки хранения, почта (SMTP) и AI-чат, а также переменные окружения сторонних компонентов, которые влияют на работу pgscope. Настройки агента для Docker описаны отдельно, на странице [Docker и Docker Swarm](docker.md).

## Как задаются настройки {#how-to-set}

- pgscope настраивается **только переменными окружения**. Аргументов командной строки и файла конфигурации нет.
- Переменные читаются один раз при запуске. Чтобы применить изменения, перезапустите pgscope.
- Пустое значение равносильно отсутствию переменной: действует значение по умолчанию, а SMTP и AI-чат остаются выключенными.
- Числовые переменные принимают только целые числа. Значение, которое не удалось разобрать (например, `5m` или `30d`), молча заменяется значением по умолчанию. Недопустимое значение — отрицательный срок хранения, `PGSCOPE_MAX_REPORT_MB` меньше 1 или неизвестный режим `PGSCOPE_SIGNUP` — останавливает pgscope при запуске с сообщением в логе.
- Где задавать: в файле `EnvironmentFile` для systemd (см. [Запуск как сервис systemd](install.md#systemd)), в `deploy/.env` для Docker Compose (см. [Переменные Docker Compose](#compose-vars)) или через `docker run -e`.

При запуске pgscope пишет в лог строку `pgscope listening on АДРЕС (public URL БАЗОВЫЙ-АДРЕС)`, по ней удобно проверить `PGSCOPE_LISTEN` и `PGSCOPE_BASE_URL`. Включены ли SMTP и AI-чат, видно в интерфейсе: если нет, в форме канала уведомлений, в форме приглашения и в AI-чате показываются предупреждения.

## Подключение и адреса {#core}

### PGSCOPE_DB {#pgscope-db}

Строка подключения к базе PostgreSQL, в которой pgscope хранит все данные. Подготовка базы и нужные права описаны в разделе [База для хранения](install.md#storage-db).

- **Формат** — как у libpq: URL `postgres://пользователь:пароль@хост:порт/база?параметр=значение` или строка `host=… port=… dbname=… user=…`.
- **По умолчанию** `postgres://localhost/pgscope`: порт 5432, база `pgscope`, имя пользователя совпадает с именем пользователя ОС, под которым запущен pgscope.
- **Пароль.** В URL спецсимволы нужно кодировать (`@` → `%40`, `:` → `%3A`, `/` → `%2F`, `%` → `%25`). Проще передать пароль переменной `PGPASSWORD` или файлом `~/.pgpass` (путь можно задать в `PGPASSFILE`) — так делает `deploy/docker-compose.yml`.
- **TLS** задаётся параметром `sslmode`. По умолчанию действует `prefer`: TLS используется, если сервер его поддерживает, но сертификат не проверяется. Для проверки укажите `sslmode=verify-full` и корневой сертификат в `sslrootcert` (путь к PEM-файлу или `system` — системное хранилище). Без TLS — `sslmode=disable`.
- **Unix-сокет**: `host=/var/run/postgresql dbname=pgscope user=pgscope`.
- **Пул соединений**: по умолчанию до max(4, число ядер CPU) соединений. Изменить можно параметром `pool_max_conns`, например `?pool_max_conns=20`.

Если строка некорректна или база недоступна при запуске, pgscope пишет ошибку в лог и завершается (при недоступной базе — с префиксом `schema setup:`).

```bash
PGSCOPE_DB='postgres://pgscope@db.example.local:5432/pgscope?sslmode=verify-full&sslrootcert=/etc/pgscope/db-ca.crt'
PGPASSWORD='p@ss:word'

PGSCOPE_DB='host=/var/run/postgresql dbname=pgscope user=pgscope'

PGSCOPE_DB='postgres://pgscope:p%40ss@db.example.local/pgscope?sslmode=require&pool_max_conns=20'
```

### PGSCOPE_LISTEN {#pgscope-listen}

Адрес и порт, на которых pgscope принимает HTTP-запросы: веб-интерфейс, API интерфейса и приём отчётов (`/api/v1/…`).

- По умолчанию `:8080` — все интерфейсы.
- Примеры: `127.0.0.1:8080` (только локально, за обратным прокси), `[::1]:8080`, `0.0.0.0:9000`, `:9000`.
- pgscope работает только по HTTP. HTTPS обеспечивает обратный прокси (см. [Reverse proxy и HTTPS](install.md#reverse-proxy)).
- Если порт занят, pgscope завершается с ошибкой.
- В Docker-образе оставьте `:8080`, как в `deploy/docker-compose.yml`, а адрес на хосте задайте при публикации порта (`PGSCOPE_PORT`).
- Таймауты HTTP-сервера фиксированы: заголовки запроса должны прийти за 10 секунд, весь запрос вместе с телом — за 10 минут, ответ может идти до 35 минут (с запасом на ответ AI-чата), простаивающее соединение закрывается через 2 минуты. Так клиент не может держать соединения открытыми бесконечно.

### PGSCOPE_BASE_URL {#pgscope-base-url}

Публичный адрес pgscope — тот, по которому его открывают пользователи и к которому обращаются pgdash CLI и агенты. По умолчанию `http://localhost:8080`. Завершающий `/` отбрасывается.

Где используется:

| Где | Как |
|---|---|
| Уведомления об оповещениях | ссылки на объекты: `БАЗОВЫЙ-АДРЕС/#/s/ID/…` |
| Приглашения в команду | ссылка `БАЗОВЫЙ-АДРЕС/#/invite/ТОКЕН` в письме и в списке приглашений |
| Письма об открытии доступа | ссылка на сервер `БАЗОВЫЙ-АДРЕС/#/s/ID` |
| Готовые команды в интерфейсе | `--base-url=БАЗОВЫЙ-АДРЕС/api/v1` в профиле, на пустой странице «Серверы» и в настройках сервера; `PGSCOPE_URL` на странице «Агенты» |
| Cookie сессии | если адрес начинается с `https://`, cookie получает флаг `Secure` (см. [Cookie сессии и флаг Secure](install.md#secure-cookie)) |

Требования:

- Только схема, хост и порт, без пути: pgscope работает лишь в корне хоста.
- За HTTPS-прокси указывайте `https://…`. Если указать `https://`, а открывать pgscope напрямую по `http://`, вход не будет работать.
- pgscope не перенаправляет запросы на этот адрес и отвечает на любое имя хоста. Переменная влияет только на ссылки и cookie.

### PGSCOPE_SIGNUP {#pgscope-signup}

Кто может сам создать учётную запись на странице «Регистрация» (`POST /api/signup`). По умолчанию `first`.

| Значение | Кто может зарегистрироваться |
|---|---|
| `first` | только первый пользователь: регистрация открыта, пока в базе нет ни одной учётной записи. Первый, кто откроет pgscope, становится владельцем, после этого ссылка «Регистрация» на странице входа пропадает. Если удалить все учётные записи, регистрация откроется снова |
| `open` | любой, кто может открыть веб-интерфейс |
| `closed` | никто: учётные записи создаются только по приглашениям в команду |

- Принять приглашение в команду можно при любом значении.
- Когда регистрация закрыта, страница регистрации показывает «Регистрация новых аккаунтов отключена. Попросите администратора пригласить вас.», а `POST /api/signup` отвечает 403 с тем же текстом ещё до проверки адреса и пароля. Открыта ли регистрация сейчас, сообщает `GET /api/signup` (`{"open": true}` или `{"open": false}`); запрос доступен без входа.
- При `first` создайте свою учётную запись сразу после первого запуска: до этого зарегистрироваться и стать владельцем может любой, кто откроет pgscope.
- Регистрация — единственный способ получить обычную учётную запись с API-ключом: по приглашению создаётся учётная запись участника команды без ключа (см. [Учётные записи](teams.md#accounts)). Если собственные серверы нужны ещё кому-то, временно задайте `open`, перезапустите pgscope, дайте человеку зарегистрироваться и верните прежнее значение.
- Другое значение останавливает pgscope при запуске, например `PGSCOPE_SIGNUP=yes: use first, open or closed`.

> [!WARNING]
> При обновлении с версии без этой настройки: если в базе уже есть учётные записи, новые пользователи больше не смогут зарегистрироваться сами. Чтобы сохранить прежнее поведение, задайте `PGSCOPE_SIGNUP=open`.

### PGSCOPE_MIN_REPORT_INTERVAL {#pgscope-min-report-interval}

Минимальный интервал в секундах между принятыми отчётами одного сервера. По умолчанию `60`.

- Ограничение действует отдельно для каждого сочетания «аккаунт, тип сервера (PostgreSQL или Pgpool), имя сервера, экземпляр PgBouncer». Отчёты PgBouncer не мешают отчётам своего сервера PostgreSQL и друг другу.
- Слишком частый отчёт отклоняется с кодом 429 и сообщением «Отчёты отправляются слишком часто». Пока предыдущий отчёт того же сервера ещё сохраняется, новый отклоняется с кодом 409 — независимо от этой настройки.
- `0` отключает ограничение.
- Отметки времени хранятся в памяти процесса и сбрасываются при перезапуске.
- Действующее значение показано в карточке «Отправка отчётов» на странице профиля («Интервал между отчётами одного сервера — не менее …»; при `0` фраза не показывается) и возвращается в поле `min_report_interval` ответа `GET /api/me`.
- Ограничение защищает базу для хранения от заданий, которые по ошибке отправляют отчёты в цикле. Интервал pgscope-agent (`PGSCOPE_AGENT_INTERVAL`) и расписание cron должны быть не меньше этого значения; рекомендуемый интервал отправки — 5 минут.

Коды ответов приёма отчётов подробно описаны в разделе [Ответы сервера](collect.md#responses).

### PGSCOPE_MAX_REPORT_MB {#pgscope-max-report-mb}

Предельный размер одного отчёта в МиБ. По умолчанию `256`.

- Предел проверяется дважды: для тела запроса в том виде, в каком оно пришло (обычно сжатое gzip), и для данных после распаковки. Он действует для `POST /api/v1/report`, `/api/v1/reportpgbouncer` и `/api/v1/reportpgpool`; у сигнала агента свой предел — 4 МиБ.
- Более крупный отчёт отклоняется с кодом 413 и сообщением «Отчёт больше 256 МиБ — это предел PGSCOPE_MAX_REPORT_MB на сервере pgscope» (в сообщении — действующее значение).
- pgmetrics пишет примерно 0,4–1 КиБ на таблицу или индекс, поэтому 256 МиБ хватает примерно на 250 тысяч объектов.
- Одновременно pgscope читает и сохраняет не больше 4 отчётов, остальные ждут очереди. На сохранение отчёта уходит в 5–7 раз больше памяти, чем его размер, поэтому в худшем случае приёму нужно около 24 × `PGSCOPE_MAX_REPORT_MB` МиБ памяти — при значении по умолчанию около 6 ГиБ. На хосте с небольшой памятью уменьшите предел, оставив запас над размером ваших самых крупных отчётов.
- Значение меньше `1` останавливает pgscope при запуске с сообщением `PGSCOPE_MAX_REPORT_MB must be at least 1`.
- Предел размера тела на обратном прокси должен быть не меньше (в nginx — `client_max_body_size`, см. [Reverse proxy и HTTPS](install.md#reverse-proxy)).

### Сроки хранения {#retention-vars}

| Переменная | По умолчанию | Что удаляется |
|---|---|---|
| `PGSCOPE_METRICS_RETENTION_DAYS` | `90` | временные ряды (графики, рост размеров) и история оповещений и изменений старше указанного числа дней |
| `PGSCOPE_REPORT_RETENTION_DAYS` | `14` | полные отчёты старше указанного числа дней, кроме последнего отчёта каждого сервера и каждого экземпляра PgBouncer |

- Очистка выполняется при запуске pgscope и затем раз в час. Одновременно удаляются истёкшие сессии — при любых сроках хранения.
- Значения — целое число дней. `0` означает «хранить всегда»: при `PGSCOPE_METRICS_RETENTION_DAYS=0` не удаляются временные ряды и история, при `PGSCOPE_REPORT_RETENTION_DAYS=0` — полные отчёты. Отрицательное значение останавливает pgscope при запуске с сообщением `PGSCOPE_METRICS_RETENTION_DAYS=-1: set a number of days to keep the data, or 0 to keep it forever` (так же для `PGSCOPE_REPORT_RETENTION_DAYS`).
- От срока хранения отчётов зависит, насколько далеко назад можно открыть прошлый отчёт и посмотреть запросы, бэкенды и блокировки. От срока хранения рядов — глубина графиков: для диапазона «30д» нужно не меньше 30 дней.
- Чем больше срок и чем больше объектов в отчётах, тем больше база для хранения. Оценка объёма и способы его сократить — на странице [Хранение данных](data.md#retention).

## Почта (SMTP) {#smtp}

pgscope отправляет письма через SMTP-сервер, указанный в настройках. В закрытом контуре это штатный способ доставки уведомлений: укажите внутренний почтовый сервер.

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `PGSCOPE_SMTP_ADDR` | — | адрес SMTP-сервера в виде `хост:порт`, порт обязателен. Пустое значение выключает отправку почты |
| `PGSCOPE_SMTP_USER` | — | логин. Если задан, используется аутентификация PLAIN |
| `PGSCOPE_SMTP_PASS` | — | пароль к логину |
| `PGSCOPE_SMTP_FROM` | `pgscope@localhost` | адрес отправителя: заголовок `From` и адрес в команде `MAIL FROM`. Укажите адрес, который ваш почтовый сервер примет |

**Что отправляется по почте:**

| Письмо | Кому | Если SMTP не настроен |
|---|---|---|
| Уведомления каналов типа email — об оповещениях и об изменениях | адресам из канала (несколько адресов — через запятую) | канал можно создать, но в форме при выборе email показано предупреждение «SMTP не настроен на этом сервере pgscope (PGSCOPE_SMTP_ADDR), поэтому письма не будут доставлены.». Кнопка «Проверить» вернёт ошибку «Не удалось отправить уведомление: SMTP не настроен (задайте PGSCOPE_SMTP_ADDR)», настоящие уведомления не отправляются (ошибка пишется в лог pgscope) |
| Приглашение нового пользователя в команду | приглашённому и владельцу (одно письмо, оба адреса в заголовке `To`) | приглашение всё равно создаётся, ссылка видна владельцу в списке приглашений: «SMTP не настроен: скопируйте ссылку-приглашение из списка и отправьте её самостоятельно.» |
| Сообщение об открытии доступа пользователю, у которого уже есть аккаунт | этому пользователю и владельцу (одно письмо) | доступ открывается сразу, письмо не отправляется |

Письма — простой текст в UTF-8. Уведомления пишутся на языке, выбранном для канала, приглашения — на языке того, кто приглашает. Если в канале несколько адресов, все они стоят в заголовке `To` одного письма и видны каждому получателю.

Каждое письмо получает заголовки `Date` и `Message-ID` (домен в `Message-ID` берётся из `PGSCOPE_SMTP_FROM`, а если в адресе его нет — `localhost`), поэтому строгие почтовые фильтры не отклоняют письма из-за их отсутствия.

Список адресов канала очищается перед отправкой: пробелы по краям отбрасываются, пустые элементы (лишняя или завершающая запятая) пропускаются, повторяющиеся адреса (без учёта регистра) получают одно письмо. Если не остаётся ни одного адреса, отправка завершается ошибкой «Не указан ни один адрес получателя».

**Как устанавливается соединение:**

- pgscope подключается к `PGSCOPE_SMTP_ADDR` обычным TCP. Если сервер предлагает STARTTLS, соединение переводится на TLS с проверкой сертификата по имени хоста из `PGSCOPE_SMTP_ADDR`.
- SMTPS с TLS с первого байта (обычно порт 465) не поддерживается. Используйте порт 587 (submission со STARTTLS) или 25.
- На отправку одного письма — подключение и весь обмен с SMTP-сервером — отводится 30 секунд. Если сервер не отвечает, отправка завершается ошибкой, и кнопка «Проверить» не позже чем через 30 секунд показывает «Не удалось отправить уведомление: SMTP-сервер не принял письмо».
- Пароль передаётся только по зашифрованному соединению: если задан `PGSCOPE_SMTP_USER`, сервер должен поддерживать STARTTLS (исключение — сервер на `localhost`). Если сервер не объявляет поддержку AUTH, отправка завершится ошибкой.
- Если сертификат почтового сервера выпущен внутренним центром сертификации, добавьте корневой сертификат в системное хранилище хоста или передайте его pgscope через `SSL_CERT_FILE` (см. [Переменные окружения сторонних компонентов](#other-env)).
- Если SMTP-сервер отклонил письмо или недоступен, pgscope пишет причину в лог с префиксом `smtp:`. В интерфейсе ошибка видна только при проверке канала кнопкой «Проверить»: «Не удалось отправить уведомление: SMTP-сервер не принял письмо». Неудачные уведомления дополнительно пишутся в лог строкой `notify email …`. Письма о приглашениях и открытии доступа отправляются в фоне: если SMTP не настроен, pgscope один раз за время работы пишет в лог `team emails are not sent: SMTP is not configured (PGSCOPE_SMTP_ADDR); pass invitation links on yourself`, а неудачная отправка пишется строкой `team email "…" to … not sent: …`. Интерфейс о таких письмах не сообщает, поэтому ссылку-приглашение всегда можно скопировать из списка приглашений.

Внутренний релей без аутентификации:

```bash
PGSCOPE_SMTP_ADDR=mail.example.local:25
PGSCOPE_SMTP_FROM=pgscope@example.com
```

Почтовый сервер с аутентификацией:

```bash
PGSCOPE_SMTP_ADDR=smtp.example.com:587
PGSCOPE_SMTP_USER=pgscope@example.com
PGSCOPE_SMTP_PASS=пароль-почтового-ящика
PGSCOPE_SMTP_FROM=pgscope@example.com
```

После настройки создайте канал email на странице «Оповещения» любого сервера и нажмите «Проверить» (см. [Каналы уведомлений](notifications.md)).

## AI-чат {#ai}

AI-чат отвечает на вопросы о сервере, опираясь на его последний отчёт (как он выглядит в интерфейсе, см. [AI-чат](monitoring.md#ai-chat)). По умолчанию чат выключен.

> [!WARNING]
> Текущая реализация работает только через облачный API Anthropic. Включённый чат отправляет данные наблюдаемых серверов за пределы вашей сети. В закрытом контуре оставьте `PGSCOPE_AI_KEY` пустым: так чат выключен, и pgscope не обращается к внешним адресам.

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `PGSCOPE_AI_KEY` | — | API-ключ Anthropic. Непустое значение включает AI-чат для всех пользователей и серверов этого pgscope |
| `PGSCOPE_AI_MODEL` | `claude-opus-5-5` | идентификатор модели Anthropic |
| `PGSCOPE_AI_BASE_URL` | — | базовый адрес API вместо стандартного адреса Anthropic: корпоративный прокси или шлюз, совместимый с Anthropic Messages API |

Переменная `PGSCOPE_AI_PROVIDER` из прежних версий больше не читается: других провайдеров, в том числе локальных моделей, нет.

**Когда чат выключен** (ключ не задан), на странице «AI-чат» показывается сообщение «AI-чат не настроен. Задайте PGSCOPE_AI_KEY (API-ключ Anthropic) и перезапустите pgscope.», поле ввода недоступно, а API чата отвечает кодом 501.

**Что уходит в Anthropic.** Каждый вопрос отправляется вместе со всей перепиской и сводкой последнего отчёта сервера — даже если в интерфейсе выбран прошлый отчёт. В одном диалоге может быть не больше 50 сообщений, то есть 25 вопросов с ответами; дальше сервер отвечает ошибкой 400, и нужно начать новый диалог. В сводку входят:

- имя сервера, версия PostgreSQL, время запуска, признак реплики;
- параметры конфигурации, отличные от значений по умолчанию;
- базы данных, табличные пространства, роли, расширения;
- 40 крупнейших таблиц и 40 крупнейших индексов;
- 25 самых затратных по общему времени запросов из `pg_stat_statements` с текстами запросов;
- до 60 сессий, кроме простаивающих (`idle`) и фоновых процессов без состояния: роль, база, приложение, адрес клиента, текст запроса;
- ожидающие блокировки, репликация и слоты, WAL, контрольные точки, системные метрики, результаты диагностики и проверки конфигурации.

Тексты запросов могут содержать литералы с данными. Пароли ролей в отчёт pgmetrics не входят, но значения параметров передаются как есть: если пароль записан в параметре конфигурации (например, в `primary_conninfo`) и роль мониторинга может его прочитать, он попадёт в сводку.

**Как устроен запрос.** pgscope вызывает Anthropic Messages API через официальный Go SDK: до 16 000 токенов в ответе, кеширование контекста отчёта между вопросами одного диалога и бета-возможности API (уровень усилий и резервная модель на стороне сервера). Переписку хранит только браузер, в хранилище сессии (`sessionStorage`) вкладки, отдельно для каждого сервера: на сервере и в базе она не сохраняется, переживает перезагрузку страницы и пропадает при закрытии вкладки или по кнопке «Новый диалог». Чатом может пользоваться любой, у кого есть доступ к серверу, — и владелец, и участники команды. Ответ приходит на языке интерфейса, если пользователь не пишет на другом языке. SDK ждёт ответа до 10 минут на попытку и делает до 3 попыток, поэтому pgscope держит ответ чата открытым до 35 минут; учтите это в таймауте чтения ответа на прокси (`proxy_read_timeout`).

**Ошибки.**

| Код | Сообщение | Причина |
|---|---|---|
| 501 | «AI-чат не настроен: укажите API-ключ Anthropic в PGSCOPE_AI_KEY» | ключ не задан |
| 400 | «Некорректный запрос» | в диалоге больше 50 сообщений: начните новый диалог |
| 404 | «Отчётов пока нет» | у сервера ещё нет отчётов |
| 502 | «AI-провайдер вернул HTTP …» | API отклонил запрос: неверный ключ, неизвестная модель, превышены лимиты |
| 502 | «Не удалось связаться с AI-провайдером» | нет сетевого доступа к API или к прокси |
| 502 | «AI-модель отказалась отвечать на этот вопрос» | модель отказалась отвечать |

**`PGSCOPE_AI_BASE_URL` и закрытый контур.** Переменная позволяет направить запросы через корпоративный шлюз, который проверяет и журналирует трафик к Anthropic. Данные при этом всё равно уходят в облако. Локальная модель за таким адресом должна поддерживать Anthropic Messages API вместе с бета-параметрами, которые передаёт pgscope; такая схема не проверялась и не поддерживается. Учтите также, что API Anthropic доступен не во всех странах.

Включение чата (если политика безопасности разрешает передачу данных):

```bash
PGSCOPE_AI_KEY=ВАШ_КЛЮЧ_ANTHROPIC
PGSCOPE_AI_MODEL=claude-opus-5-5
```

## Переменные окружения сторонних компонентов {#other-env}

Эти переменные читает не сам pgscope, а библиотеки, на которых он построен. Иногда они полезны.

| Переменная | Кто читает | Зачем |
|---|---|---|
| `PGPASSWORD`, `PGPASSFILE`, `PGHOST`, `PGPORT`, `PGUSER`, `PGDATABASE`, `PGSSLMODE`, `PGSSLROOTCERT`, `PGAPPNAME`, `PGCONNECT_TIMEOUT` и другие `PG*` | драйвер PostgreSQL (pgx) при подключении к базе для хранения | значения, которых нет в `PGSCOPE_DB`. `deploy/docker-compose.yml` передаёт так пароль (`PGPASSWORD`) |
| `SSL_CERT_FILE`, `SSL_CERT_DIR` | TLS в Go | корневые сертификаты, которым доверяет pgscope при STARTTLS к SMTP, вызове вебхуков по HTTPS, обращении к AI API и проверке сертификата базы с `sslrootcert=system`. `SSL_CERT_FILE` — PEM-файл вместо системного файла-набора (например, `/etc/ssl/certs/ca-certificates.crt`); сертификаты из каталогов `/etc/ssl/certs` и `/etc/pki/tls/certs` при этом всё равно читаются. `SSL_CERT_DIR` — список каталогов через `:` вместо этих стандартных. Нужны, если сервисы используют сертификаты внутреннего центра сертификации, который не добавлен в системное хранилище |
| `HTTPS_PROXY`, `HTTP_PROXY`, `NO_PROXY` | HTTP-клиент Go | прокси для исходящих HTTP-запросов: вебхуки, Slack, PagerDuty, VictorOps, xMatters, AI-чат. Почта через прокси не идёт. Внутренние адреса вебхуков перечислите в `NO_PROXY` |
| `ANTHROPIC_BASE_URL`, `ANTHROPIC_CUSTOM_HEADERS` и другие `ANTHROPIC_*` | SDK Anthropic | `PGSCOPE_AI_KEY` и `PGSCOPE_AI_BASE_URL` имеют приоритет; чат включается только переменной `PGSCOPE_AI_KEY` |

## Переменные Docker Compose {#compose-vars}

Файл `deploy/docker-compose.yml` читает переменные из `deploy/.env`. Три из них использует только сам compose-файл:

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `PGSCOPE_DB_PASSWORD` | обязательна | пароль пользователя `pgscope` в контейнере базы. Применяется только при первой инициализации тома `pgscope-data`; в pgscope передаётся как `PGPASSWORD` |
| `PGSCOPE_PORT` | `8080` | порт на хосте, на котором публикуется pgscope; `127.0.0.1:8080` — только локальный интерфейс |
| `PGSCOPE_IMAGE` | `pgscope:latest` | образ pgscope; укажите версионный тег, чтобы обновления и откаты были явными |

`PGSCOPE_DB` (`postgres://pgscope@db:5432/pgscope?sslmode=disable`) и `PGSCOPE_LISTEN` (`:8080`) заданы в compose-файле жёстко. Чтобы хранить данные во внешней базе, отредактируйте compose-файл. Остальные переменные (`PGSCOPE_BASE_URL`, `PGSCOPE_SIGNUP`, `PGSCOPE_MIN_REPORT_INTERVAL`, `PGSCOPE_MAX_REPORT_MB`, сроки хранения, `PGSCOPE_SMTP_*`, `PGSCOPE_AI_KEY`, `PGSCOPE_AI_MODEL`, `PGSCOPE_AI_BASE_URL`) передаются из `.env` с теми же значениями по умолчанию, что и у pgscope.

Переменные, которых нет в секции `environment` сервиса `pgscope` (например, `SSL_CERT_FILE`, `HTTPS_PROXY`, `NO_PROXY`), из `.env` в контейнер не попадают: `.env` служит только для подстановки значений в compose-файл. Добавьте такие переменные в `environment` сами, а файлы сертификатов смонтируйте в контейнер через `volumes`.

## Примеры конфигурации {#examples}

Пробная установка на одном хосте, без прокси:

```bash
PGSCOPE_DB=postgres://pgscope:secret@localhost/pgscope
PGSCOPE_BASE_URL=http://monitor.example.local:8080
```

Промышленная установка за HTTPS-прокси, с внутренней почтой, в закрытом контуре (AI-чат выключен, потому что `PGSCOPE_AI_KEY` не задан):

```bash
PGSCOPE_DB=postgres://pgscope@pgstore.example.local:5432/pgscope?sslmode=verify-full&sslrootcert=/etc/pgscope/db-ca.crt
PGPASSWORD=надёжный-пароль
PGSCOPE_LISTEN=127.0.0.1:8080
PGSCOPE_BASE_URL=https://pgscope.example.local
PGSCOPE_SMTP_ADDR=mail.example.local:25
PGSCOPE_SMTP_FROM=pgscope@example.local
PGSCOPE_METRICS_RETENTION_DAYS=60
PGSCOPE_REPORT_RETENTION_DAYS=7
# корневой сертификат внутреннего центра сертификации (вместо системного файла-набора)
SSL_CERT_FILE=/etc/pgscope/internal-ca.pem
```

## Переменные агента {#agent-vars}

pgscope-agent настраивается своими переменными: `PGSCOPE_URL`, `PGSCOPE_API_KEY` или `PGSCOPE_API_KEY_FILE`, `PGSCOPE_AGENT_*` (интервал сбора, роль мониторинга, таймауты, сети), а также `DOCKER_HOST` и `PGMETRICS`. Они описаны на странице [Docker и Docker Swarm](docker.md). Интервал сбора агента не должен быть меньше `PGSCOPE_MIN_REPORT_INTERVAL` сервера, иначе часть отчётов будет отклонена с кодом 429.
