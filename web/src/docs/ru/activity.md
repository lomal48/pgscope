# Запросы, бэкенды и блокировки

Эта страница описывает группу «Активность» сервера PostgreSQL: «Запросы» — статистику `pg_stat_statements` с графиками, советами и планами выполнения, «Бэкенды» — все клиентские подключения на момент отчёта, и «Блокировки» — цепочки блокировок и список всех блокировок.

Все три страницы показывают снимок из отчёта — последнего или выбранного в верхней панели (см. [Выбор прошлого отчёта](ui.md#report-picker)). pgscope видит сервер только в моменты сбора отчётов (обычно раз в несколько минут), поэтому короткие всплески между отчётами в снимок не попадают.

## Запросы {#queries}

Страница «Запросы» (адрес `#/s/<id>/queries`) показывает самые тяжёлые запросы сервера по данным расширения `pg_stat_statements`.

### Откуда берутся данные {#queries-source}

- pgmetrics читает представление `pg_stat_statements` и передаёт в отчёте запросы с наибольшим общим временем выполнения. По умолчанию — 100 запросов (флаг pgmetrics `--statements-limit`), тексты усечены до 500 символов (флаг `--sql-length`).
- Все показатели накопительные: они растут с момента последнего сброса статистики `pg_stat_statements` (`pg_stat_statements_reset()`).
- Тексты запросов нормализует сам PostgreSQL: как правило, константы в них заменены параметрами `$1`, `$2` и т. д.

Если расширение не установлено или недоступно роли мониторинга, страница показывает «Нет статистики запросов» с инструкцией: добавить `pg_stat_statements` в `shared_preload_libraries`, перезапустить PostgreSQL и выполнить `CREATE EXTENSION pg_stat_statements` в каждой базе. Подробно — в разделе [Подготовка PostgreSQL](postgres.md).

Некоторые показатели появляются только при дополнительных настройках PostgreSQL:

| Показатель | Что нужно |
|---|---|
| время чтения и записи блоков | `track_io_timing = on` |
| время планирования и число планирований | `pg_stat_statements.track_planning = on` |
| показатели JIT | PostgreSQL 15 и новее |
| планы выполнения | `auto_explain` с `auto_explain.log_format = json` и доступ pgmetrics к журналу PostgreSQL: журнал в формате `stderr` или `csvlog` (`csvlog` PostgreSQL 13+ — только с [pgmetrics из сборки pgscope](collect.md#pgmetrics-build)), pgmetrics работает на хосте базы с локальным подключением (для RDS / Aurora — `--aws-rds-dbid`), см. [Планы выполнения](#plans) |

### Список запросов {#queries-list}

В заголовке — число разных запросов в отчёте (строки одного запроса от разных пользователей считаются одним запросом) и их суммарное время выполнения. Над таблицей — выбор базы («Все базы» или конкретная) и поле «Фильтр…», которое ищет по тексту запроса, пользователю и базе. По умолчанию таблица отсортирована по общему времени.

| Столбец | Что показывает |
|---|---|
| «Запрос» | нормализованный текст запроса; в таблице он обрезается до двух строк, полный текст — на странице запроса |
| «База данных», «Пользователь» | где и от чьего имени выполнялся запрос; если запрос в этой базе выполняли несколько пользователей, они перечислены через запятую |
| «Вызовы» | число выполнений |
| «Общее время» | суммарное время выполнения; полоса показывает долю запроса в общем времени всех собранных запросов |
| «Среднее» | общее время / число вызовов |
| «Макс.» | наибольшее время одного выполнения |
| «Строк за вызов» | среднее число возвращённых или изменённых строк |
| «Попадания в кеш» | доля блоков, прочитанных из `shared_buffers`; ниже 90 % выделяется жёлтым |
| «Временные файлы» | объём, записанный запросом во временные файлы (число временных блоков × 8 КиБ) |

Как пользоваться:

- **Сортировка по «Общее время»** показывает, на что сервер тратит больше всего времени. Это главный кандидат на оптимизацию: ускорение частого запроса на 10 % может дать больше, чем ускорение редкого в 10 раз.
- **Сортировка по «Среднее» и «Макс.»** находит медленные отдельные выполнения, которые замечают пользователи.
- **Сортировка по «Вызовы»** находит запросы, которые приложение вызывает слишком часто (например, N+1 в ORM).
- **«Временные файлы»** — признак сортировок и хешей, не помещающихся в `work_mem`.

Щелчок по строке открывает страницу запроса.

> [!NOTE]
> `pg_stat_statements` ведёт отдельную строку для каждого пользователя, выполнявшего запрос. pgscope объединяет строки одного запроса в одной базе (с одинаковым `queryid`): вызовы, время, строки, блоки и остальные счётчики суммируются, «Макс.» и минимальное время берутся по всем пользователям, стандартное отклонение считается по всем выполнениям, а «Среднее» — общее время / число вызовов. Так же построены карточки и графики на странице запроса и правила оповещений уровня «Запрос» (см. [Запрос](alerts.md#metrics-query)). Строки удалённых баз приходят без имени базы, поэтому одинаковые запросы из разных удалённых баз тоже объединяются в один.

### Страница запроса {#query-detail}

Адрес страницы — `#/s/<id>/queries/<база>/<queryid>`. Если запроса нет в показываемом отчёте (например, выбран прошлый отчёт или запрос выпал из числа собранных), под заголовком написано «Отсутствует в выбранном отчёте». Графики в этом случае всё равно показываются, если для них есть данные; карточек, советов и раздела «Статистика» нет, а раздел планов пуст.

Страница содержит:

- под заголовком — пользователи и база в виде `пользователь@база` (несколько пользователей — через запятую);
- полный текст запроса (в пределах `--sql-length`) с кнопкой «Копировать»;
- карточки: «Вызовы», «Общее время», «Среднее время», «Макс. время» (с минимальным временем ниже), «Строки» (с числом строк за вызов), «Попадания в кеш» — по всем пользователям запроса;
- карточку «Советы» — автоматические рекомендации (см. [Советы по запросу](#query-suggestions));
- раздел «Динамика» — графики по этому запросу (см. [Графики запроса](#query-charts));
- раздел «Статистика» — все остальные поля `pg_stat_statements`: стандартное отклонение времени, разделяемые блоки (попадания, прочитано, загрязнено, записано), локальные и временные блоки, время чтения и записи блоков, число и время планирований, записи WAL, полные образы страниц, объём WAL, JIT-функции и время генерации JIT, идентификатор запроса;
- раздел «Планы выполнения» (см. [Планы выполнения](#plans)).

### Советы по запросу {#query-suggestions}

Карточка «Советы» появляется, если для запроса сработало хотя бы одно правило:

| Условие | Совет |
|---|---|
| больше 10 000 обращений к разделяемым блокам (попадания + чтения) и доля попаданий в кеш ниже 90 % | индекс, сокращающий число просматриваемых строк, или больше `shared_buffers` / RAM |
| запрос записывал временные файлы | увеличить `work_mem` для этой нагрузки или добавить индекс, обеспечивающий нужный порядок |
| в среднем больше 1000 строк за вызов | `LIMIT`, keyset-пагинация или агрегация в SQL |
| больше 10 вызовов, стандартное отклонение больше 2 средних и максимум больше 10 средних | проверить планы, зависящие от параметров, ожидания блокировок, холодный кеш |
| время чтения и записи блоков больше 30 % общего времени (при общем времени больше 1 с) | запрос упирается в дисковый ввод-вывод |
| время планирования больше половины времени выполнения (и больше 100 мс в сумме) | подготовленные операторы, чтобы планировать один раз |
| JIT занимает больше 10 % времени (и больше 100 мс) | `jit = off` или более высокий `jit_above_cost` |
| больше 100 000 вызовов при среднем времени меньше 0,5 мс | кеширование результатов в приложении или пакетная обработка |
| запрос сгенерировал больше 1 ГиБ WAL | объединять массовые изменения в пакеты или использовать `COPY` |
| найдены проблемы в собранных JSON-планах | предупреждения из плана с префиксом «План:» (см. [Как читать план](#plan-view)) |

### Графики запроса {#query-charts}

Раздел «Динамика» строится по значениям этого запроса из каждого отчёта за выбранный период:

| График | Что показывает |
|---|---|
| «Вызовы» | вызовов в секунду |
| «Среднее время выполнения» | среднее время одного выполнения за каждый интервал между отчётами; показывает, когда запрос начал работать медленнее |
| «Строки» | строк в секунду |
| «Разделяемые блоки» | «Попадания» и «Чтения» блоков в секунду |
| «Общее затраченное время» | миллисекунд выполнения в секунду: 1000 мс/с означает, что в среднем одно подключение всё время выполняло этот запрос |
| «Записанные временные блоки» | временных блоков в секунду |

Точки есть только для отчётов, в которые запрос попал. Если запрос то входит в число собранных pgmetrics, то выпадает из него, на графиках будут разрывы. После `pg_stat_statements_reset()` для интервала со сбросом скорость не вычисляется.

### Планы выполнения {#plans}

Раздел «Планы выполнения» показывает планы этого запроса, которые записал в журнал PostgreSQL модуль `auto_explain`. Чтобы они появились, нужно:

1. Включить `auto_explain` и задать формат JSON — только он отображается деревом, планы в других форматах показываются как текст:

```ini
shared_preload_libraries = 'pg_stat_statements,auto_explain'
auto_explain.log_min_duration = 2000   # планы запросов дольше 2 секунд
auto_explain.log_analyze = on          # фактические строки и циклы
auto_explain.log_timing = off          # on — время по узлам, но больше накладных расходов
auto_explain.log_format = json
```

2. Дать pgmetrics доступ к журналу. pgmetrics читает журнал, только когда работает на хосте базы данных и подключается локально (через Unix-сокет или 127.0.0.1); флаги `--log-file` и `--log-dir` лишь указывают, где лежит журнал, и локальное подключение не заменяют. Для AWS RDS / Aurora журнал читается через API при флаге `--aws-rds-dbid`. Журнал пишется в формате `stderr` (`log_destination = 'stderr'`) с меткой времени в `log_line_prefix`, например `'%m [%p] %q%u@%d '`, или в формате `csvlog`. `csvlog` PostgreSQL 13+ читает только [pgmetrics из сборки pgscope](collect.md#pgmetrics-build), официальные выпуски такие файлы пропускают (подробности — в разделе [Журнал](server.md#logs)). Из журнала берутся записи только за последние минуты: по умолчанию 5, флаг `--log-span` (см. [Отправка отчётов](collect.md)).

Без планов раздел показывает «Планы выполнения не собраны» с этими же подсказками.

Как планы связываются с запросом: по идентификатору запроса, если он записан в плане, иначе — по тексту (среди планов той же базы или планов без указания базы). При сравнении текстов константы и параметры `$n` заменяются одинаковой заглушкой, регистр и пробелы не учитываются. Для очень длинных запросов, текст которых в `pg_stat_statements` усечён, сопоставление по тексту может не сработать.

Показываются три последних плана, остальные — по кнопке «Показать все планы (N)». Над каждым планом — время записи в журнал, пользователь и база.

### Как читать план {#plan-view}

JSON-план показывается деревом узлов. Узлы с дочерними элементами сворачиваются щелчком по стрелке.

Над деревом:

- «всего …» — общее время выполнения, если в плане есть время по узлам (`auto_explain.log_timing = on`);
- «полосы показывают долю стоимости (нет данных о времени)» — если времени по узлам нет;
- общее число строк результата, если включён `log_analyze`.

Строка узла:

| Элемент | Что показывает |
|---|---|
| тип узла | например, `Seq Scan`, `Index Scan`, `Hash Join (Inner)` |
| объект | таблица (`on схема.таблица псевдоним`), индекс (`using индекс`) или CTE |
| фактические строки | строки, которые вернул узел, и `× N` — число циклов, если узел выполнялся несколько раз |
| «оценка N» | сколько строк ожидал планировщик |
| время | собственное время узла (без дочерних), если есть время по узлам |
| «стоимость N» | итоговая стоимость узла по оценке планировщика |
| условия | `Index Cond`, `Recheck Cond`, `Hash Cond`, `Merge Cond`, `Join Filter`, `Filter`, `Sort Key`, `Group Key` |

Полоса под узлом — его доля в общем времени (собственное время узла) или, если времени нет, доля его стоимости в стоимости всего плана. Цвет полосы: красный — больше 50 %, жёлтый — больше 20 %, иначе обычный. Начинайте разбор с красных узлов. Учтите, что стоимость узла по оценке планировщика включает стоимость дочерних узлов: без данных о времени полоса корня всегда полная, а полосы верхних узлов длиннее, чем их собственный вклад.

Под узлом выводятся предупреждения:

| Предупреждение | Когда появляется | Что делать |
|---|---|---|
| планировщик ожидал меньше строк, чем получил | фактических строк больше оценки более чем в 10 раз (когда хотя бы одно из значений больше 100); переоценки не учитываются, так как они нормальны под `LIMIT` | `ANALYZE` таблицы или расширенная статистика (`CREATE STATISTICS`) |
| `Seq Scan` отбрасывает много строк | фильтр отбросил больше 1000 строк и в 10 раз больше, чем вернул | индекс по столбцам фильтра |
| сортировка вышла на диск | метод сортировки `external` | увеличить `work_mem` |
| Hash разбит на пакеты | больше одного пакета (batch) у хеша | увеличить `work_mem` |
| `Nested Loop` выполнен много раз | больше 1000 циклов узла | проверить оценки строк и индексы для соединения |
| много обращений к куче в Index Only Scan | `Heap Fetches` больше 10 000 | `VACUUM`, чтобы обновить карту видимости |

Предупреждения о расхождении оценок требуют фактических строк, то есть `auto_explain.log_analyze = on`.

## Бэкенды {#backends}

Страница «Бэкенды» (адрес `#/s/<id>/backends`) показывает все клиентские подключения к серверу на момент отчёта. В заголовке — число подключений и время отчёта. Все возрасты (транзакции, запроса, подключения) считаются от момента отчёта.

В PostgreSQL 10 и новее pgmetrics собирает только клиентские бэкенды (`backend_type = 'client backend'`); фоновые процессы учитываются в разделе «Типы бэкендов». Тексты запросов усечены до 500 символов (флаг pgmetrics `--sql-length`).

### Карточки и фильтры {#backends-filters}

| Карточка | Что считает | Выделение |
|---|---|---|
| «Всего» | все клиентские подключения | — |
| «Активные» | состояние `active` | зелёным |
| «Простаивают» | состояние `idle` | — |
| «Простой в транзакции» | состояния `idle in transaction` и `idle in transaction (aborted)` | жёлтым, если больше 0 |
| «Ждут блокировок» | `wait_event_type = Lock` | красным, если больше 0 |
| «Транзакции > 5 мин» | транзакция открыта дольше 5 минут | жёлтым, если больше 0 |

Над таблицей — фильтры «Все базы», «Все пользователи», «Все приложения», «Все состояния», флажок «Только ожидающие» (только ждущие блокировок) и поле «Фильтр…», которое ищет по PID, тексту запроса и адресу клиента.

### Таблица бэкендов {#backends-table}

По умолчанию сортировка по возрасту транзакции (сначала самые старые). Строки бэкендов, ждущих блокировку, подкрашены красным, простаивающих в транзакции — жёлтым.

| Столбец | Что показывает |
|---|---|
| «PID» | идентификатор процесса — его используют в `pg_cancel_backend` и `pg_terminate_backend` |
| «База данных», «Пользователь» | к какой базе и под какой ролью подключён бэкенд |
| «Приложение» | `application_name` (первые 24 символа) |
| «Клиент» | имя хоста клиента (если включён `log_hostname`) или IP-адрес; «локально» — адреса нет: подключение через Unix-сокет (или адрес скрыт от роли мониторинга) |
| «Состояние» | `active` (зелёный), `idle in transaction` (жёлтый), `idle` (серый), прочие (синий) |
| «Ожидание» | тип и имя события ожидания; ожидание блокировки выделено красным |
| «Возраст транзакции» | сколько открыта текущая транзакция; больше 5 минут выделяется жёлтым |
| «Возраст запроса» | сколько выполняется (или выполнялся последним) текущий запрос |
| «Подключён» | сколько существует подключение |
| «Запрос» | текст текущего или последнего запроса |

На что смотреть:

- **Долгие транзакции** (особенно в состоянии `idle in transaction`) удерживают снимок данных, мешают очистке (vacuum) и заморозке строк и могут держать блокировки. Ограничьте их параметром `idle_in_transaction_session_timeout`.
- **Много бэкендов в `idle`** при большом `max_connections` — признак того, что приложению нужен пул подключений.
- **Много ожидающих блокировок** — откройте [Блокировки](#locks), чтобы найти виновника.

```sql
-- завершать сеансы, простаивающие в транзакции дольше 10 минут
ALTER SYSTEM SET idle_in_transaction_session_timeout = '10min';
SELECT pg_reload_conf();
```

### Графики и типы процессов {#backends-charts}

Раздел «Динамика» содержит два графика:

- «Бэкенды по состояниям» — «Активные», «Простаивают», «Простой в транзакции» и «Ожидают» (ждущие блокировок);
- «Долгие транзакции (> 5 мин)» — число бэкендов с транзакцией дольше 5 минут.

Раздел «Типы бэкендов» (PostgreSQL 10 и новее) показывает число процессов каждого типа из `pg_stat_activity`, включая фоновые: `autovacuum worker`, `walsender`, `checkpointer` и другие.

## Блокировки {#locks}

Страница «Блокировки» (адрес `#/s/<id>/locks`) помогает найти, кто кого блокирует. В заголовке — общее число блокировок в отчёте и число невыданных.

### Цепочки блокировок {#blocking-chains}

Карточка «Цепочки блокировок» строится по `pg_blocking_pids()` для каждого бэкенда, который ждёт блокировку. Она показывает деревья:

- в корне — бэкенд с меткой «блокирует»: он удерживает блокировку и сам ничего не ждёт;
- под ним — бэкенды с меткой «ждёт», которые ждут его (и, ниже, те, кто ждёт уже их).

Для каждого бэкенда показаны PID, пользователь и база, состояние, сколько открыта транзакция и текст запроса. Если блокировки образуют цикл и корня нет, показываются все блокирующие бэкенды.

Если никто не ждёт, карточка показывает «Нет заблокированных бэкендов».

Типичная картина: в корне — бэкенд в состоянии `idle in transaction` с давно открытой транзакцией, а под ним — очередь запросов приложения или миграция с `ALTER TABLE`.

### Все блокировки {#all-locks}

Раздел «Все блокировки» — все строки `pg_locks` из отчёта. По умолчанию сначала невыданные; они подкрашены красным. «Фильтр…» ищет по PID, режиму, типу и имени отношения.

| Столбец | Что показывает |
|---|---|
| «PID» | процесс, который удерживает или ждёт блокировку |
| «База данных» | база блокируемого объекта |
| «Тип» | тип блокировки (`relation`, `transactionid`, `tuple`, `virtualxid` и т. д.) |
| «Режим» | режим блокировки (`AccessShareLock`, `RowExclusiveLock`, `AccessExclusiveLock` и т. д.) |
| «Отношение» | имя таблицы или индекса (`схема.имя`); если объекта нет в отчёте — `oid N` |
| «Выдана» | «выдана» или «ждёт» |
| «Ждёт» | сколько бэкенд ждёт эту блокировку (PostgreSQL 14 и новее) |

### Статистика ожиданий и взаимоблокировки {#lock-stats}

- **«Статистика ожиданий блокировок»** — накопительная статистика по типам блокировок из `pg_stat_lock`: «Ожидания», «Время ожидания», «Превышений fast-path». Раздел появляется только для PostgreSQL 19 и новее и версии pgmetrics, которая собирает `pg_stat_lock`.
- **Раздел «Динамика»**: график «Блокировки» («Удерживаются» — все блокировки в отчёте, «Не выданы» — ожидающие) и график «Взаимоблокировки» — число взаимоблокировок в минуту по всем базам.
- **«Взаимоблокировки в журнале»** — сообщения о взаимоблокировках из журнала PostgreSQL с временем и подробностями (какие процессы и запросы участвовали). Раздел появляется, если pgmetrics читает журнал (см. [Планы выполнения](#plans), шаг 2).

### Что делать с блокировкой {#lock-actions}

pgscope показывает снимок на момент отчёта и сам не завершает сеансы. Прежде чем действовать, проверьте текущее состояние на сервере:

```sql
-- кто сейчас блокирует бэкенд 12345
SELECT pid, usename, state, now() - xact_start AS xact_age, query
FROM pg_stat_activity
WHERE pid = ANY (pg_blocking_pids(12345));
```

Затем, если это допустимо для приложения:

```sql
-- отменить текущий запрос блокирующего бэкенда
SELECT pg_cancel_backend(23456);
-- завершить сеанс целиком: его транзакция будет откачена
SELECT pg_terminate_backend(23456);
```

Чтобы реже попадать в такие ситуации:

- задайте `idle_in_transaction_session_timeout`, чтобы брошенные транзакции не держали блокировки;
- выполняйте миграции с `SET lock_timeout = '5s'`, чтобы `ALTER TABLE` не выстраивал за собой очередь;
- включите `log_lock_waits = on`, чтобы ожидания дольше `deadlock_timeout` попадали в журнал — короткие блокировки между отчётами pgscope иначе не увидит.
