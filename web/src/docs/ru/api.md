# API

У pgscope три группы HTTP-методов: открытый API приёма отчётов, совместимый с pgdash CLI, метод сигнала для pgscope-agent и внутренний API, через который работает веб-интерфейс. На этой странице описаны форматы запросов, проверки, ограничения и коды ответов. Исходящие запросы pgscope (вебхуки уведомлений) описаны отдельно, в разделе [Формат вебхука](notifications.md#webhook).

## Общие правила {#conventions}

- **Адрес.** Пути отсчитываются от публичного адреса pgscope (`PGSCOPE_BASE_URL`), например `https://pgscope.example.com/api/v1/report`. pgdash CLI получает базовый адрес вместе с `/api/v1`: `--base-url=https://pgscope.example.com/api/v1`.
- **Формат.** Тела запросов и ответов — JSON в UTF-8.
- **Ошибки.** При ошибке pgscope отвечает кодом HTTP и телом `{"error": "текст"}`. Если заголовок `Accept-Language` начинается с `en`, текст будет на английском, иначе — на русском. pgscope-agent отправляет `Accept-Language: en`.
- **Сжатие.** Тело запроса к API приёма и к методу сигнала можно сжать gzip, указав заголовок `Content-Encoding: gzip`. Без этого заголовка тело читается как есть.
- **HTTPS** обеспечивает reverse proxy (см. [Reverse proxy и HTTPS](install.md#reverse-proxy)).

## API приёма отчётов {#ingest}

API совместим с командами pgdash CLI `report`, `report-pgbouncer` и `report-pgpool`, поэтому существующим заданиям достаточно указать `--base-url`. Про отправку отчётов на практике рассказано на странице [Отправка отчётов](collect.md).

### Методы {#ingest-endpoints}

| Метод и путь | Команда pgdash CLI | Что принимает | Поля с именами |
|---|---|---|---|
| `POST /api/v1/report` | `report` | отчёт сервера PostgreSQL | `server` |
| `POST /api/v1/reportpgbouncer` | `report-pgbouncer` | отчёт PgBouncer, привязанный к серверу PostgreSQL | `server`, `pgbouncer` |
| `POST /api/v1/reportpgpool` | `report-pgpool` | отчёт Pgpool-II | `pgpool` |

### Тело запроса {#ingest-body}

| Поле | Тип | Где нужно | Описание |
|---|---|---|---|
| `apikey` | строка | везде | API-ключ владельца со страницы «Профиль»: ровно 22 латинские буквы или цифры |
| `server` | строка | `report`, `reportpgbouncer` | имя сервера PostgreSQL в pgscope: символы `A–Z a–z 0–9 _ . -`, от 1 до 64 |
| `pgbouncer` | строка | `reportpgbouncer` | имя экземпляра PgBouncer, те же правила |
| `pgpool` | строка | `reportpgpool` | имя Pgpool в pgscope, те же правила |
| `data` | объект | везде | полный вывод `pgmetrics -f json` — JSON-объект, а не строка |

`apikey` должен идти в JSON-объекте раньше `data`: pgscope проверяет ключ до того, как читает отчёт. pgdash CLI и pgscope-agent уже отправляют его первым. Остальные поля верхнего уровня игнорируются. Скелет запроса (в настоящем запросе `data` — весь отчёт pgmetrics, здесь показано только поле, которое pgscope проверяет обязательно):

```json
{
  "apikey": "ABCDEFGHIJKLMNOPQRSTUV",
  "server": "prod-db-1",
  "data": { "meta": { "at": 1793008773 } }
}
```

Из отчёта pgscope использует:

- `data.meta.at` — время начала сбора в секундах Unix. Оно становится временем отчёта в pgscope: по нему строятся графики, выбирается последний отчёт и работает очистка. Поэтому часы хостов сбора должны быть синхронизированы.
- `data.pgbouncer` — обязателен для `reportpgbouncer` (pgmetrics, подключённый к служебной базе `pgbouncer`).
- `data.pgpool` — обязателен для `reportpgpool` (pgmetrics с флагом `--pgpool`).

### Обработка запроса {#ingest-processing}

pgscope проверяет запрос в таком порядке и останавливается на первой ошибке:

1. Распаковка gzip (если указан `Content-Encoding: gzip`) и разбор JSON. Тело читается потоком; до поля `data` допускается не больше 64 КиБ JSON.
2. Формат API-ключа, затем поиск ключа в базе для хранения. `apikey` должен стоять в теле раньше `data` (так отправляют pgdash CLI и pgscope-agent): ключ проверяется до чтения отчёта, поэтому запрос без действующего ключа получает ответ, не передав отчёт, и не занимает место для отчётов.
3. Имена в `server`, `pgbouncer`, `pgpool`.
4. Поле `data`: это отчёт pgmetrics с заполненным `meta.at`, а для PgBouncer и Pgpool — с соответствующим разделом.
5. Не сохраняется ли сейчас предыдущий отчёт того же источника.
6. Прошло ли `PGSCOPE_MIN_REPORT_INTERVAL` секунд (по умолчанию 60) с момента, когда был сохранён предыдущий отчёт того же источника.

Источник — это сочетание аккаунта, типа (PostgreSQL или Pgpool), имени сервера и имени PgBouncer. Отчёты сервера и каждого его PgBouncer учитываются раздельно. Время последнего отчёта хранится в памяти процесса и сбрасывается при перезапуске pgscope.

Одновременно pgscope читает и сохраняет отчёты не больше чем из 4 запросов; остальные ждут своей очереди, пока клиент не отключится. Весь запрос вместе с телом должен прийти за 10 минут, иначе pgscope закрывает соединение.

Затем pgscope сохраняет отчёт:

- Сервер ищется по аккаунту владельца ключа, типу и имени и создаётся автоматически, если его нет. Для `reportpgbouncer` так же находится или создаётся сервер PostgreSQL с именем из `server`, а отчёт сохраняется как отчёт его PgBouncer.
- Отчёт сохраняется целиком в сжатом виде, из него извлекаются временные ряды. Для отчётов самого сервера обновляются время последнего отчёта и сводка для списка серверов. Отчёты PgBouncer время последнего отчёта сервера не меняют.
- Для отчётов PostgreSQL (не PgBouncer и не Pgpool) после сохранения в фоне проверяются правила оповещений, а отчёт сравнивается с предыдущим для оповещений об изменениях. Ответ клиенту этой проверки не ждёт.

Успешный ответ — код 200 и тело `{}`.

### Ответы {#ingest-responses}

| Код | Сообщение | Причина |
|---|---|---|
| 200 | — (тело `{}`) | отчёт сохранён |
| 400 | «Не удалось распаковать тело запроса (gzip)» | указан `Content-Encoding: gzip`, но тело не сжато gzip |
| 400 | «Некорректное тело запроса» | тело не JSON нужной структуры, оборвано или до поля `data` в нём больше 64 КиБ |
| 400 | «Поле apikey должно идти в теле запроса до поля data» | `data` идёт раньше `apikey` или `apikey` нет |
| 413 | «Отчёт больше N МиБ — это предел PGSCOPE_MAX_REPORT_MB на сервере pgscope» | тело больше `PGSCOPE_MAX_REPORT_MB` (по умолчанию 256 МиБ) в переданном виде или после распаковки gzip |
| 401 | «Некорректный API-ключ» | ключ — не 22 латинские буквы или цифры |
| 403 | «Неизвестный API-ключ» | такого ключа нет, например его перегенерировали |
| 503 | «Хранилище временно недоступно» | база для хранения не ответила при проверке ключа |
| 400 | «Некорректное имя сервера» | имя пустое, длиннее 64 символов или содержит недопустимые символы |
| 400 | «Данные не являются JSON-отчётом pgmetrics» | `data` не разбирается как отчёт pgmetrics или в нём нет `meta.at` |
| 400 | «В отчёте нет данных PgBouncer», «В отчёте нет данных Pgpool» | отчёт снят не с PgBouncer или не с флагом `--pgpool` |
| 409 | «Предыдущий отчёт этого сервера ещё сохраняется» | тот же источник прислал отчёт, пока сохранялся предыдущий |
| 429 | «Отчёты отправляются слишком часто» | не прошло `PGSCOPE_MIN_REPORT_INTERVAL` секунд |
| 500 | «Не удалось сохранить отчёт» | ошибка записи в базу для хранения; подробности — в журнале pgscope (строка `store report …`) |

Размер тела ограничивает `PGSCOPE_MAX_REPORT_MB` (по умолчанию 256 МиБ, см. [Сводная таблица](config.md#reference)): один предел и для тела в переданном виде, и для него же после распаковки gzip. Превышение pgscope возвращает как 413 с JSON-телом и текстом из таблицы. 413 без такого тела (например, HTML-страницу) возвращает reverse proxy, у которого лимит тела меньше (у nginx по умолчанию 1 МиБ).

Запрос на неверный путь (например, когда в `--base-url` нет `/api/v1`) попадает в обработчик файлов веб-интерфейса и получает 404 с текстом `404 page not found`, а не JSON.

Что делать при каждом коде, описано в разделе [Ответы сервера](collect.md#responses) и на странице [Решение проблем и FAQ](troubleshooting.md#http-errors).

### Пример: отправка отчёта через curl {#curl-example}

Ручная отправка удобна для проверки связи и ключа: видны код ответа и текст ошибки.

```bash
# 1. Снять отчёт в файл
pgmetrics -w -f json -h DBHOST -U pgmon -o report.json db1 db2

# 2. Обернуть отчёт в тело запроса, сжать и отправить
KEY=ABCDEFGHIJKLMNOPQRSTUV   # API-ключ со страницы «Профиль»
{ printf '{"apikey":"%s","server":"%s","data":' "$KEY" prod-db-1; cat report.json; printf '}'; } \
  | gzip -c \
  | curl -sS -X POST https://pgscope.example.com/api/v1/report \
      -H 'Content-Type: application/json' -H 'Content-Encoding: gzip' \
      --data-binary @- -w '\nHTTP %{http_code}\n'
```

При успехе curl выведет `{}` и `HTTP 200`. Чтобы получить текст ошибки на английском, добавьте `-H 'Accept-Language: en'`. Для PgBouncer отправьте отчёт, снятый с базы `pgbouncer`, на `/api/v1/reportpgbouncer` и добавьте в тело поле `"pgbouncer":"pgb-1"`; для Pgpool — на `/api/v1/reportpgpool` с полем `"pgpool"` вместо `"server"`.

## Сигнал агента {#agent-heartbeat}

`POST /api/v1/agent` — метод, которым pgscope-agent раз в минуту сообщает о себе и о состоянии своих целей. По этим данным строится страница «Агенты» (см. [Страница «Агенты»](docker.md#agents-page)). Сами отчёты агент отправляет обычным API приёма.

```json
{
  "apikey": "ABCDEFGHIJKLMNOPQRSTUV",
  "agent": {
    "id": "prod-swarm/x7k2m9q4w1e8r5t3y6u0i2o4p",
    "cluster": "prod-swarm",
    "host": "node-1",
    "mode": "swarm",
    "version": "dev",
    "docker_version": "28.3.3",
    "autoconnect": false,
    "interval": 300
  },
  "targets": [
    {
      "name": "prod-swarm.billing_db",
      "kind": "postgres",
      "container": "billing_db.1.k2x9q8w7e6r5t4y3u2i1o0p9a",
      "container_id": "3f2a9c1b7d4e",
      "image": "postgres:17",
      "network": "billing_backend",
      "address": "10.0.5.12:5432",
      "status": "ok",
      "error": "",
      "last_ok": 1793008773,
      "last_attempt": 1793008773
    }
  ]
}
```

| Поле | Описание |
|---|---|
| `apikey` | API-ключ владельца, как в API приёма |
| `agent.id` | идентификатор агента `<кластер>/<хост или id узла>`: символы `A–Z a–z 0–9 _ . : / -`, от 1 до 128 |
| `agent.cluster`, `agent.host` | кластер (значение `PGSCOPE_AGENT_CLUSTER` или имя Docker-хоста) и имя хоста |
| `agent.mode` | `standalone` (отдельный хост) или `swarm` |
| `agent.version`, `agent.docker_version` | версии агента и Docker |
| `agent.autoconnect` | подключается ли агент к сетям баз сам |
| `agent.interval` | интервал сбора, секунд |
| `targets[]` | найденные контейнеры: имя сервера в pgscope, тип (`postgres` или `pgbouncer`), контейнер, образ, сеть, адрес, статус, текст ошибки, время последнего успешного сбора и последней попытки (секунды Unix) |
| `targets[].status` | `ok` («Работает»), `pending` («Ожидает первого сбора»), `unreachable` («Недоступна»), `auth_failed` («Ошибка аутентификации»), `error` («Ошибка») |

Как pgscope обрабатывает сигнал:

- Тело — не больше 4 МиБ в сети и после распаковки, можно сжать gzip.
- Запись об агенте хранится по паре «аккаунт владельца ключа + `agent.id`» и полностью заменяется каждым сигналом. Серверы сигнал не создаёт.
- Агент считается потерявшим связь («Нет связи с агентом»), если сигнала не было 3 минуты по часам базы для хранения.
- Ограничения частоты для сигналов нет.

| Код | Сообщение | Причина |
|---|---|---|
| 200 | — (тело `{}`) | сигнал принят |
| 400 | «Не удалось распаковать тело запроса (gzip)», «Некорректное тело запроса» | тело не gzip, не JSON нужной структуры или больше 4 МиБ (у сигнала превышение даёт 400, а не 413) |
| 401, 403, 503 | как в API приёма | ключ неверного формата, неизвестен или база для хранения недоступна |
| 400 | «Некорректный идентификатор агента» | `agent.id` пустой, длиннее 128 символов или с недопустимыми символами |
| 500 | «Внутренняя ошибка сервера» | ошибка записи в базу для хранения |

## Внутренний API интерфейса {#internal-api}

> [!WARNING]
> Это внутренний API веб-интерфейса. Он не документирован как стабильный и может меняться между версиями без предупреждения. Его можно использовать для разовых задач и скриптов, но учитывайте, что после обновления pgscope скрипты придётся проверить.

### Аутентификация и общие правила {#internal-auth}

- Вход: `POST /api/login` с телом `{"email": "…", "password": "…"}`. В ответ pgscope ставит cookie `pgscope_session` (см. [Сеансы и cookie](security.md#sessions)) и возвращает `{"ok": true}`. При неверных данных — 401 «Неверный адрес электронной почты или пароль». Ответ для неизвестного адреса занимает столько же времени, сколько для неверного пароля, поэтому по нему нельзя узнать, есть ли такая учётная запись.
- Все остальные запросы передают этот cookie.
- Запросы с любым методом HTTP, кроме GET, должны иметь заголовок `Content-Type: application/json`, иначе ответ 415 «Тело запроса должно быть в формате JSON». Это касается всех методов, требующих входа, и методов без входа `POST /api/signup`, `/api/login`, `/api/logout` и `/api/invite/{token}`. Это защита от CSRF; у методов со входом заголовок проверяется раньше сеанса. API приёма отчётов и сигнал агента этот заголовок не проверяют.
- Без действующего сеанса — 401 «Вход не выполнен».
- Тело, которое не разбирается как JSON нужной структуры, — 400 «Некорректный запрос». Непредвиденная ошибка базы для хранения — 500 «Внутренняя ошибка сервера», подробности в журнале pgscope.
- Для методов сервера `{id}` — числовой id, тот же, что в адресе страницы `#/s/{id}`. Если сервер не принадлежит пользователю и не открыт ему, ответ 404 «Сервер не найден». Если действие доступно только владельцу, а запрос сделал участник команды, ответ 403 «Это действие доступно только владельцу сервера».
- Тело запроса — не больше 1 МиБ.

### Методы {#internal-routes}

Без входа:

| Метод и путь | Назначение |
|---|---|
| `GET /api/signup` | открыта ли сейчас регистрация: `{"open": true}` или `{"open": false}`. Зависит от `PGSCOPE_SIGNUP` и, в режиме `first`, от того, есть ли в базе учётные записи |
| `POST /api/signup` | регистрация `{"email","password"}`; создаёт аккаунт владельца с API-ключом и сразу начинает сеанс. Если регистрация закрыта, — 403 «Регистрация новых аккаунтов отключена. Попросите администратора пригласить вас.» (эта проверка идёт раньше проверки адреса и пароля) |
| `POST /api/login` | вход |
| `POST /api/logout` | выход: удаляет сеанс из cookie |
| `GET /api/invite/{token}` | сведения о приглашении: email и имя сервера |
| `POST /api/invite/{token}` | принять приглашение `{"password"}`: создаёт аккаунт участника, открывает доступ и начинает сеанс. Работает при любом значении `PGSCOPE_SIGNUP`. Приглашение расходуется, только когда учётная запись создана: при ошибке оно остаётся действительным. Если на этот адрес уже есть учётная запись, — 409 «Учётная запись с этим адресом электронной почты уже существует. Войдите в неё и попросите владельца сервера открыть доступ этой учётной записи.» |

Пароль при регистрации, принятии приглашения и смене пароля должен содержать не меньше 8 символов и занимать не больше 72 байт в UTF-8, иначе ответ 400 «Пароль должен содержать от 8 символов и не более 72 байт (символ кириллицы занимает 2 байта)». Пароль только из кириллицы может быть не длиннее 36 букв.

Аккаунт:

| Метод и путь | Назначение |
|---|---|
| `GET /api/me` | текущий пользователь: id, email, API-ключ, признак участника команды, `PGSCOPE_BASE_URL`, включены ли AI-чат и SMTP, язык, часовой пояс `tz` (`null` — пояс браузера) и `min_report_interval` — значение `PGSCOPE_MIN_REPORT_INTERVAL` в секундах |
| `POST /api/me/apikey` | выпустить новый API-ключ (участнику команды — 403) |
| `POST /api/me/password` | сменить пароль `{"Old","New"}`. Все остальные сеансы пользователя завершаются, текущий остаётся |
| `PUT /api/me/lang` | сохранить язык `{"lang": "ru"}` или `{"lang": "en"}` |
| `PUT /api/me/tz` | сохранить часовой пояс интерфейса `{"tz": "Europe/Moscow"}` (имя из базы IANA); `{"tz": ""}` — снова пояс браузера. Неизвестное имя — 400 «Неизвестный часовой пояс» |
| `DELETE /api/me` | удалить аккаунт; у владельца — вместе со всеми его серверами |
| `GET /api/servers` | серверы пользователя и открытые ему: сводка, сработавшие оповещения, имена PgBouncer. В сводке `repl_lag_bytes` равен `null`, если репликация есть, но ни одно отставание не известно, и `0`, если репликации нет |
| `GET /api/agents` | агенты аккаунта с целями |
| `DELETE /api/agents?id=…` | удалить запись об агенте |

Сервер:

| Метод и путь | Назначение | Кому доступно |
|---|---|---|
| `GET /api/servers/{id}/report` | полный отчёт pgmetrics: последний или последний не позже `?at=` (секунды Unix); `?source=` — имя PgBouncer. Время отчёта — в заголовке `X-Report-At`, соседние отчёты того же источника — в `X-Report-Prev` и `X-Report-Next`, самый ранний сохранённый — в `X-Report-First` (передаётся и с ответом 404); заголовка нет, если такого отчёта нет. 404 «Нет отчёта на этот момент или раньше» — если с `?at=` отчёта не нашлось, а более поздние есть; «Отчётов пока нет» — если отчётов нет совсем; внутренняя ошибка — 500. Если клиент принимает gzip, отчёт отдаётся сжатым | владелец и участники |
| `GET /api/servers/{id}/reports` | время отчётов начиная с `?from=` (секунды Unix), не больше 2000, от новых к старым; `?source=` — имя PgBouncer | владелец и участники |
| `GET /api/servers/{id}/series` | временной ряд объекта: `?obj=` — ключ объекта (см. [Таблицы базы для хранения](data.md#tables)), `?fields=` — поля через запятую, `?from=` и `?to=` — секунды Unix (по умолчанию последние сутки) | владелец и участники |
| `GET /api/servers/{id}/baseline` | значение поля `?field=` у всех объектов с префиксом `?prefix=` (например, `tbl:`) из первого отчёта не раньше `?at=` | владелец и участники |
| `GET /api/servers/{id}/diagnostics` | диагностика и проверка конфигурации для последнего отчёта или отчёта `?at=`; если отчёта нет — 404 «Отчётов пока нет», а с `?at=` — 404 «Нет отчёта на этот момент или раньше» | владелец и участники |
| `GET /api/servers/{id}/alerts` | каталог метрик, правила, сработавшие оповещения, настройки оповещений об изменениях, каналы, последние 200 событий | владелец и участники |
| `POST /api/servers/{id}/alerts/rules` | добавить правило | владелец и участники |
| `DELETE /api/servers/{id}/alerts/rules/{rid}` | удалить правило | владелец и участники |
| `PUT /api/servers/{id}/changes` | настройки оповещений об изменениях `{"kinds": […], "size_pct": 20}` | владелец и участники |
| `POST /api/servers/{id}/notifiers` | добавить канал `{"scope","kind","target","lang"}` | владелец и участники |
| `DELETE /api/servers/{id}/notifiers/{nid}` | удалить канал | владелец и участники |
| `POST /api/servers/{id}/notifiers/{nid}/test` | отправить тестовое уведомление; при ошибке доставки — 502. Письмо, которое SMTP-сервер не принял за 30 секунд, считается недоставленным | владелец и участники |
| `GET /api/servers/{id}/shares` | владелец, участники и (только владельцу) приглашения со ссылками | владелец и участники |
| `POST /api/servers/{id}/shares` | пригласить `{"email"}`. Повторное приглашение того же адреса не создаёт второе, а обновляет первое и возвращает ту же ссылку | только владелец |
| `DELETE /api/servers/{id}/shares/{uid}` | отозвать доступ участника | только владелец |
| `DELETE /api/servers/{id}/invites/{token}` | отменить приглашение | только владелец |
| `DELETE /api/servers/{id}` | удалить сервер со всеми данными | только владелец |
| `POST /api/servers/{id}/chat` | вопрос AI-чату `{"messages": [{"role": "user", "content": "…"}]}`; если чат не настроен — 501 | владелец и участники |

Ряды запросов `q:…` в `GET /api/servers/{id}/series` суммируются по всем пользователям, выполнявшим запрос (`max_time` — максимум). В рядах отставания и удержания WAL (`repl:…`, `slot:…`, поля `lsn` и `standby_lag_bytes` сервера) точки нет, если pgmetrics не получил нужную позицию WAL (LSN).

Тело правила оповещения — объект с полями `metric` (идентификатор метрики из каталога `GET /api/servers/{id}/alerts`), `op` (`gt` или `lt`), `threshold` (порог в базовых единицах метрики: байты, секунды, миллисекунды для времени запросов, проценты или штуки), `param` (возраст транзакции в секундах, только для метрики `backends_long_xact`), `severity` (`warn` или `crit`), `match` (`all`, `contains`, `notcontains`, `startswith`, `endswith`, `exact`), `match_text` и `db_name`. Неизвестная метрика или недопустимое значение `op`, `severity` или `match` — 400 «Некорректное правило». Добавление и удаление правила сразу перепроверяют правила по последнему отчёту: если набор сработавших оповещений изменился, уведомления уходят сразу.

Тело канала уведомлений: `scope` (`alerts` — оповещения, `changes` — оповещения об изменениях), `kind` (`email`, `slack`, `pagerduty`, `victorops`, `xmatters`, `webhook`), `target` (для `email` — адреса через запятую, для `pagerduty` — ключ интеграции Events API v2, для остальных — URL со схемой `http` или `https`) и `lang` (`ru` или `en`, язык текстов уведомлений; если не указан, берётся язык запроса). Ошибки: 400 «Некорректный канал уведомлений» (неизвестные `kind` или `scope`, пустой `target`), «Адрес должен быть URL со схемой http или https», «Неподдерживаемый язык». В настройках оповещений об изменениях `size_pct` должен быть больше 0, а неизвестные значения в `kinds` отбрасываются.

### Пример {#internal-example}

```bash
BASE=https://pgscope.example.com

# вход: cookie сеанса сохраняется в файл jar (храните его как пароль)
read -rs PW
printf '{"email":"%s","password":"%s"}' dba@example.com "$PW" \
  | curl -sS -c jar -H 'Content-Type: application/json' --data-binary @- "$BASE/api/login"

# список серверов
curl -sS -b jar "$BASE/api/servers"

# последний полный отчёт сервера с id 42
curl -sS -b jar --compressed "$BASE/api/servers/42/report" -o prod-db-1.json
```

Если пароль содержит кавычки или обратную косую черту, экранируйте их по правилам JSON. Если cookie выдан с флагом `Secure`, curl отправит его обратно только по HTTPS.

## Исходящие уведомления {#outgoing}

pgscope сам отправляет POST-запросы в каналы уведомлений типа «Вебхук» (и в Slack, PagerDuty, VictorOps, xMatters в их форматах). Формат тела, заголовки, таймауты и повторы описаны в разделе [Формат вебхука](notifications.md#webhook), а содержимое уведомлений об изменениях — на странице [Оповещения об изменениях](change-alerts.md).
