pgscope — система мониторинга PostgreSQL, которую разворачивают на своём сервере. Она собирает данные о серверах
PostgreSQL, строит графики, ищет проблемы, присылает алерты и отвечает на вопросы о сервере через AI-чат.

## 1. Как это устроено

```
PostgreSQL ──► pgmetrics ──(JSON)──► pgdash CLI ──(HTTP, gzip)──► pgscope ──► веб-интерфейс
 PgBouncer ─┘                                                       │
 Pgpool ────┘                                                       └──► email / Slack / PagerDuty / вебхук
```

- **pgmetrics** — открытая утилита, которая за один запуск собирает сотни показателей сервера и выдаёт их в JSON.
- **pgdash CLI** — открытая утилита, которая отправляет этот JSON на сервер мониторинга.
- **pgscope** принимает отчёт, сохраняет его, извлекает временные ряды, проверяет правила алертов и сравнивает
  отчёт с предыдущим (оповещения об изменениях).

Каждый отчёт — снимок состояния на момент сбора. Чтобы появились графики, отчёты нужно отправлять регулярно,
обычно раз в 5 минут (cron).

## 2. Установка и запуск

### Требования

- Go 1.26+ и Node.js 20+ — только для сборки;
- PostgreSQL 13+ для хранения данных pgscope (можно тот же сервер, что и мониторится, но лучше отдельная база).

### Сборка

```bash
cd web && npm ci && npm run build && cd .. && go build -o pgscope .
```

Получается один файл `pgscope`, в который уже встроен веб-интерфейс.

### База для хранения

```bash
createdb pgscope
```

Таблицы pgscope создаёт сам при первом запуске.

### Запуск

```bash
PGSCOPE_DB=postgres://pgscope:secret@dbhost/pgscope PGSCOPE_BASE_URL=https://monitor.example.com ./pgscope
```

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `PGSCOPE_DB` | `postgres://localhost/pgscope` | строка подключения к базе, где pgscope хранит данные |
| `PGSCOPE_LISTEN` | `:8080` | адрес и порт веб-сервера |
| `PGSCOPE_BASE_URL` | `http://localhost:8080` | публичный адрес; из него строятся ссылки в алертах и приглашениях |
| `PGSCOPE_MIN_REPORT_INTERVAL` | `60` | минимальный интервал между отчётами одного сервера, секунд |
| `PGSCOPE_METRICS_RETENTION_DAYS` | `90` | сколько дней хранить графики и историю событий |
| `PGSCOPE_REPORT_RETENTION_DAYS` | `14` | сколько дней хранить полные отчёты |
| `PGSCOPE_SMTP_ADDR` | — | SMTP-сервер `host:port` для email-алертов и приглашений |
| `PGSCOPE_SMTP_USER`, `PGSCOPE_SMTP_PASS` | — | логин и пароль SMTP (если нужны) |
| `PGSCOPE_SMTP_FROM` | `pgscope@localhost` | адрес отправителя |
| `PGSCOPE_AI_KEY` | — | API-ключ Anthropic; включает AI-чат |
| `PGSCOPE_AI_MODEL` | `claude-opus-5-5` | модель для AI-чата |
| `PGSCOPE_AI_BASE_URL` | — | свой адрес Anthropic API (прокси или шлюз) |

### Работа как сервис (systemd)

```ini
# /etc/systemd/system/pgscope.service
[Unit]
Description=pgscope PostgreSQL monitoring
After=network.target

[Service]
ExecStart=/usr/local/bin/pgscope
Environment=PGSCOPE_DB=postgres://pgscope:secret@localhost/pgscope
Environment=PGSCOPE_BASE_URL=https://monitor.example.com
Environment=PGSCOPE_LISTEN=127.0.0.1:8080
Restart=always
User=pgscope

[Install]
WantedBy=multi-user.target
```

Снаружи pgscope лучше открывать через reverse proxy с HTTPS (nginx, Caddy), а сам сервис слушать на `127.0.0.1`.

## 3. Первый вход и API-ключ

1. Откройте адрес pgscope в браузере и нажмите **Регистрация** → укажите email и пароль (не короче 8 символов).
2. После входа откройте **Профиль** (ваш email внизу бокового меню).
3. В блоке **API-ключ** скопируйте ключ. Им pgdash CLI подписывает отчёты. Все серверы, отправленные с этим ключом,
   принадлежат вашему аккаунту.

На странице профиля также есть готовые команды для отправки отчётов с уже подставленными ключом и адресом.

Сессия в браузере живёт 30 дней.

## 4. Подготовка PostgreSQL

Базовые метрики собираются без настройки. Для полной картины включите следующее.

### Пользователь для мониторинга

```sql
CREATE ROLE pgmon LOGIN PASSWORD 'secret';
GRANT pg_monitor TO pgmon;
```

Роль `pg_monitor` даёт доступ ко всей статистике, включая тексты запросов в `pg_stat_statements`.

### Статистика запросов — pg_stat_statements (страница «Запросы»)

1. В `postgresql.conf`: `shared_preload_libraries = 'pg_stat_statements'` (через запятую, если там уже что-то есть).
2. Перезапустите PostgreSQL (обязательно, перечитать конфигурацию недостаточно).
3. В каждой отслеживаемой базе: `CREATE EXTENSION pg_stat_statements;`
4. Проверьте под пользователем мониторинга: `SELECT query FROM pg_stat_statements LIMIT 1;` —
   в колонке не должно быть `<insufficient privilege>`.

### Планы выполнения — auto_explain (планы на странице запроса)

```
shared_preload_libraries = 'pg_stat_statements,auto_explain'
auto_explain.log_min_duration = 2000     # логировать планы запросов дольше 2 секунд
auto_explain.log_analyze = on
auto_explain.log_timing = off            # off — меньше накладных расходов, время узлов не будет показано
auto_explain.log_format = json           # обязательно json — только он визуализируется деревом
```

Планы попадают в лог PostgreSQL, поэтому pgmetrics должен иметь доступ к логу (см. [раздел 5](#логи-планы-и-история-autovacuum)).

### Полезные настройки

| Настройка | Что даёт в pgscope |
|---|---|
| `track_io_timing = on` | время чтения и записи с диска у запросов и баз |
| `track_functions = pl` | статистика функций (Расширения и прочее → Функции) |
| `log_autovacuum_min_duration = 1000` | история autovacuum на странице «Очистка (vacuum)» |
| `log_lock_waits = on` | ожидания блокировок в логах |
| `log_checkpoints = on` | контекст для страницы «WAL и контрольные точки» |

## 5. Отправка отчётов

### Основная команда

```bash
pgmetrics --no-password -f json -h DBHOST -U pgmon db1 db2 \
  | pgdash -a APIKEY --base-url=https://monitor.example.com/api/v1 report prod-db-1
```

- `prod-db-1` — имя сервера в pgscope. Допустимы латинские буквы, цифры, `_ . -`, до 64 символов.
  Рекомендуется имя хоста. Сервер создаётся автоматически при первом отчёте.
- Перечислите все базы, которые нужно видеть, или используйте `--all-dbs`.
- `--base-url` обязателен: без него pgdash CLI отправит данные в облачный pgDash.

Пароль pgmetrics берёт из `~/.pgpass`, клиентских сертификатов, `PGPASSWORD` или настроек `pg_hba.conf`.
Флаг `--no-password` (`-w`) нужен, чтобы команда в cron не зависала на запросе пароля.

### Полезные флаги pgmetrics

| Флаг | Назначение |
|---|---|
| `--all-dbs` | собрать данные из всех пользовательских баз |
| `--statements-limit=N` | сколько самых тяжёлых запросов брать из pg_stat_statements (по умолчанию 100) |
| `--sql-length=N` | сколько символов текста запроса сохранять (по умолчанию 500) |
| `--log-file=PATH` / `--log-dir=DIR` | где читать лог PostgreSQL (планы, autovacuum, deadlocks, ошибки) |
| `--log-span=MIN` | за сколько последних минут читать лог (по умолчанию 5 — делайте равным интервалу cron) |
| `-c` / `-C` / `-a` / `-A` | включить или исключить схемы и таблицы по регулярному выражению |
| `--omit=...` | не собирать отдельные части, например `--omit=bloat` |
| `-S`, `--no-sizes` | не собирать размеры (ускоряет сбор на огромных базах) |
| `--aws-rds-dbid=ID` | метрики AWS CloudWatch и логи для RDS / Aurora |
| `--az-resource=ID` | метрики Azure Monitor |

### Полезные флаги pgdash CLI

| Флаг | Назначение |
|---|---|
| `-a KEY` | API-ключ из профиля |
| `--base-url=URL` | адрес pgscope с суффиксом `/api/v1` |
| `-i FILE` | взять JSON из файла вместо stdin |
| `--timeout=SEC`, `--retries=N` | таймаут и число повторов при сетевых ошибках и ответах 5xx |
| `--debug` | подробный вывод для диагностики |

### Автоматизация

Cron, раз в 5 минут:

```cron
*/5 * * * * pgmetrics -w -f json -h localhost -U pgmon --all-dbs | pgdash -a APIKEY --base-url=https://monitor.example.com/api/v1 report prod-db-1
```

Или цикл:

```bash
while true; do
  pgmetrics -w -f json -h localhost -U pgmon --all-dbs | pgdash -a APIKEY --base-url=https://monitor.example.com/api/v1 report prod-db-1
  sleep 300
done
```

Отчёты одного сервера должны приходить не чаще раза в `PGSCOPE_MIN_REPORT_INTERVAL` (по умолчанию 60 секунд),
иначе pgscope ответит 429. Не ставьте cron на каждую минуту: сбор занимает несколько секунд, и следующий запуск
может прийти раньше лимита.

### Логи, планы и история autovacuum

pgmetrics читает лог PostgreSQL, только если запущен **на том же хосте**, что и сервер, или если указан
`--log-file` / `--log-dir`. Для RDS и Aurora логи читаются через CloudWatch Logs при `--aws-rds-dbid`.
Без доступа к логу не будет планов выполнения, истории autovacuum, deadlocks из лога и страницы «Журнал».

Системные метрики (нагрузка, память, swap, свободное место на диске) тоже собираются только при запуске на хосте БД.

### AWS RDS и Aurora

```bash
export AWS_REGION=eu-central-1 AWS_ACCESS_KEY_ID=... AWS_SECRET_ACCESS_KEY=...
pgmetrics -w -f json -h mydb.xxxx.rds.amazonaws.com -U pgmon --aws-rds-dbid=mydb --log-span=5 db1 \
  | pgdash -a APIKEY --base-url=https://monitor.example.com/api/v1 report mydb
```

Вместо переменных окружения можно использовать IAM-роль EC2 или `~/.aws/credentials`. Метрики появятся
в пункте **Облачные метрики** раздела **Интеграции**. Учтите, что запросы к CloudWatch AWS тарифицирует отдельно.

### PgBouncer

Подключитесь к служебной базе `pgbouncer` админ-пользователем PgBouncer и отправьте отчёт с привязкой к серверу:

```bash
pgmetrics -h PGB_HOST -p 6432 -U pgb_admin -wfjson pgbouncer \
  | pgdash -a APIKEY --base-url=https://monitor.example.com/api/v1 report-pgbouncer prod-db-1 pgb-1
```

Здесь `prod-db-1` — сервер PostgreSQL, к которому относится пулер, а `pgb-1` — имя экземпляра PgBouncer.
Если пулеров несколько, отправляйте отчёт с каждого под своим именем, сразу после отчёта самого PostgreSQL.
После первого отчёта у сервера появится пункт меню **PgBouncer**.

### Pgpool-II

```bash
pgmetrics -h PGPOOL_HOST -p 9999 -U user -wfjson --pgpool postgres \
  | pgdash -a APIKEY --base-url=https://monitor.example.com/api/v1 report-pgpool pool-1
```

Pgpool появляется в списке серверов как отдельный объект со своим дашбордом.

### Ответы сервера

| Код | Значение | Что делать |
|---|---|---|
| 200 | отчёт принят | — |
| 400 | неверное тело, имя сервера или данные не от pgmetrics | проверьте имя и что pgmetrics запущен с `-f json` |
| 401 / 403 | ключ неверного формата или неизвестен | скопируйте ключ из профиля заново (после перегенерации старый не работает) |
| 409 | предыдущий отчёт этого сервера ещё сохраняется | повторите позже |
| 429 | отчёты приходят слишком часто | увеличьте интервал |
| 5xx | ошибка pgscope | pgdash CLI сам повторит запрос; смотрите лог pgscope |

## 6. Мониторинг баз в Docker и Docker Swarm

Если базы работают в контейнерах и доступны только во внутренних сетях Docker, cron с pgmetrics на каждую базу
неудобен. Вместо него на каждый Docker-хост ставится **pgscope-agent**. Агент сам находит контейнеры с базами,
подключается к ним по сети Docker, запускает pgmetrics и отправляет отчёты в pgscope. Сам pgscope к базам
не подключается, ему нужен только входящий HTTPS от агентов.

### Как работает агент

```
Docker-хост или узел Swarm
┌────────────────────────────────────────────────────────────────┐
│  pgscope-agent ──(Docker API, /var/run/docker.sock)──► dockerd │
│       │ pgmetrics по внутренней сети Docker                     │
│       ▼                                                        │
│  контейнеры PostgreSQL и PgBouncer с меткой pgscope.enable=true │
└────────────────────────────────────────────────────────────────┘
        │ HTTPS: /api/v1/report, /api/v1/reportpgbouncer, /api/v1/agent
        ▼
     pgscope ──► страница «Агенты», серверы, алерты
```

1. Каждые 30 секунд агент запрашивает у Docker запущенные контейнеры с меткой `pgscope.enable=true`.
2. Для каждой цели он выбирает сеть, через которую её видно (см. [Сети](#сети)), и при необходимости
   подключается к этой сети сам.
3. Перед сбором агент подключается к базе `postgres` (или к первой базе из метки `pgscope.dbs`) под ролью
   мониторинга с таймаутом 10 секунд. Так он отличает недоступную базу от неверного пароля и узнаёт список баз,
   к которым у роли есть доступ.
   pgmetrics получает этот список явно. С `--all-dbs` одна база с запретом подключения прервала бы весь отчёт.
4. Затем агент запускает pgmetrics и отправляет отчёт в pgscope. Сбор идёт раз в 5 минут, первые запуски
   распределены по интервалу, чтобы базы не опрашивались одновременно.
5. Раз в минуту агент сообщает pgscope о себе и о состоянии каждой цели. Это видно на странице **Агенты**.

Агент работает только с контейнерами своего хоста через локальный Docker API. Поэтому в Swarm он запускается
глобальным сервисом: по одной задаче на каждом узле, каждая обслуживает базы своего узла.

### Образы

Образы собираются из корня репозитория на машине с доступом в интернет:

```bash
docker build -t pgscope:latest .
docker build -f Dockerfile.agent -t pgscope-agent:latest .
```

В образ агента входят сам агент и pgmetrics, собранный из исходников той версии, которую использует pgscope.
Агенту не нужны внешние сервисы, только Docker API своего хоста, базы и pgscope.

Для закрытого контура перенесите образы файлами:

```bash
docker save pgscope-agent:latest | gzip > pgscope-agent.tar.gz     # на машине с интернетом
docker load -i pgscope-agent.tar.gz                                 # на каждом Docker-хосте и узле Swarm
```

Вместо этого можно положить образы во внутренний registry. Для самого pgscope таким же образом перенесите
`pgscope:latest` и `postgres:17-alpine`.

pgscope с базой для хранения можно запустить готовым compose-файлом `deploy/docker-compose.yml`:

```bash
cd deploy
printf 'PGSCOPE_DB_PASSWORD=%s\nPGSCOPE_BASE_URL=%s\n' 'пароль' 'https://pgscope.example.com' > .env
docker compose up -d
```

Данные лежат в томе `pgscope-data`. Остальные переменные из [раздела 2](#запуск) задаются в том же `.env`.

### Метки контейнеров с базами

Агент обслуживает только контейнеры с меткой `pgscope.enable=true`. Остальные метки необязательны.

| Метка | По умолчанию | Назначение |
|---|---|---|
| `pgscope.enable` | — | `true` — контейнер отслеживается |
| `pgscope.name` | см. ниже | имя сервера в pgscope, используется как есть |
| `pgscope.port` | `5432` | порт PostgreSQL или PgBouncer внутри контейнера |
| `pgscope.dbs` | все доступные | базы через запятую, например `app,billing` |
| `pgscope.network` | — | через какую сеть подключаться. Можно короткое имя сети из compose-файла или стека |
| `pgscope.sslmode` | `PGSCOPE_AGENT_SSLMODE` | `sslmode` для этой базы |
| `pgscope.kind` | `postgres` | `pgbouncer` для контейнера PgBouncer |
| `pgscope.server` | — | для PgBouncer: полное имя сервера PostgreSQL в pgscope, к которому относится пулер |
| `pgscope.user`, `pgscope.password-file` | роль агента | своя роль для этой цели. Файл с паролем — ещё один секрет агента, путь только внутри `/run/secrets/` |

Пример для Docker Compose:

```yaml
services:
  db:
    image: postgres:17
    command: ["postgres", "-c", "shared_preload_libraries=pg_stat_statements"]
    labels:
      pgscope.enable: "true"
    networks: [backend]
networks:
  backend:
    internal: true
```

В стеке Swarm метки пишутся в `labels:` сервиса, а **не** в `deploy.labels`. Только метки из `labels:` попадают
на контейнеры, которые видит агент.

**Имя сервера.** Если метки `pgscope.name` нет, имя строится так:

- контейнер Compose — `<проект>-<сервис>`, у второго и следующих экземпляров добавляется `-<номер>`;
- задача Swarm — имя сервиса (в стеке это `<стек>_<сервис>`), у реплик со второй добавляется `-<слот>`,
  у глобального сервиса `-<первые 6 символов id узла>`;
- остальные контейнеры — имя контейнера.

Если задан `PGSCOPE_AGENT_CLUSTER`, к построенному имени спереди добавляется `<кластер>.`, например
`prod.billing-db`. В Swarm кластер задаётся всегда. Символы вне `A-Z a-z 0-9 _ . -` заменяются на `-`, длина
не больше 64. Имя не меняется при перезапуске и пересоздании контейнера. Если переименовать проект, сервис или
стек, в pgscope появится новый сервер, а старый перестанет обновляться.

**PgBouncer.** Укажите `pgscope.kind: pgbouncer`, `pgscope.server: <имя сервера PostgreSQL>` и обычно
`pgscope.port: "6432"`. Агент подключается к служебной базе `pgbouncer`. Отчёт отправляется как
`report-pgbouncer`, а имя пулера строится по тем же правилам. Роль мониторинга должна быть в `stats_users`
PgBouncer и в его файле пользователей, либо задайте `pgscope.user` и `pgscope.password-file`.

### Роль мониторинга и секреты

Для всех баз используется одна роль `pgscope_monitor` с правами `pg_monitor`. Агент получает два Docker-секрета:

| Секрет | Путь в контейнере агента | Что внутри |
|---|---|---|
| `pgscope_api_key` | `/run/secrets/pgscope_api_key` | API-ключ из профиля pgscope |
| `pgscope_monitor_password` | `/run/secrets/pgscope_monitor_password` | пароль роли `pgscope_monitor` |

Пароль и ключ не попадают в переменные окружения контейнера, аргументы команд или логи. pgmetrics получает
пароль через `PGPASSWORD` только в своём окружении.

Роль создаёт скрипт `deploy/agent/bootstrap-monitor-role.sh`. Его запускают на каждом Docker-хосте и каждом
узле Swarm, где есть базы:

```bash
cd deploy/agent
./bootstrap-monitor-role.sh --dry-run                       # что будет сделано
./bootstrap-monitor-role.sh --password-file secrets/pgscope_monitor_password --with-pg-stat-statements
```

Для каждого запущенного контейнера с меткой `pgscope.enable=true` скрипт:

- создаёт роль `pgscope_monitor` с паролем из файла, а если она уже есть, задаёт ей этот пароль;
- выдаёт роли `pg_monitor`;
- с флагом `--with-pg-stat-statements` выполняет `CREATE EXTENSION IF NOT EXISTS pg_stat_statements` в каждой
  базе, кроме баз с `=` или `://` в имени (psql принял бы такое имя за строку подключения), и
  предупреждает, если библиотека не загружена.

SQL передаётся в `psql` внутри контейнера через stdin `docker exec -i`, поэтому пароль не виден в списке
процессов. На время своей сессии скрипт отключает журнал команд и учёт в `pg_stat_statements`, иначе пароль
попал бы в лог PostgreSQL и через `pg_stat_statements` в отчёты pgscope. Скрипт можно запускать повторно,
например после смены пароля. Реплики и контейнеры PgBouncer пропускаются, на реплики роль придёт с primary.
Можно указать контейнеры явно: `./bootstrap-monitor-role.sh db-1 db-2`.

Скрипт рассчитан на официальный образ `postgres`: `psql` подключается через локальный сокет от имени
`$POSTGRES_USER`, такое подключение в этом образе не требует пароля. Для других образов создайте роль вручную
в `psql` под суперпользователем:

```sql
CREATE ROLE pgscope_monitor LOGIN;
GRANT pg_monitor TO pgscope_monitor;
\password pgscope_monitor
```

`\password` хеширует пароль на клиенте, поэтому открытый пароль не попадёт ни в лог, ни в `pg_stat_statements`.

**pg_stat_statements в контейнере.** Библиотеку нужно загрузить при старте сервера: добавьте в compose-файл
или стек `command: ["postgres", "-c", "shared_preload_libraries=pg_stat_statements"]` и пересоздайте контейнер.
Если библиотек несколько, перечислите их через запятую. После этого выполните
`./bootstrap-monitor-role.sh --with-pg-stat-statements`.

### Сети

Для каждой цели агент ищет путь в таком порядке:

1. сеть из метки `pgscope.network`;
2. сеть, в которой агент уже состоит вместе с базой;
3. если `PGSCOPE_AGENT_AUTOCONNECT=true` (по умолчанию) и агент не в Swarm, он подключает свой контейнер
   к сети базы. Пользовательские сети bridge и overlay предпочтительнее стандартной `bridge`. Overlay-сеть
   должна быть `--attachable`. Когда сеть больше не нужна ни одной цели, агент из неё выходит;
4. если агент запущен с `network_mode: host`, он подключается по IP контейнера. Так работают только сети
   bridge, overlay с хоста недоступны;
5. иначе у цели будет статус **Недоступна** с причиной.

Сети `ingress`, `docker_gwbridge`, `host` и `none` не используются.

Внутренние сети (`internal: true`) подходят: подключение к ним не меняет маршрут агента до pgscope. Сеть
с опцией `com.docker.network.bridge.enable_icc=false` запрещает трафик между контейнерами, через неё агент
базу не увидит.

Для автоподключения агенту нужен `POST /networks/{id}/connect`, то есть право записи в Docker API. Если
давать его нельзя, задайте `PGSCOPE_AGENT_AUTOCONNECT=false` и перечислите сети в compose-файле агента
(пример закомментирован в `deploy/agent/docker-compose.yml`). Сеть `default` оставьте, через неё агент
выходит к pgscope.

**Swarm.** Задачу Swarm нельзя подключить к сети после запуска, поэтому в Swarm агент к сетям сам
не подключается. Перечислите все overlay-сети с базами в `deploy/agent/docker-stack.yml`:

```yaml
services:
  agent:
    networks: [default, billing_backend]
networks:
  default:
  billing_backend:
    external: true
```

Или добавьте сеть к уже запущенному сервису командой
`docker service update --network-add billing_backend pgscope-agent_agent`. Сервис при этом перезапустит все
задачи агента. Флаг `--attachable` для этого не нужен.

### Отдельный Docker-хост

```bash
docker load -i pgscope-agent.tar.gz          # если на хосте нет доступа к registry
cd deploy/agent
mkdir -p secrets
printf '%s' 'API-ключ'              > secrets/pgscope_api_key
printf '%s' 'пароль pgscope_monitor' > secrets/pgscope_monitor_password
chmod 600 secrets/*
echo 'PGSCOPE_URL=https://pgscope.example.com' > .env
./bootstrap-monitor-role.sh --with-pg-stat-statements
docker compose up -d
docker compose logs -f agent
```

API-ключ берётся в **Профиле**. На странице **Агенты**, пока агентов нет, показан compose-файл с уже
подставленными ключом и адресом.

Без `PGSCOPE_AGENT_CLUSTER` имена серверов строятся без префикса. Если на разных хостах есть проекты Compose
с одинаковыми именами, их отчёты попадут в один сервер pgscope. Тогда задайте каждому хосту свой
`PGSCOPE_AGENT_CLUSTER` в `.env`. Если хост входит в Swarm, переменная обязательна, как в стеке.

### Docker Swarm

На менеджере:

```bash
printf '%s' 'API-ключ'              | docker secret create pgscope_api_key -
printf '%s' 'пароль pgscope_monitor' | docker secret create pgscope_monitor_password -
# в deploy/agent/docker-stack.yml перечислите overlay-сети с базами (см. «Сети»)
PGSCOPE_URL=https://pgscope.example.com PGSCOPE_AGENT_CLUSTER=prod-swarm \
  docker stack deploy --resolve-image never -c deploy/agent/docker-stack.yml pgscope-agent
```

- `PGSCOPE_AGENT_CLUSTER` обязателен и одинаков для всех узлов одного кластера. Рабочие узлы не видят
  id кластера, а без общего имени имена серверов различались бы между узлами. Без этой переменной агент
  на узле Swarm завершится с ошибкой.
- Сервис глобальный: по одной задаче на узел, ограничения 1 CPU и 512 МБ памяти.
- Образ должен быть на каждом узле: `docker load` на каждом узле или внутренний registry.
  `--resolve-image never` не даёт `docker stack deploy` обращаться к registry за образом.
- `bootstrap-monitor-role.sh` запускается на каждом узле с базами, потому что `docker exec` работает только
  с контейнерами своего узла. Передайте ему файл с тем же паролем, что в секрете, и удалите файл после запуска.
- Логи: `docker service logs -f pgscope-agent_agent`.

### Переменные агента

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `PGSCOPE_URL` | — | адрес pgscope, например `https://pgscope.example.com` (обязательно) |
| `PGSCOPE_API_KEY_FILE` / `PGSCOPE_API_KEY` | `/run/secrets/pgscope_api_key` | API-ключ: файл или значение |
| `PGSCOPE_AGENT_CLUSTER` | — | имя кластера и префикс имён серверов. Если не задан, префикса нет, а кластером агента считается имя Docker-хоста. В Swarm обязательно |
| `PGSCOPE_AGENT_INTERVAL` | `300` | интервал сбора, секунд (или `5m`) |
| `PGSCOPE_AGENT_DISCOVERY_INTERVAL` | `30` | как часто искать контейнеры, секунд |
| `PGSCOPE_AGENT_PGUSER` | `pgscope_monitor` | роль мониторинга |
| `PGSCOPE_AGENT_PGPASSWORD_FILE` / `PGSCOPE_AGENT_PGPASSWORD` | `/run/secrets/pgscope_monitor_password` | пароль роли: файл или значение |
| `PGSCOPE_AGENT_SSLMODE` | `prefer` | `sslmode` подключений к базам |
| `PGSCOPE_AGENT_CONCURRENCY` | `4` | сколько баз собирать одновременно |
| `PGSCOPE_AGENT_TIMEOUT` | `120` | предел на один запуск pgmetrics, секунд |
| `PGSCOPE_AGENT_QUERY_TIMEOUT` | `30` | таймаут каждого запроса pgmetrics (`-t`), секунд. Запрос, не уложившийся в него, прерывает весь отчёт |
| `PGSCOPE_AGENT_PGMETRICS_ARGS` | — | дополнительные флаги pgmetrics, например `--omit=bloat` или `-S` |
| `PGSCOPE_AGENT_AUTOCONNECT` | `true` | подключаться к сетям баз самому (кроме Swarm) |
| `PGSCOPE_AGENT_LABEL_SELECTOR` | `pgscope.enable=true` | метка, по которой ищутся контейнеры |
| `PGSCOPE_AGENT_CONTAINER` | определяется сам | id или имя контейнера агента, если автоопределение не сработало |
| `DOCKER_HOST` | `unix:///var/run/docker.sock` | Docker API: сокет или `tcp://host:port` (socket proxy) |
| `PGMETRICS` | `pgmetrics` | путь к pgmetrics |
| `SSL_CERT_FILE` | — | PEM-файл с сертификатом внутреннего CA, если HTTPS pgscope подписан им (смонтируйте файл в контейнер агента) |

Интервал сбора не должен быть меньше `PGSCOPE_MIN_REPORT_INTERVAL` сервера pgscope (по умолчанию 60 секунд).
Иначе pgscope ответит 429, и агент пропустит отчёт до следующего интервала.

### Страница «Агенты»

Пункт **Агенты** в верхней части бокового меню. Для каждого агента показаны кластер, хост, режим (отдельный
хост или Swarm), версии агента и Docker, время последнего сигнала и таблица целей: имя (ссылка на сервер,
если отчёты уже пришли), контейнер, образ, сеть, адрес, статус, текст ошибки и время последнего успешного
сбора. Если агент молчит дольше 3 минут, показывается предупреждение и кнопка удаления. Удаление только убирает
запись. Если агент на самом деле работает, он появится снова со следующим сигналом.

### Решение проблем

| Статус цели | Что значит | Что делать |
|---|---|---|
| **Ожидает первого сбора** | контейнер найден, первый сбор ещё не прошёл | подождите до одного интервала сбора: первые запуски распределены по интервалу |
| **Недоступна** | нет общей сети или к базе нет TCP-подключения | прочитайте причину в колонке ошибки: добавьте сеть в стек агента или `--network-add`, укажите `pgscope.network`, проверьте `pgscope.port` и что PostgreSQL слушает не только `localhost` (`listen_addresses`) |
| **Ошибка аутентификации** | `password authentication failed` или `no pg_hba.conf entry` | запустите `bootstrap-monitor-role.sh` с тем же файлом пароля, что в секрете агента. Проверьте, что `pg_hba.conf` пускает `pgscope_monitor` из сети агента. Для PgBouncer проверьте `stats_users` и файл пользователей |
| **Ошибка** | pgmetrics завершился с ошибкой или pgscope не принял отчёт | текст в колонке ошибки. При `canceling statement due to statement timeout` увеличьте `PGSCOPE_AGENT_QUERY_TIMEOUT` или добавьте `--omit=bloat` / `-S` в `PGSCOPE_AGENT_PGMETRICS_ARGS` |

**Агента нет на странице «Агенты».** Посмотрите лог агента (`docker compose logs agent` или
`docker service logs pgscope-agent_agent`). Проверьте, что `PGSCOPE_URL` доступен из контейнера и что ключ
в секрете совпадает с ключом из профиля. При неверном ключе агент пишет в лог `HTTP 403` и продолжает работу.

**`docker compose down` проекта с базой пишет `Resource is still in use` про его сеть.** Агент ещё подключён
к этой сети, поэтому Compose её не удаляет. Это безопасно: следующий `docker compose up` использует ту же сеть,
а агент выйдет из неё, когда база исчезнет.

**`docker compose up` проекта с базой падает с `error while removing network … has active endpoints`, контейнер
базы остаётся остановленным.** Так бывает после изменения настроек сети в compose-файле: Compose пересоздаёт
сеть, а агент к ней подключён. Отключите агента и повторите:

```bash
docker network disconnect <сеть> <контейнер агента>
docker compose up -d
```

Чтобы это не повторялось, создайте сеть баз один раз командой `docker network create` и объявите её
в проектах как `external: true`, тогда Compose не будет её удалять. Другой вариант —
`PGSCOPE_AGENT_AUTOCONNECT=false` и сети в compose-файле агента. Тогда подключение видно в конфигурации:
перед изменением сети агента останавливают (`docker compose stop agent`), а после запускают заново
(`docker compose up -d --force-recreate agent`).

Агент выходит из подключённых им сетей, когда они больше не нужны, и при штатной остановке (SIGTERM).
Список этих сетей он хранит в своём контейнере (`/var/tmp/pgscope-agent-joined.json`), поэтому и после
аварийного перезапуска (OOM, `kill -9`, сбой питания хоста) выходит из них сам. Если корневая файловая система
агента доступна только для чтения (`read_only: true`), агент пишет об этом в лог, и после такой аварии его нужно
отключить вручную: `docker network disconnect <сеть> <контейнер агента>`.

### Безопасность

- Доступ к `/var/run/docker.sock` равен root на хосте. Поэтому агент работает от root и не содержит ничего,
  кроме себя и pgmetrics. Монтирование сокета с `:ro` API не ограничивает.
- Доступ можно сузить через [docker-socket-proxy](https://github.com/Tecnativa/docker-socket-proxy). Реальное
  ограничение даёт только `POST=0`: в этом прокси `POST=1` вместе с `CONTAINERS=1` разрешает и
  `POST /containers/create` и `/start`, а это тот же root. С `POST=0` автоподключение невозможно, поэтому
  задайте `PGSCOPE_AGENT_AUTOCONNECT=false` и объявите сети статически. Дополнение к
  `deploy/agent/docker-compose.yml` (образ прокси в закрытый контур тоже переносится через `docker save`):

  ```yaml
  services:
    socket-proxy:
      image: tecnativa/docker-socket-proxy:0.3.0
      restart: unless-stopped
      environment: {CONTAINERS: 1, NETWORKS: 1, INFO: 1, POST: 0}
      volumes: ["/var/run/docker.sock:/var/run/docker.sock:ro"]
      networks: [docker-api]
    agent:
      # монтирование docker.sock у агента в deploy/agent/docker-compose.yml удалите
      environment:
        DOCKER_HOST: tcp://socket-proxy:2375
        PGSCOPE_AGENT_AUTOCONNECT: "false"
      networks: [default, docker-api, billing_backend]
  networks:
    docker-api:
      internal: true
    billing_backend:
      external: true
  ```

- Агент предъявляет пароль `pgscope_monitor` каждому контейнеру с меткой `pgscope.enable=true`. Кто может
  запускать контейнеры с метками, тот может получить этот пароль, поэтому у роли не должно быть прав сверх
  `pg_monitor`. Метка `pgscope.password-file` читает только секреты агента в `/run/secrets/`.
- Роль `pgscope_monitor` только читает статистику. Учтите, что через `pg_monitor` видны тексты запросов
  из `pg_stat_statements`, а в них могут быть литералы с данными.
- `sslmode=prefer` шифрует соединение, если сервер поддерживает TLS, но сертификат не проверяет. Для проверки
  задайте `PGSCOPE_AGENT_SSLMODE` или метку `pgscope.sslmode`.

## 7. Интерфейс: навигация, графики, таблицы

### Боковое меню

- **Серверы** — все ваши серверы и серверы, которыми с вами поделились.
- **Инспектор** — сводка по всему парку.
- **Агенты** — агенты сбора в Docker и Swarm и состояние их целей (см. [раздел 6](#страница-агенты)).
- После выбора сервера появляются переключатель серверов и его разделы:
  - **Мониторинг** — Обзор, Диагностика, AI-чат;
  - **Активность** — Запросы, Бэкенды, Блокировки;
  - **Объекты** — Базы данных, Таблицы, Индексы, Управление индексами, Топ-k, Табличные пространства, Расширения и прочее, Роли;
  - **Сервер** — Репликация, WAL и контрольные точки, Очистка (vacuum), Конфигурация, Система, Журнал;
  - **Интеграции** — Облачные метрики и PgBouncer (появляются, когда есть данные);
  - **Оповещения и команда** — Оповещения, Оповещения об изменениях, Команда и настройки.
- Внизу — профиль, переключение светлой и тёмной темы, переключатель языка **Русский / English**, выход.

На узких экранах меню открывается кнопкой ☰ слева вверху.

### Верхняя панель сервера

- **Индикатор и время отчёта.** Зелёная точка — отчёт свежий, жёлтая — последнему отчёту больше 15 минут
  (сбор, вероятно, остановился).
- **Последний отчёт / выбор отчёта.** По умолчанию показывается последний отчёт, и данные обновляются каждую минуту.
  В списке можно выбрать любой отчёт за последние 30 дней (в пределах срока хранения), чтобы увидеть, что
  происходило в прошлом: какие были запросы, блокировки, бэкенды. Пока выбран прошлый отчёт, автообновление
  выключено, а графики заканчиваются в момент этого отчёта.
- **1ч / 6ч / 24ч / 7д / 30д** — период графиков; запоминается в браузере.
- **⟳** — обновить данные сейчас. **Иконка робота** — открыть AI-чат.

### Язык интерфейса

Интерфейс доступен на русском и английском. Переключатель **Русский / English** есть внизу бокового меню,
на страницах входа и регистрации и в профиле (карточка **Язык**). Язык меняется сразу, без перезагрузки страницы.
Вместе с ним меняются формат чисел, дат и единиц (например, «1,5 ГиБ» ↔ «1.5 GiB»).

- Выбор, сделанный после входа, сохраняется в профиле и применяется на любом устройстве.
- До входа язык берётся из прошлого выбора в этом браузере, а если его нет — из языка браузера.
- На языке интерфейса приходят и данные с сервера: диагностика, рекомендации, тексты оповещений и истории
  изменений, ошибки, ответы AI-чата. История хранится в нейтральном виде, поэтому каждый участник команды видит её
  на своём языке.
- Язык уведомлений задаётся отдельно для каждого канала (см. [раздел 10](#10-оповещения-алерты)).
- Письма о совместном доступе и приглашения уходят на языке того, кто приглашает.

### Графики

- Наведите курсор на график, чтобы увидеть значения в конкретный момент. Без наведения легенда показывает
  последние значения.
- Счётчики PostgreSQL накопительные, поэтому графики «транзакций», «строк», «записи WAL» показывают скорость:
  изменение между соседними отчётами, делённое на время (в секунду, если не указано иное).
- Отношения вроде доли попаданий в кеш и среднего времени запроса считаются по интервалу между отчётами, а не за всё время.
- Разрыв линии означает, что в этот момент значения не было: отчёт не пришёл, счётчик сбросился или pgmetrics
  не смог прочитать размер из-за блокировки.

### Таблицы

- Поле **Фильтр…** ищет по тексту строки; выпадающие списки рядом фильтруют по базе, пользователю и т. д.
- Если в строке есть ссылка, клик открывает детальную страницу объекта.
- При большом числе строк внизу появляются страницы.

## 9. Страницы сервера

### Обзор

- Карточки: версия, время работы, бэкенды к `max_connections`, число и размер баз, общие попадания в кеш, активные оповещения.
- **Кластер** — системный идентификатор, линия времени, последняя контрольная точка, LSN, использование XID, очередь
  уведомлений (LISTEN/NOTIFY), время перечитывания конфигурации, каталог данных.
- **Активные оповещения** — сработавшие правила.
- Графики: транзакции, бэкенды по состояниям, строки, попадания в кеш, генерация WAL, размер баз,
  временные файлы, диапазон XID, а при наличии системных метрик — нагрузка и память.
- Таблица баз со ссылками на детальные страницы.

### Диагностика

Автоматическая проверка выбранного отчёта. Вкладка **Проблемы** — найденные проблемы с уровнем
(Критично / Предупреждения / Советы), объяснением, списком объектов (**Подробнее**) и кнопкой **Открыть** для перехода
к нужной странице. Проверяется в том числе:

- угроза переполнения счётчика транзакций (wraparound);
- неактивные слоты репликации, отстающие и приостановленные реплики, ошибки подписок;
- сбои архивации WAL, очередь на архивацию, слишком много WAL-файлов, слишком частые контрольные точки;
- заполнение `max_connections`, долгие транзакции (>5 мин), бездействие в транзакции (idle in transaction, >1 мин), ожидание блокировок,
  переполнение очереди уведомлений;
- ошибки контрольных сумм, низкая доля попаданий в кеш (<90 %), много откатов, много временных файлов, взаимоблокировки;
- раздутые таблицы и индексы, много мёртвых строк, таблицы без vacuum/analyze, большие таблицы
  с последовательными сканированиями, таблицы без первичного или уникального ключа;
- неиспользуемые и дублирующиеся индексы;
- расширения с доступным обновлением, отключённые триггеры;
- диск заполнен больше 80 / 90 %;
- неподдерживаемая версия PostgreSQL, лишние суперпользователи, отсутствие pg_stat_statements.

Вкладка **Проверка конфигурации** — рекомендации по настройкам в четырёх областях:
Безопасность, Сохранность данных, Производительность, Надёжность (например, `ssl`, `password_encryption`, `fsync`,
`shared_buffers`, `work_mem`, `random_page_cost`, `autovacuum`, `idle_in_transaction_session_timeout`,
`max_slot_wal_keep_size`).

### AI-чат

Чат о сервере на любом языке. Ответы строятся на данных последнего отчёта: настройки, базы, крупнейшие таблицы
и индексы, тяжёлые запросы, бэкенды, блокировки, репликация, результаты диагностики. Работает, если задан
`PGSCOPE_AI_KEY`.

- Кнопки-подсказки дают типовые вопросы: общий обзор здоровья, что оптимизировать, какие индексы добавить
  или удалить, успевает ли autovacuum, разбор конфигурации.
- **Enter** отправляет, **Shift+Enter** переносит строку.
- Переписка хранится до закрытия вкладки браузера; **Новый диалог** начинает новую.
- Ответы AI нужно проверять перед применением.

### Запросы

Запросы из pg_stat_statements (по умолчанию 100 самых тяжёлых): текст, база, пользователь, число вызовов,
суммарное, среднее и максимальное время, строк на вызов, попадания в кеш, объём временных файлов. Полоска в столбце
**Общее время** показывает долю запроса в общем времени.

Клик по запросу открывает **страницу запроса**:

- полный текст с кнопкой копирования и ключевые показатели;
- **Советы** — низкая доля попаданий в кеш, временные файлы (поднять `work_mem` или добавить индекс),
  слишком много строк на вызов, большой разброс времени, преобладание I/O, долгое планирование
  (подготовленные операторы), накладные расходы JIT, очень частые вызовы, много WAL, а также проблемы из планов;
- графики: вызовы, среднее время по интервалам, строки, блоки из кеша и с диска, затраченное время, временные блоки;
- **Статистика** — все поля pg_stat_statements;
- **Планы выполнения** — планы из auto_explain, найденные для этого запроса (последние три, остальные по кнопке
  **Показать все планы**). План показан деревом: тип узла, таблица или индекс, фактические и ожидаемые строки, стоимость,
  время (если `log_timing = on`), условия. Полоса под узлом — его доля во времени (или в стоимости, если время
  не собиралось): красная больше 50 %, жёлтая больше 20 %. Под узлами выводятся предупреждения — неверная оценка
  строк, Seq Scan с отбрасыванием многих строк, сортировка на диске, многопроходный hash, частые nested loop,
  heap fetches в index-only scan.

### Бэкенды

Все подключения на момент отчёта: карточки (всего, активные, простаивают, простой в транзакции, ждут блокировок,
транзакции дольше 5 минут), фильтры по базе, пользователю, приложению и состоянию, флажок **Только ожидающие**.
Таблица показывает PID, клиента, состояние, событие ожидания, возраст транзакции, запроса и подключения, текст
запроса. Ожидающие блокировок подсвечены красным, простой в транзакции — жёлтым. Ниже — графики и разбивка
по типам процессов.

### Блокировки

- **Цепочки блокировок** — дерево блокировок: кто блокирует (корень) и кто ждёт за ним, с пользователем, базой,
  возрастом транзакции и текстом запроса. Здесь видно, какой сеанс нужно завершить, чтобы освободить остальных.
- **Все блокировки** — все блокировки с режимом, отношением (имя таблицы или индекса) и временем ожидания.
- Статистика ожиданий блокировок (PostgreSQL 18+), графики и взаимоблокировки из журнала.

### Базы данных

Список баз: размер, бэкенды, доля фиксаций, попадания в кеш, возраст XID относительно `autovacuum_freeze_max_age`,
транзакции, временные файлы, взаимоблокировки, конфликты. Страница базы показывает подробную статистику, графики,
крупнейшие таблицы, расширения (с отметкой доступного обновления) и отключённые триггеры.

### Таблицы

Все таблицы: размер, раздувание (bloat), живые и мёртвые строки, последовательные и индексные сканирования,
попадания в кеш, время последней очистки и анализа. Страница таблицы:

- карточки размера, раздувания, строк, доли мёртвых строк, попаданий в кеш, доли HOT-обновлений;
- **Очистка и анализ** — последние ручные и автоматические запуски, счётчики, изменения с последнего analyze,
  возраст XID;
- **Активность** — сканирования, изменения строк, блоки кучи / индексов / TOAST, вид таблицы, секционирование;
- графики размера, строк, изменений, сканирований, попаданий в кеш, частоты autovacuum;
- индексы таблицы и, для секционированной таблицы, её секции.

### Индексы

Все индексы: таблица, тип (btree, gin…), размер, раздувание, число сканирований (0 подсвечен), попадания в кеш,
время последнего использования (PostgreSQL 16+). Страница индекса — определение, показатели, готовый SQL
для `REINDEX ... CONCURRENTLY` и `DROP INDEX CONCURRENTLY`, графики.

### Управление индексами

Три вкладки для чистки индексов. В каждой отметьте индексы флажками — ниже появится готовый SQL,
сгруппированный по базам (с `\c база` для psql):

- **Неиспользуемые** — неуникальные индексы, которые не использовались. Период: с последнего сброса статистики или за
  последние 1 / 7 / 30 / 90 дней (сравнивается с отчётом начала периода, поэтому нужна история такой длины).
  SQL: `DROP INDEX CONCURRENTLY`.
- **Раздутые** — раздутые индексы. SQL: `REINDEX INDEX CONCURRENTLY`.
- **Дубликаты** — индексы с одинаковым определением на одной таблице; предлагается удалить лишние.

Перед удалением индекса на реплике или в другом окружении убедитесь, что он не нужен и там: статистика
использования своя у каждого сервера.

### Топ-k

Рейтинги объектов: выберите тип (Таблицы, Индексы, Схемы), критерий и размер списка (Топ-10 / Топ-25 / Топ-50).

- Таблицы: размер, живые и мёртвые строки, раздувание, последовательные сканирования, число записей,
  **Рост размера** и **Рост числа строк** за 1, 7 или 30 дней.
- Индексы: размер, раздувание, сканирования, рост размера.
- Схемы: размер таблиц, размер индексов, строки, число таблиц и индексов.

### Табличные пространства

Карточки табличных пространств: расположение, размер, заполнение диска и inode (если pgmetrics запущен на
хосте). Клик по карточке выбирает пространство: ниже его графики и список таблиц и индексов в нём.
Отметьте объекты, выберите действие **перенести в** + целевое пространство или **удалить** — получите SQL
(`ALTER TABLE/INDEX ... SET TABLESPACE` или `DROP`). Учтите, что перенос таблицы её блокирует.

### Расширения и прочее

- **Расширения** — расширения по базам с установленной и доступной версией; обновление делается
  `ALTER EXTENSION имя UPDATE` в нужной базе.
- **Функции** — статистика пользовательских функций (нужен `track_functions`).
- **Последовательности** — обращения к последовательностям.
- **Отключённые триггеры** — отключённые триггеры.

### Роли

Роли и их атрибуты: вход (login), суперпользователь, создание БД, создание ролей, репликация, обход RLS, лимит подключений,
срок действия пароля, членство в группах.

### Репликация

- На ведущем сервере (метка **Ведущий**): реплики с состоянием, режимом sync/async и лагами записи, сброса и применения (в байтах
  и времени); графики лага для выбранной реплики.
- На реплике (метка **Реплика**): LSN получения и применения, лаг, время последней применённой транзакции, пауза
  воспроизведения, состояние приёмника WAL и графики.
- **Слоты репликации** — тип, плагин, активность, `wal_status`, сколько WAL удерживает слот, график
  удерживаемого WAL. Неактивный слот, удерживающий много WAL, — частая причина переполнения диска.
- Публикации и подписки логической репликации (с ошибками применения и синхронизации).

### WAL и контрольные точки

Число WAL-файлов, файлы в очереди архивации, состояние архивации (последний успешный и неудачный файл,
`archive_command`), статистика контрольных точек и фоновой записи, `pg_stat_wal`, графики (генерация WAL,
контрольные точки по расписанию и по запросу, записанные буферы, архивация) и `pg_stat_io` (PostgreSQL 16+).
Если контрольные точки «По запросу» преобладают над плановыми («По расписанию»), стоит увеличить `max_wal_size`.

### Очистка (vacuum)

- **Выполняется сейчас** — текущие VACUUM, ANALYZE, CREATE INDEX, CLUSTER / VACUUM FULL, COPY, pg_basebackup с прогрессом.
- **Возраст XID по базам данных** — шкала до wraparound и доля от `autovacuum_freeze_max_age`.
- **Таблицы с наибольшим числом мёртвых строк** и **Самые старые таблицы (возраст замороженного XID)**.
- **История autovacuum (из журнала)** — запуски autovacuum из лога (нужен `log_autovacuum_min_duration`).
- Все настройки `autovacuum*` и `vacuum_*`.

### Конфигурация

- **Настройки** — все параметры с понятными единицами (МиБ, мс), значением по умолчанию, источником
  и отметкой **нужен перезапуск** (изменение ждёт перезапуска). Флажок **Только изменённые** оставляет
  только изменённые.
- **Проверка конфигурации** — те же рекомендации, что в разделе «Диагностика», в виде таблицы.

### Система

Модель CPU, число ядер, нагрузка (в том числе на ядро), разбивка памяти (занято / буферы / кеш / свободно), swap,
графики и заполнение дисков по табличным пространствам. Данные есть, только если pgmetrics запускается на хосте БД.

### Журнал

Записи журнала PostgreSQL за период сбора (`--log-span`) с фильтром по уровню (LOG, WARNING, ERROR, FATAL…)
и поиском.

### Облачные метрики

Для AWS RDS / Aurora — метрики CloudWatch (CPU, память, IOPS, хранилище и др.) с графиками, а при включённом
Enhanced Monitoring — его данные. Для Azure — метрики Azure Monitor.

### PgBouncer

Для каждого экземпляра (переключатель справа вверху): клиентские подключения (активные, ожидающие, простаивающие),
максимальное и среднее ожидание клиентов, серверные подключения, графики; таблица upstream-баз (состояние
**приостановлена** / **отключена**); трафик по базам (транзакции, запросы, среднее время, байты) с графиками; пулы с ожидающими
клиентами и графиками. Если клиенты ждут, пул мал (`default_pool_size`) или сервер перегружен.

### Pgpool

Бэкенды (узел, статус up / down, роль, вес балансировки, select и запись, ошибки, задержка репликации),
статистика проверок состояния (health check: успешность, сбои, длительность), кеш запросов (доля попаданий, записи,
объём), графики по кешу и по выбранному узлу.

## 10. Оповещения (алерты)

Раздел **Оповещения** сервера. Правила проверяются при каждом новом отчёте, а также сразу после добавления или
удаления правила.

### Вкладки

- **Сработавшие** — что сработало сейчас: важность, правило, объект, значение (для запросов — текст). Клик ведёт
  к объекту.
- **Правила** — создание и список правил по уровням.
- **Уведомления** — куда отправлять уведомления.
- **История** — история изменений набора сработавших алертов.

### Создание правила

1. **Уровень**: Сервер, База данных, Таблица, Табличное пространство, Запрос.
2. **Метрика** — метрика (список ниже).
3. **Условие** — *больше* или *меньше*, **Порог** — пороговое значение, **Единица** — единица измерения
   (МиБ / ГиБ / КиБ / ТиБ для размеров; секунды, минуты, часы, дни для времени; % для процентов).
4. **Важность** — Предупреждение или Критично.
5. Для уровней кроме «Сервер» — к каким объектам применять (поле **Применять к …**): *все объекты* или по имени
   (*имя содержит*, *имя не содержит*, *имя начинается с*, *имя заканчивается на*, *имя равно*). Имя таблицы имеет
   вид `база.схема.таблица`. Для уровней «Таблица» и «Запрос» можно ограничить правило одной базой
   (поле **Только в базе (необязательно)**).
6. **Добавить правило**.

Для каждого подходящего объекта создаётся отдельный алерт: правило «Размер таблицы больше 10 ГиБ» при трёх
больших таблицах даст три алерта.

### Метрики

| Уровень | Метрика | Единицы |
|---|---|---|
| Сервер | Диапазон XID — сколько XID использовано (риск wraparound при ~2 млрд) | число |
| Сервер | Время с последней контрольной точки | время |
| Сервер | Число неактивных слотов репликации | число |
| Сервер | Отставание репликации по записи (write) / по сбросу (flush) / по воспроизведению (replay) на ведущем (для каждой реплики) | байты |
| Сервер | Отставание воспроизведения на реплике | байты или время |
| Сервер | Число файлов WAL / Число файлов WAL, готовых к архивации | число |
| Сервер | Число бэкендов, ожидающих блокировки / Число бэкендов в состоянии idle in transaction | число |
| Сервер | Число бэкендов с транзакциями, открытыми дольше N минут | число (N задаётся в поле **Возраст транзакции (минуты)**) |
| Сервер | Общее число бэкендов | число |
| База данных | Число бэкендов / Доля бэкендов от максимума подключений | число / % |
| База данных | Доля фиксаций | % |
| База данных | Возраст XID в процентах от autovacuum_freeze_max_age | % |
| База данных | Размер базы данных | байты |
| База данных | Число отключённых триггеров | число |
| База данных | Попадания в кеш | % |
| Таблица | Время с последней очистки (vacuum) / Время с последнего сбора статистики (analyze) (никогда не выполнявшийся считается бесконечно давним) | время |
| Таблица | Размер таблицы / Раздувание таблицы | байты |
| Таблица | Раздувание таблицы в процентах от размера | % |
| Табличное пространство | Размер табличного пространства | байты |
| Табличное пространство | Свободное место на диске / Свободные inode | % |
| Запрос | Макс. время выполнения запроса / Среднее время выполнения запроса | время |

Примеры полезных правил:

- Сервер · Число бэкендов, ожидающих блокировки · больше 10 · Предупреждение;
- Сервер · Число неактивных слотов репликации · больше 0 · Критично;
- База данных · Возраст XID в процентах от autovacuum_freeze_max_age · больше 150 · Предупреждение;
- База данных · Попадания в кеш · меньше 90 % · Предупреждение;
- Табличное пространство · Свободное место на диске · меньше 15 % · Критично;
- Таблица · Время с последней очистки (vacuum) · больше 7 дней · Предупреждение, *имя начинается с* `prod.public.`;
- Запрос · Макс. время выполнения запроса · больше 3 минут · Предупреждение.

### Уведомления

Добавьте один или несколько каналов: выберите **Канал**, укажите **Адрес** и **Язык уведомлений**
(русский или английский, по умолчанию — текущий язык интерфейса), нажмите **Добавить**. Язык канала виден
в списке рядом с ним. Так, например, можно отправлять уведомления в русскоязычный Slack-канал и англоязычный
PagerDuty одновременно. Кнопка **Проверить** отправляет тестовое уведомление на языке канала.

| Канал | Что указать |
|---|---|
| Email | адреса через запятую; нужен настроенный SMTP (`PGSCOPE_SMTP_ADDR`) |
| Slack | URL Incoming Webhook (`https://hooks.slack.com/services/...`) |
| PagerDuty | ключ интеграции сервиса (Events API v2); инцидент автоматически закрывается, когда все алерты прошли |
| VictorOps (Splunk On-Call) | URL REST-эндпоинта с ключом маршрутизации (routing key); при снятии алертов отправляется RECOVERY |
| xMatters | URL входящей интеграции |
| Вебхук | любой `http(s)` URL, см. формат ниже |

Уведомления отправляются **только при изменении** набора сработавших алертов (появился новый, исчез старый,
поменялся уровень), а не при каждом отчёте. Когда всё нормализовалось, приходит уведомление с пустым списком.
Если уведомлений нет, значит, состояние с прошлого уведомления не изменилось.

### Формат вебхука

Запрос `POST`, `Content-Type: application/json`, `User-Agent: pgscope-Webhook/1`. Обработчик должен ответить
кодом 2xx в течение 3 секунд; при таймауте pgscope ждёт 5 секунд и повторяет запрос, не больше трёх раз
(ответы с ошибкой не повторяются). Формат совместим с вебхуками pgDash:

```json
{
  "version": 1,
  "server": "prod-db-1",
  "reported": 1793008773,
  "alerts": [
    {
      "type": "crit",
      "text": "Размер базы данных больше 10 ГиБ",
      "value": "14,4 ГиБ",
      "objname": "inventory",
      "objlink": "https://monitor.example.com/#/s/1/databases/inventory"
    },
    {
      "type": "warn",
      "text": "Макс. время выполнения запроса больше 3 мин",
      "value": "4 мин",
      "objname": "select * from orders",
      "objlink": "https://monitor.example.com/#/s/1/queries/shop/712461705543615171",
      "query": "select * from orders where ..."
    }
  ]
}
```

`type` — `warn` или `crit`, `reported` — время отчёта (Unix-секунды), пустой `alerts` означает, что все алерты сняты.

## 11. Оповещения об изменениях

Раздел **Оповещения об изменениях** сравнивает каждый новый отчёт с предыдущим и сообщает о важных изменениях. Это помогает
заметить незапланированные обновления, восстановление из бэкапа, изменение схемы, массовую вставку или удаление
данных и изменения прав.

1. В блоке **Отслеживаемые изменения** отметьте нужные виды изменений (**Выбрать все** — все):
   - «Перезапуск сервера», «Изменение версии PostgreSQL», «Изменение системного идентификатора (восстановление
     или новый кластер)», «Изменение режима восстановления (повышение или понижение)»;
   - «Добавление, удаление или изменение пользователей / ролей» (атрибуты, членство в группах);
   - «Добавление или удаление баз данных», «Добавление или удаление таблиц», «Добавление или удаление индексов»,
     «Добавление или удаление слотов репликации», «Добавление, удаление или обновление расширений»;
   - «Изменение параметров конфигурации», «Отключение триггеров»;
   - «Резкое изменение размера таблицы», «Резкое изменение числа строк таблицы», «Резкое изменение размера
     базы данных», «Резкое изменение размера табличного пространства».
2. В поле **«Резким» считается изменение более чем на (%)** задайте порог в процентах (по умолчанию 20 %).
   Таблицы меньше 1 МиБ и меньше 1000 строк не учитываются, чтобы не было шума.
3. **Сохранить**.
4. Добавьте каналы в блоке **Уведомления** ниже — они отдельные от каналов обычных алертов.

Каждое найденное изменение приходит сразу и попадает в **Обнаруженные изменения** (**Было** → **Стало**).
Формат вебхука:

```json
{
  "version": 1,
  "server": "prod-db-1",
  "prevreport": 1567432246,
  "currreport": 1567432291,
  "changes": [
    { "item": "Добавлена таблица", "curr": "shop.public.invoices" },
    { "item": "Изменён параметр «work_mem»", "prev": "4096", "curr": "16384" }
  ]
}
```

## 13. Профиль, аккаунт, удаление данных

На странице **Профиль**:

- **API-ключ → Сгенерировать заново** — выпустить новый ключ. Старый перестаёт работать сразу, поэтому обновите его во
  всех cron-задачах.
- **Смена пароля** — смена пароля (нужен текущий).
- **Удалить аккаунт** (блок **Опасная зона**) — удалить аккаунт. Для владельца удаляются и все его серверы со всеми данными.
  Аккаунт участника удаляется без влияния на чужие серверы.

Удалить один сервер: **Команда и настройки → Удаление данных сервера**, введите имя сервера для подтверждения
и нажмите **Удалить сервер**.
Удаляются отчёты, графики, правила и доступы. Если отчёты продолжат приходить под этим именем, сервер
создастся заново.

## 14. Хранение данных

Всё хранится в базе `PGSCOPE_DB`:

- полные отчёты в сжатом виде — `PGSCOPE_REPORT_RETENTION_DAYS` дней (по умолчанию 14); последний отчёт
  каждого сервера сохраняется всегда;
- временные ряды и история алертов и изменений — `PGSCOPE_METRICS_RETENTION_DAYS` дней (по умолчанию 90).

Старые данные удаляются автоматически раз в час. Объём растёт с числом таблиц и индексов: на каждый объект
приходится одна строка ряда на каждый отчёт. Для серверов с десятками тысяч таблиц сократите сбор флагами
pgmetrics (`-c`, `-A`, `--omit`) или уменьшите срок хранения. Базу pgscope бэкапьте как обычную базу PostgreSQL.

## 15. Типовые сценарии

**«База тормозит».** Обзор → резкие изменения на графиках транзакций, бэкендов, попаданий в кеш.
Затем Блокировки (нет ли цепочки блокировок) → Бэкенды (долгие сессии и простой в транзакции) →
Запросы (сортировка по «Общее время», что изменилось) → страница запроса: Советы и планы.
Чтобы посмотреть, что было во время инцидента, выберите прошлый отчёт в верхней панели.

**«Заканчивается место».** Диагностика → «Диск почти заполнен» / «Неактивные слоты репликации» / «Слишком много
файлов WAL». Затем Репликация → слоты (удерживаемый WAL), WAL и контрольные точки (архивация), Топ-k → *Рост размера*
за 7 дней, Таблицы → раздувание. Поставьте алерт Табличное пространство · Свободное место на диске · меньше 15 %.

**«Реплика отстаёт».** Репликация → лаг по реплике и график, на реплике — пауза воспроизведения и приёмник WAL.
Инспектор → Репликация покажет все серверы сразу.

**«Убрать лишние индексы».** Управление индексами → Неиспользуемые за последние 30 дней → отметить → скопировать SQL;
Дубликаты → удалить дубли. Проверьте индексы на репликах, где идут свои запросы.

**«Риск wraparound».** Очистка (vacuum) → «Возраст XID по базам данных» и «Самые старые таблицы (возраст
замороженного XID)», Бэкенды → долгие транзакции (они мешают заморозке), Репликация → слоты с `xmin`. Поставьте
алерт База данных · Возраст XID в процентах от autovacuum_freeze_max_age · больше 150.

**«Кто что поменял».** Включите оповещения об изменениях пользователей / ролей, таблиц, индексов и параметров
конфигурации — каждое изменение будет приходить в Slack или на почту.

**«Объяснить коллеге».** AI-чат → «Кратко оцени состояние этого сервера.» или свой вопрос на любом языке.

## 16. Решение проблем

**Сервер не появляется после отправки отчёта.** Проверьте вывод pgdash CLI (код ответа, раздел 5), что указан
`--base-url` с `/api/v1` и что ключ скопирован из профиля этого же pgscope. Запустите с `--debug`.

**Точка у сервера жёлтая.** Последний отчёт старше 15 минут — проверьте cron и логи сбора.

**На странице «Запросы» пусто.** Не установлен или не читается pg_stat_statements (раздел 4), либо у пользователя
нет роли `pg_monitor`.

**Нет планов выполнения.** Нужны `auto_explain` с `log_format = json`, запросы дольше
`auto_explain.log_min_duration` и доступ pgmetrics к логу (запуск на хосте, `--log-file` / `--log-dir`
или `--aws-rds-dbid`). Планы ищутся только в логах за `--log-span` минут.

**Пустые «Система», «Журнал», история autovacuum, заполнение дисков.** pgmetrics запущен не на хосте БД.

**График рваный или с пропуском.** Отчёт в это время не пришёл или pgmetrics не смог прочитать размеры из-за
блокировки (`--lock-timeout`). Точки с неизвестным размером пропускаются, а не рисуются нулём.

**Нет пункта PgBouncer.** Он появляется после первого отчёта `report-pgbouncer` для этого сервера
(список обновляется раз в минуту или после перезагрузки страницы).

**Email не приходят.** Не задан `PGSCOPE_SMTP_ADDR` — на странице уведомлений будет предупреждение.
Проверьте кнопкой **Проверить**: ошибка SMTP покажется в интерфейсе и в логе pgscope.

**Вебхук не вызывается.** Уведомления отправляются только при изменении набора алертов. Кнопка **Проверить**
отправит запрос сразу. Ответ должен быть 2xx не позже чем через 3 секунды.

**AI-чат пишет, что не настроен.** Задайте `PGSCOPE_AI_KEY` и перезапустите pgscope.

**Ошибка 429 в cron.** Отчёты идут чаще `PGSCOPE_MIN_REPORT_INTERVAL` — увеличьте интервал запуска.
